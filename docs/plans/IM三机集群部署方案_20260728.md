# 通用 IM 三机集群部署方案

**日期：** 2026-07-28  
**适用项目：** `genericim-tongba`  
**目标：** 使用 3 台同构服务器横向扩展 API 与 Mongo/Redis 集群，MySQL 与对象存储保留在 node1，以最低成本解决 API 单点和 Mongo/Redis 单点问题。

## 1. 结论

本方案描述的"3 机集群"是对《IM 完整集群部署与改造方案》第一阶段的**成本优化版**：把不能轻易分布的 MySQL 和对象存储留在 node1，仅对 MongoDB 和 Redis 做 3 节点集群化，把 Go API 在每台机器各跑一份。

| 模块 | 当前状态 | 集群风险 | 本方案处理 |
| --- | --- | --- | --- |
| REST API | 单实例 | 单点 | **三机各跑一份**，由 Nginx 负载均衡 |
| WebSocket | `Hub` 进程内 | 单节点视角 | 三节点 + Redis Streams 事件总线 |
| MySQL | 单实例 | 单点 | **保留在 node1 单实例**（带每日备份） |
| MongoDB | 单实例 | 单点 | **3 节点副本集**，primary 可在任意节点 |
| Redis | 单实例 | 单点 | **Redis Cluster 3 主 3 从（6 实例，每机 2 实例）** |
| 对象存储 | 本地 volume | 单机可见 | **保留在 node1**，API 走内网访问；或迁移到 S3 兼容存储 |
| 定时任务 | 每进程 ticker | 多节点重复 | Redis 分布式锁 + 幂等 |
| Nginx | 单点 | 单点 | **建议保留在 node1**，但需注意单点；或前置云 LB |

正式上线前必须完成：

1. MongoDB 3 节点副本集切换（含连接串、读写偏好改造）。
2. Redis Cluster 6 节点（3 主 3 从）切换 + Streams 事件总线。
3. WebSocket 跨节点事件总线。
4. 后台任务分布式锁和幂等保护。
5. 节点标识、健康检查和优雅停机。

下列组件**仍是单点**，必须通过备份、监控和故障演练来兜底：

- MySQL（node1）：宕机即业务停摆；必须做从库热备 + binlog 备份。
- 对象存储（node1）：API 上传/下载受影响；可挂 S3 兼容存储替换。
- Nginx（如果部署在 node1）：流量入口单点；建议替换为云 LB 或独立 LB。

## 2. 目标架构

### 2.1 整体拓扑

```text
                ┌──────────────────────────────────┐
                │  Cloud LB / Nginx (推荐 node1)   │
                │  HTTPS + WebSocket Upgrade       │
                └──────────────┬───────────────────┘
                               │
            ┌──────────────────┼──────────────────┐
            │                  │                  │
   ┌────────▼────────┐ ┌───────▼────────┐ ┌───────▼────────┐
   │ node1           │ │ node2          │ │ node3          │
   │                 │ │                │ │                │
   │ Go API (×1~N)   │ │ Go API (×1~N)  │ │ Go API (×1~N)  │
   │ Nginx (可选)    │ │                │ │                │
   │ MySQL 8 主库    │ │ MySQL 从库?    │ │ MySQL 从库?    │
   │ MongoDB PRIMARY │ │ MongoDB SEC    │ │ MongoDB SEC    │
   │ Redis Cluster   │ │ Redis Cluster  │ │ Redis Cluster  │
   │  7000/7001     │ │  7002/7003     │ │  7004/7005     │
   │  (M1 + S1)      │ │  (M2 + S2)     │ │  (M3 + S3)     │
   │ Object Storage  │ │                │ │                │
   └─────────────────┘ └────────────────┘ └────────────────┘
            │                  │                  │
            └──────────────────┴──────────────────┘
                          内网互联
```

### 2.2 节点角色

| 节点 | API | MySQL | Mongo | Redis | 存储 | Nginx |
| --- | --- | --- | --- | --- | --- | --- |
| **node1** | ✓ | 主库 | PRIMARY（初始） | Redis M1+S1 (7000/7001) | 本地/挂载卷 | 推荐放置 |
| **node2** | ✓ | 可选从库 | SECONDARY | Redis M2+S2 (7002/7003) | — | — |
| **node3** | ✓ | 可选从库 | SECONDARY | Redis M3+S3 (7004/7005) | — | — |

要点：

- Mongo 副本集允许 primary 在任意节点，初始建议固定在 node1，便于和 MySQL/存储就近。
- Redis 三机采用 **Redis Cluster**（3 主 3 从共 6 实例），每机跑 1 主 1 从；业务 key 通过 `redis.NewClusterClient` 路由，无需关心主从切换；Streams 事件总线在 Cluster 下同样可用（`XADD` 会按 key 哈希到对应分片），消费者组语义保持一致。
- 如果 MySQL 后续要加从库，从库只放在 node2/node3，不提升为主（主从切换仍需人工介入）。
- 对象存储只在 node1 暴露，API 通过内网访问；如果想消除该单点，最简单是替换成 MinIO（仍可单实例运行）或直接上 S3。

### 2.3 流量路径

```text
客户端 → Cloud LB → Nginx(node1) → API node1/2/3 (轮询/最小连接)
                                       │
                  ┌────────────────────┼─────────────────────┐
                  │                    │                     │
              MySQL(node1)      Redis Cluster(go-redis ClusterClient)  Mongo(node 本机→primary)
                  │
            Object Storage(node1)
```

**网络优化建议**：

- API 通过 `redis.NewClusterClient` 接入 Redis Cluster，客户端内部维护 slots → 节点映射；本地存在 slot 时优先走本机，无 slot 时通过 `-MOVED` 重定向；无需关心主从切换。
- API 节点连接 MongoDB 时使用 **primaryPreferred** 读偏好，写操作走 primary；驱动自动从副本集发现所有节点。
- API 节点访问对象存储走 **node1 内网 IP**，避免公网流量。

## 3. 当前代码基线

### 3.1 WebSocket

`backend/internal/ws/hub.go` 中的 `Hub` 保存：

- `userID -> ClientSet`
- `chatID -> ClientSet`
- 当前进程在线人数
- 当前进程广播队列

`Hub` 不是消息权威存储，可以保留为本地连接路由器，但必须增加跨节点事件输入。

### 3.2 Redis

`backend/cmd/server/main.go` 已初始化 Redis、缓存和消息队列。`backend/internal/mq/queue.go` 使用 Redis 列表和延迟队列进行任务消费。

Redis 队列是"一个任务由一个消费者处理"的语义，不能直接用于 WebSocket 广播。WebSocket 广播需要"每个 API 节点都收到一份事件"的语义，应增加 Redis Streams 或专用 Pub/Sub。

### 3.3 上传

`compose.yaml` 默认将 `genericim_uploads` 挂载到 API 容器，`backend/config.yaml` 默认 storage provider 为 local。**在本方案中，该 local volume 仍放在 node1 上**，多 API 节点通过内网访问 node1 的存储路径（推荐走对象存储协议，而不是 NFS）。

### 3.4 后台任务

以下服务由 API 进程启动：

- `wallet_cron_service.go`
- `call_cleanup_service.go`
- `media_object_service.go`
- `chat_auto_message_service.go`
- Redis 延迟消息轮询

多节点后每个节点都会启动一份，必须使用 Redis 分布式锁做 leader 模式。

## 4. WebSocket 集群改造

### 4.1 事件分类

| 类型 | 示例 | 推荐机制 | 丢失处理 |
| --- | --- | --- | --- |
| 持久业务事件 | 新消息、撤回、编辑、群成员变化、系统通知 | Redis Streams | 客户端按 `seq` 补偿 |
| 瞬时状态事件 | typing、临时在线状态、呼叫铃状态 | Redis Pub/Sub | 丢失可接受，下一状态覆盖 |

不应把持久业务事件只放在 Redis Pub/Sub，因为订阅断开期间事件会丢失。

### 4.2 事件信封

所有跨节点事件统一使用如下结构：

```json
{
  "event_id": "uuid",
  "event_type": "message.created",
  "chat_id": "uuid",
  "user_ids": ["uuid"],
  "seq": 12345,
  "origin_node": "api-node1",
  "occurred_at": "2026-07-28T12:00:00Z",
  "payload": {}
}
```

要求：

- `event_id` 全局唯一。
- `seq` 使用数据库权威序号，不能使用节点本地自增值。
- `origin_node` 用于排查重复和延迟。
- 消费端必须幂等，同一个 `event_id` 重复到达不能造成业务重复。
- 业务写入数据库成功后再发布事件。

### 4.3 Streams 消费组

每个 API 节点使用独立 consumer group，以保证每个节点都收到完整事件：

```text
Stream: genericim:ws:events
Group:  genericim:ws-node:api-node1
Group:  genericim:ws-node:api-node2
Group:  genericim:ws-node:api-node3
```

每个节点内部仍由当前 `Hub` 将事件路由到本节点的本地连接。节点重启后使用 `XREADGROUP` 和 pending message reclaim 继续消费。

瞬时事件可以使用：

```text
Channel: genericim:ws:ephemeral
```

节点断开期间不要求补发 typing 等瞬时状态。

### 4.4 发送流程

```text
HTTP/WS 请求
    |
    +-- MySQL/MongoDB 持久化
    |
    +-- 写入 Redis Stream
    |
    +-- 所有 API 节点消费
    |
    +-- 每个节点的本地 Hub 路由
    |
    +-- 客户端按 message_id/seq 去重
```

### 4.5 在线状态

当前 Hub 的在线人数只能代表单节点。集群后：

- Redis 保存 `presence:user:{id}`，使用 TTL。
- 节点连接建立时写入节点和设备信息。
- 心跳续期，断开时只删除当前连接对应的 token。
- "用户是否在线"以 Redis 中是否存在有效连接为准。
- 管理端统计区分 `local_online` 和 `global_online`。

## 5. 上传和媒体处理

### 5.1 生产存储方案

**方案 A（推荐）：S3 兼容存储（MinIO 或云 OSS）**

即使对象存储跑在 node1，也用 S3 协议而非本地 volume：

```yaml
storage:
  provider: s3
  s3:
    region: ap-southeast-1
    endpoint: http://node1.internal:9000  # 内网 endpoint
    bucket: genericim-media
    public_base_url: https://media.example.com
    access_key: ${S3_ACCESS_KEY}
    secret_key: ${S3_SECRET_KEY}
```

优势：

- API 节点无状态，无需挂载任何 volume。
- 后续替换成 AWS S3 / 阿里云 OSS 时只改 endpoint。
- 媒体处理可以直接用预签名 URL，不需要走 API 节点中转。

**方案 B（最低成本）：node1 本地 volume**

```yaml
storage:
  provider: local
  local:
    base_url: https://media.example.com  # 经 Nginx 反代
```

要求：

- node1 至少 1TB 数据盘。
- API node2/node3 通过 Nginx 反代访问 node1 上的静态文件。
- 必须配置每日 `rsync` 或 `restic` 备份到异地。

### 5.2 媒体处理

媒体处理服务应使用对象存储 URL 或预签名 URL，不依赖某一个 API 节点的本地临时文件。处理结果写回对象存储，并在数据库中原子推进状态：

```text
uploading -> uploaded -> processing -> processed
                         \-> failed
```

同一个媒体对象必须使用数据库幂等键和对象 key，避免多个节点重复生成不可追踪的文件。

### 5.3 文件下载路径

```text
客户端 → CDN → Nginx(node1) → storage node1
                  │
                  └── 也可以让客户端直接用对象存储的 pre-signed URL
```

## 6. 后台任务和分布式锁

### 6.1 方案选择

三机部署下，**优先采用 Redis 锁方案**，不单独拆分 worker 服务：

1. API 节点保留 ticker，但使用 Redis 锁选举执行者。
2. 锁 key 持有者执行任务，其他节点跳过本轮。
3. 所有任务保留数据库幂等约束，锁失效不能导致重复扣款或重复发放。

后续如果任务量增长，再把高负载任务（钱包 cron、媒体清理）拆成独立 worker 服务。

### 6.2 锁规范

锁 key 示例：

```text
genericim:lock:wallet-cron
genericim:lock:call-cleanup
genericim:lock:media-cleanup
genericim:lock:chat-auto-message
```

要求：

- 使用 Redis `SET NX EX`。
- value 使用 `node_id + random_token`。
- 释放锁必须校验 value，不能无条件 `DEL`。
- 任务执行时间超过 TTL 时需要续期或缩短批次。
- 任务日志记录 `node_id`、锁等待、执行耗时、处理数量。

### 6.3 Redis Cluster 下的锁可靠性

Redis Cluster 在主从切换（master 故障 → 新 master 晋升）期间也会出现"旧持锁者短暂失去锁、新候选者拿到锁"的风险；此外 Cluster 还引入 hash slot 维度的不确定因素。补偿措施：

- **必须给锁 key 加 hash tag**：`SET genericim:lock:{wallet_cron}:run NX EX 30`，强制所有锁 key 落在同一 slot，避免跨 slot 时 `SET + DEL` 不是原子的（Cluster 跨 slot 的事务靠 `MSET`/`EVAL` 都不可靠，唯一可行是 hash tag）。
- 任务粒度必须保证**幂等**：即使双节点并发执行，业务结果必须一致。
- 任务批次大小要小（< TTL 的一半），让任务在主从切换前完成。
- 关键任务（钱包）建议额外加数据库乐观锁或唯一约束作为最后防线。
- Cluster 不支持 `SCRIPT FLUSH` 在全部节点生效（如需跨节点 Lua 脚本，请用 `EVALSHA` 并确保脚本 key 在同一 slot），本方案 `wallet_cron_service` 不依赖 Lua，加锁只是 `SET NX EX` + `DEL`，零迁移成本。

## 7. 负载均衡配置要求

### 7.1 Nginx 推荐配置（放在 node1）

```nginx
upstream genericim_api {
    # 三台 API 节点，按权重或最小连接调度
    server node1.internal:8080 weight=1 max_fails=3 fail_timeout=30s;
    server node2.internal:8080 weight=1 max_fails=3 fail_timeout=30s;
    server node3.internal:8080 weight=1 max_fails=3 fail_timeout=30s;
    keepalive 64;
}

server {
    listen 443 ssl;
    server_name api.example.com;

    ssl_certificate     /etc/ssl/certs/example.com.pem;
    ssl_certificate_key /etc/ssl/private/example.com.key;

    location /api/v1/ws {
        proxy_pass http://genericim_api;
        proxy_http_version 1.1;
        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection "upgrade";
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_read_timeout 3600s;
        proxy_send_timeout 3600s;
    }

    location /api/ {
        proxy_pass http://genericim_api;
        proxy_http_version 1.1;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }

    location /health {
        proxy_pass http://genericim_api;
    }

    location /ready {
        proxy_pass http://genericim_api;
    }
}
```

### 7.2 节点健康

- API 节点必须提供 `/health` 和 `/ready`。
- `/ready` 应检查必要的 MySQL、MongoDB、Redis 连接状态。
- 正在排空的节点先从负载均衡摘除，再等待 WebSocket 连接自然关闭或发送重连提示。

### 7.3 Nginx 单点补偿

Nginx 部署在 node1 上是单点，可选方案：

1. **云 LB 替代**：把 Nginx 换成云厂商负载均衡（ALB/CLB），后端直接挂三台 API。
2. **双 Nginx + keepalived**：node1 和 node2 各跑一个 Nginx，VIP 漂移。
3. **Nginx 多实例 + DNS 轮询**：解析到三个 Nginx IP，客户端随机，但故障切换慢。

推荐方案 1，成本最低且运维最简单。

### 7.4 完整 Nginx 配置（生产模板）

下面给出一份**可直接用于生产**的 nginx.conf，覆盖：

- HTTPS 入口 + WebSocket Upgrade
- `proxy_next_upstream` 自动 failover
- 限流、访问日志统一字段
- 主动健康检查接入点（见 §7.5）

**部署位置**：node1 的 `/etc/nginx/nginx.conf`（如果是 docker，volume 挂进去）。

```nginx
user  nginx;
worker_processes auto;
worker_rlimit_nofile 65535;
error_log  /var/log/nginx/error.log warn;
pid        /var/run/nginx.pid;

events {
    worker_connections 4096;
    use epoll;
    multi_accept on;
}

http {
    include       /etc/nginx/mime.types;
    default_type  application/octet-stream;
    sendfile        on;
    tcp_nopush      on;
    tcp_nodelay    on;
    keepalive_timeout 65;
    types_hash_max_size 2048;

    # JSON 访问日志（便于 ELK/Loki 采集）
    log_format json escape=json '{'
        '"ts":"$time_iso8601",'
        '"remote_addr":"$remote_addr",'
        '"x_forwarded_for":"$proxy_add_x_forwarded_for",'
        '"req":"$request",'
        '"status":$status,'
        '"upstream":"$upstream_addr",'
        '"upstream_status":"$upstream_status",'
        '"upstream_response_time":"$upstream_response_time",'
        '"node":"$upstream_http_x_node_id",'
        '"req_time":"$request_time",'
        '"host":"$host",'
        '"uri":"$uri"'
    '}';
    access_log /var/log/nginx/access.log json;

    server_tokens off;

    # WebSocket Upgrade 头映射
    map $http_upgrade $connection_upgrade {
        default upgrade;
        ''      close;
    }

    # upstream —— 三台 API
    upstream genericim_api {
        # 最小连接数调度，公平性比 round-robin 更好
        least_conn;

        server node1.internal:8080 max_fails=2 fail_timeout=10s;
        server node2.internal:8080 max_fails=2 fail_timeout=10s;
        server node3.internal:8080 max_fails=2 fail_timeout=10s;

        keepalive 64;
        keepalive_requests 1000;
        keepalive_timeout 60s;
    }

    # 独立 health upstream（不与流量混合）
    upstream genericim_api_health {
        server node1.internal:8080;
        server node2.internal:8080;
        server node3.internal:8080;
    }

    # 限流
    limit_req_zone $binary_remote_addr zone=login_limit:10m rate=10r/m;
    limit_req_zone $binary_remote_addr zone=api_limit:10m rate=200r/s;

    server {
        listen 80;
        server_name api.example.com;
        return 301 https://$host$request_uri;
    }

    server {
        listen 443 ssl http2;
        server_name api.example.com;

        ssl_certificate     /etc/ssl/certs/example.com.pem;
        ssl_certificate_key /etc/ssl/private/example.com.key;
        ssl_protocols       TLSv1.2 TLSv1.3;
        ssl_ciphers         HIGH:!aNULL:!MD5;
        ssl_session_cache   shared:SSL:10m;
        ssl_session_timeout 1d;

        proxy_http_version 1.1;
        proxy_set_header Host              $host;
        proxy_set_header X-Real-IP         $remote_addr;
        proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;

        # WebSocket
        location /api/v1/ws {
            proxy_pass http://genericim_api;
            proxy_set_header Upgrade    $http_upgrade;
            proxy_set_header Connection $connection_upgrade;
            proxy_read_timeout  3600s;
            proxy_send_timeout  3600s;
            proxy_buffering off;
            proxy_next_upstream error timeout http_502 http_503 http_504;
            proxy_next_upstream_tries 2;
        }

        # 普通 REST
        location /api/ {
            proxy_pass http://genericim_api;
            limit_req zone=api_limit burst=400 nodelay;
            proxy_connect_timeout 2s;
            proxy_send_timeout    30s;
            proxy_read_timeout    60s;
            proxy_next_upstream error timeout http_502 http_503 http_504;
            proxy_next_upstream_tries 2;
            proxy_next_upstream_timeout 10s;
        }

        # 登录/注册敏感接口限流
        location ~ ^/api/v\d+/(login|register|sms) {
            proxy_pass http://genericim_api;
            limit_req zone=login_limit burst=20 nodelay;
            proxy_connect_timeout 2s;
            proxy_read_timeout    10s;
            proxy_next_upstream error timeout http_502 http_503 http_504;
        }

        # nginx 自身健康
        location = /health {
            access_log off;
            default_type application/json;
            return 200 '{"status":"ok","node":"nginx-node1"}';
        }

        # 后端节点健康（独立 upstream）
        location = /ready {
            proxy_pass http://genericim_api_health;
            access_log off;
            proxy_connect_timeout 1s;
            proxy_read_timeout    2s;
        }
    }
}
```

> **说明**：
> - `least_conn` 比 `round-robin` 更适合 IM 这种**长连接 + 短请求混合**的场景：每个 API 节点的当前连接数会更均衡。
> - `proxy_next_upstream` 配合 `tries=2` 让 nginx 在 502/503/504 时自动 failover 到下一节点，**对客户端几乎无感知**（仅多几十 ms）。
> - `/ready` 走的是独立 upstream，专门用于探测节点是否在线（不与流量混合）。

### 7.5 主动健康检查

仅靠 `proxy_next_upstream` 的被动 failover 不够，**生产环境必须加主动健康检查**，在节点真正故障时立刻摘除。

**方案 A（推荐 OSS 版）：nginx + lua + redis**

```nginx
# 需要编译时带 lua 模块（openresty 即可）
init_worker_by_lua_block {
    local redis = require "resty.redis"
    local ok, err = redis.connect(redis, "127.0.0.1", 6379)
    if not ok then
        ngx.log(ngx.ERR, "redis connect failed: ", err)
    end
}

server {
    location = /internal/healthcheck {
        internal;
        content_by_lua_block {
            local http = require "resty.http"
            local nodes = {"node1.internal:8080", "node2.internal:8080", "node3.internal:8080"}
            for _, n in ipairs(nodes) do
                local cli = http.new()
                cli:set_timeout(1000)
                local res, err = cli:request_uri("http://" .. n .. "/ready")
                if res and res.status == 200 then
                    ngx.shared.upstream_health:set(n, "up", 5)
                else
                    ngx.shared.upstream_health:set(n, "down", 5)
                end
            end
        }
    }
}
```

**方案 B（最简单）：用 cron curl + `nginx -s reload`**

```bash
#!/bin/bash
# /usr/local/bin/check-api.sh
NODES=("node1.internal:8080" "node2.internal:8080" "node3.internal:8080")
UPSTREAM=/etc/nginx/upstream.conf

declare -a UP_LIST
for n in "${NODES[@]}"; do
    if curl -sf -m 2 "http://$n/ready" >/dev/null; then
        UP_LIST+=("server $n max_fails=2 fail_timeout=10s;")
    else
        UP_LIST+=("# server $n down;")
    fi
done

cat > $UPSTREAM <<EOF
upstream genericim_api {
    least_conn;
    $(IFS=$'\n'; echo "${UP_LIST[*]}")
    keepalive 64;
}
EOF

nginx -t && nginx -s reload
```

加 crontab：

```cron
* * * * * /usr/local/bin/check-api.sh >> /var/log/healthcheck.log 2>&1
```

**方案 C（Nginx Plus / Tengine）**：使用官方的 `health_check` 指令：

```nginx
upstream genericim_api {
    server node1.internal:8080;
    server node2.internal:8080;
    server node3.internal:8080;
    health_check uri=/ready interval=2s fails=2 passes=2;
}
```

生产推荐**方案 A 或 B**。方案 C 需要商业版/二次编译版 nginx。

### 7.6 负载均衡调度策略

| 策略 | 指令 | 适用场景 | 本方案选择 |
| --- | --- | --- | --- |
| 轮询 | `round-robin`（默认） | 短连接、负载均匀 | — |
| 最小连接 | `least_conn` | **长连接 + 短请求混合** | ✅ 推荐 |
| IP hash | `ip_hash` | 需要会话粘性 | —（不需要，见 §7.7） |
| 一致性 hash | `hash $key consistent` | 缓存亲和性 | — |
| 权重 | `weight=N` | 节点性能差异 | 可选（初期全部 1） |

**推荐配置**：

```nginx
upstream genericim_api {
    least_conn;
    server node1.internal:8080 weight=1;
    server node2.internal:8080 weight=1;
    server node3.internal:8080 weight=1;
}
```

- IM 流量是"少数 ws 长连接 + 大量短消息"组合，`least_conn` 避免某节点集中大量 ws 连接后新请求打爆它。
- 节点性能一致时全部 `weight=1`；后续如果节点配置不同（如加机器做 raid0），再调整权重。

### 7.7 WebSocket 是否需要粘性会话

**结论：本方案不需要 sticky session。**理由：

1. WebSocket 连接建立后就被绑定到一个节点，但**消息已经走 Redis Streams 总线**，跨节点消息会自动到达所有节点并被本地 Hub 路由。
2. 真正的会话状态（在线列表、未读、typing）全部在 Redis 或 Mongo，全局可见。
3. 客户端重连时会落到另一节点，业务无影响。

如果业务上**确实需要粘性**（例如某个客户端长连接中断重试时不希望换节点），可加 IP hash：

```nginx
upstream genericim_api {
    ip_hash;   # 同一客户端 IP 落到同一节点
    server node1.internal:8080;
    server node2.internal:8080;
    server node3.internal:8080;
}
```

**注意**：

- 移动网络下客户端 IP 会变（4G/5G 切换、WiFi 漫游），粘性可能失效。
- `ip_hash` 会让某 IP 集中到某节点，不一定均衡。
- **推荐保持 `least_conn`**，把"粘性"交给客户端的**自动重连逻辑**（客户端 SDK 检测到 ws 断开就 reconnect 一次）。

### 7.8 节点摘除与滚动发布

**滚动发布流程**（假设要升级 API 到 v2）：

```bash
# 1. 把 node3 标记为不可用（优雅摘除）
curl -X POST http://node3:8080/admin/drain  # API 应提供 /admin/drain，让 /ready 返回非 200
# 或直接停掉 node3 上的 nginx upstream 中的 server：
sed -i 's/server node3.internal/# server node3.internal/' /etc/nginx/upstream.conf
nginx -s reload

# 2. 等待 node3 的 ws 连接自然断开（或推送重连提示）
sleep 60  # 等 1 分钟

# 3. 升级 node3 的 API
ssh node3 "docker pull genericim-tongba:v2 && docker compose up -d api"

# 4. 验证 node3 健康
curl http://node3:8080/ready

# 5. 恢复 node3 的 upstream
sed -i 's/# server node3.internal/server node3.internal/' /etc/nginx/upstream.conf
nginx -s reload

# 6. 同样的步骤对 node1 和 node2 执行
```

**API 侧 `/admin/drain` 的实现要点**：

```go
mux.HandleFunc("/admin/drain", func(w http.ResponseWriter, r *http.Request) {
    drainFlag.Store(true)
    w.WriteHeader(200)
    log.Info("node entered drain mode")
})

mux.HandleFunc("/ready", func(w http.ResponseWriter, r *http.Request) {
    if drainFlag.Load() {
        w.WriteHeader(503)  // nginx 自动剔除
        return
    }
    // ... 健康检查逻辑（MySQL/Mongo/Redis 连接状态）
})
```

**观察指标**：

- `nginx upstream_status`：返回 200 的节点数。
- API 节点 `upstream_response_time`：摘除后其他节点延迟是否上升。
- WebSocket 重连率：摘除过程中是否陡增。

### 7.9 横向扩缩容（从 3 → N 节点）

**扩容步骤**（例如加到 5 节点）：

```bash
# 1. 准备 node4 和 node5
ssh node4 "git clone repo && cd repo && ./scripts/init.sh"
ssh node5 "git clone repo && cd repo && ./scripts/init.sh"

# 2. 在 node4 / node5 启动 API（不带 Mongo / Redis / Nginx）
ssh node4 "docker compose -f docker-compose.node4.yml up -d"
ssh node5 "docker compose -f docker-compose.node5.yml up -d"

# 3. 验证健康
curl http://node4:8080/ready
curl http://node5:8080/ready

# 4. 修改 nginx upstream，加入新节点
cat > /etc/nginx/upstream.conf <<EOF
upstream genericim_api {
    least_conn;
    server node1.internal:8080;
    server node2.internal:8080;
    server node3.internal:8080;
    server node4.internal:8080;  # 新增
    server node5.internal:8080;  # 新增
    keepalive 64;
}
EOF

nginx -t && nginx -s reload

# 5. 观察 5 分钟，确认流量分摊到 5 节点
tail -f /var/log/nginx/access.log | grep upstream_addr
```

**缩容**反过来：先把节点从 upstream 摘除 → 等 ws 连接断开 → 停服务。

**注意**：

- 扩容只增加 API 节点不会消除 MySQL / 对象存储单点，参考 §11 的缓解措施。
- 不要在同一台物理机上跑多份 API 来"扩容"——单点风险不会降低。
- 每次 upstream 变更都要先 `nginx -t` 验证语法，再 `nginx -s reload`。

### 7.10 双 Nginx + keepalived（自建高可用）

如果不愿意用云 LB，但希望消除 nginx 单点，可采用 node1 + node2 双 Nginx + keepalived 漂移 VIP：

**网络拓扑**：

```text
Internet → 公网 VIP（10.0.0.10，keepalived 漂移）
              │
   ┌──────────┴──────────┐
   │                     │
node1 (MASTER)     node2 (BACKUP)
Nginx + keepalived Nginx + keepalived
权重 100             权重 90
```

**node1 `/etc/keepalived/keepalived.conf`**：

```conf
vrrp_script check_nginx {
    script "/usr/local/bin/check-nginx.sh"
    interval 2
    weight  -20
    fall     3
    rise     2
}

vrrp_instance VI_1 {
    state MASTER
    interface eth0          # 网卡名
    virtual_router_id 51
    priority 100
    advert_int 1

    authentication {
        auth_type PASS
        auth_pass 123456
    }

    virtual_ipaddress {
        10.0.0.10/24          # VIP
    }

    track_script {
        check_nginx
    }

    notify_master "/usr/local/bin/notify.sh master"
    notify_backup "/usr/local/bin/notify.sh backup"
    notify_fault   "/usr/local/bin/notify.sh fault"
}
```

**node1 `/usr/local/bin/check-nginx.sh`**：

```bash
#!/bin/bash
if ! pgrep nginx >/dev/null; then
    exit 1
fi
curl -sf -m 1 http://127.0.0.1/health >/dev/null || exit 1
exit 0
```

**node2 配置**几乎相同，只改 `priority 90` 和 `state BACKUP`。

**DNS / 上游指向**：

- 上游（云解析 / 客户端）直接指向 VIP `10.0.0.10`。
- keepalived 检测 nginx 健康，nginx 故障时 VIP 漂移到 node2，~3s 切换。

**代价**：

- 维护成本高（keepalived 配置、VRRP 协议、组播/单播、心跳网络）。
- VIP 漂移过程中**有秒级中断**，需要客户端 SDK 容错。
- 不如云 LB 简单。

### 7.11 访问日志与故障排查

**统一日志格式**：nginx 用 JSON 格式（见 §7.4 配置中的 `log_format json`），便于 ELK / Loki 采集。

**关键字段**：

- `upstream_addr`：实际命中的 API 节点（排查流量不均）。
- `upstream_status`：上游返回状态码（排查 5xx）。
- `upstream_response_time`：上游响应耗时（排查慢节点）。
- `node`（来自 API 响应头 `X-Node-Id`）：每个请求归属哪个 API 进程。

**常用排查命令**：

```bash
# 1. 实时观察 upstream 命中
tail -f /var/log/nginx/access.log | jq '.upstream_addr, .upstream_response_time, .status'

# 2. 各节点流量占比（最近 1000 条）
tail -1000 /var/log/nginx/access.log | jq -r '.upstream_addr' | sort | uniq -c

# 3. 慢请求（> 1s）
tail -f /var/log/nginx/access.log | jq 'select(.upstream_response_time > 1)'

# 4. 5xx 错误
tail -f /var/log/nginx/access.log | jq 'select(.status >= 500)'
```

**典型故障场景**：

| 现象 | 排查方向 |
| --- | --- |
| 某节点流量一直偏少 | upstream 配置、`max_fails` 是否把它摘除了、API 自身 `/ready` 是否正常 |
| 客户端偶发 502 | `proxy_next_upstream_tries` 是否过小；后端是否真在重启；nginx error log |
| WebSocket 频繁断开 | API 节点是否在 drain；nginx `proxy_read_timeout` 是否够大；keepalive 是否被中间设备重置 |
| 摘除节点后流量不切换 | nginx 缓存、`upstream` reload 是否生效；DNS 是否缓存 |

## 9. 数据层策略

### 9.1 MongoDB（3 节点副本集）

- 每台机器一个 `mongod` 进程，加入同一个副本集 `rs0`。
- 初始 primary 固定在 node1；后续允许自动 failover。
- 应用连接串必须包含副本集信息和正确的读写偏好：

  ```text
  mongodb://node1:27017,node2:27017,node3:27017/?replicaSet=rs0&readPreference=primaryPreferred
  ```

- 消息历史写入不能依赖某个 API 节点的本地 Mongo 连接状态。
- 推荐为消息集合配置合适的 `writeConcern`（`majority`）以保证副本集多数派写入。
- Oplog 大小建议 ≥ 50GB，避免高写入场景被覆盖。

**副本集初始化**（仅在首次部署执行）：

```javascript
rs.initiate({
  _id: "rs0",
  members: [
    { _id: 0, host: "node1:27017", priority: 2 },   // 优先 primary
    { _id: 1, host: "node2:27017", priority: 1 },
    { _id: 2, host: "node3:27017", priority: 1 }
  ]
});
```

### 9.2 Redis Cluster（3 主 3 从，6 实例）

- 每台机器跑 **2 个 Redis 实例**：1 主 1 从；6 个实例组成 3 主 3 从的 Cluster。
- 不使用 Sentinel，Cluster 自带故障检测和 master 晋升（`cluster-node-timeout` 触发选举）。
- 应用侧用 `redis.NewClusterClient`，客户端内置 slot 路由和 `-MOVED` 重定向，对业务透明。
- 必须强制所有 key 使用 hash tag 共享 slot 的场景（如分布式锁、Lua 脚本、`MSET` 等）。
- Redis 密码 + ACL 限制内网访问；**强烈建议开启 `protected-mode yes` + `bind 内网网卡`**。

#### 9.2.1 拓扑与端口规划

| 节点 | 实例 | 角色 | 端口 | 数据目录 | 配置文件 |
| --- | --- | --- | --- | --- | --- |
| node1 | redis-1 | master(M1) | 7000 | `/var/lib/redis/7000` | `/etc/redis/7000.conf` |
| node1 | redis-2 | slave(S1) ← M2 | 7001 | `/var/lib/redis/7001` | `/etc/redis/7001.conf` |
| node2 | redis-3 | master(M2) | 7002 | `/var/lib/redis/7002` | `/etc/redis/7002.conf` |
| node2 | redis-4 | slave(S2) ← M3 | 7003 | `/var/lib/redis/7003` | `/etc/redis/7003.conf` |
| node3 | redis-5 | master(M3) | 7004 | `/var/lib/redis/7004` | `/etc/redis/7004.conf` |
| node3 | redis-6 | slave(S3) ← M1 | 7005 | `/var/lib/redis/7005` | `/etc/redis/7005.conf` |

> 从节点故意**不放在本机**，而是交错：M1↔S1、M2↔S2、M3↔S3 分布在不同机器上，单机宕机不会同时丢失一个分片的主从。

#### 9.2.2 单实例配置示例（`/etc/redis/7000.conf`）

```conf
# 监听端口（每个实例不同：7000~7005）

bind 10.0.0.11                  # 内网网卡，禁止 0.0.0.0
protected-mode yes
daemonize yes
pidfile /var/run/redis_7000.pid
logfile /var/log/redis/7000.log
dir /var/lib/redis/7000

appendfilename "appendonly-7000.aof"
appendfsync everysec

# 集群模式
cluster-enabled yes
cluster-config-file nodes-7000.conf
cluster-node-timeout 15000
cluster-replica-validity-factor 0
cluster-migration-barrier 1
cluster-require-full-coverage yes

# 安全
requirepass ${REDIS_PASSWORD}
masterauth ${REDIS_PASSWORD}
rename-command FLUSHALL ""
rename-command FLUSHDB ""
rename-command KEYS ""
```

> 其余 5 个实例（7001~7005）只需要把 `port`、`pidfile`、`logfile`、`dir`、`appendfilename`、`cluster-config-file` 中的端口号替换为对应值，其他字段相同。`requirepass` / `masterauth` 通过环境变量注入，不进版本控制。

#### 9.2.4 创建集群（只需在 node1 执行一次）

```bash
redis-cli --cluster create \
  10.0.0.11:7000 10.0.0.12:7002 10.0.0.13:7004 \
  10.0.0.12:7003 10.0.0.13:7005 10.0.0.11:7001 \
  --cluster-replicas 1 \
  --user default \
  -a "${REDIS_PASSWORD}" \
  --cluster-yes
```

参数说明：

- 前 3 个地址（7000/7002/7004）会被识别为 **master**（M1/M2/M3），后 3 个为 **replica**。
- `--cluster-replicas 1`：每个 master 配 1 个 replica，CLI 自动交错（实际结果是 `7000→M1`、`7001→S1=replica-of M2`，依次类推）。
- 命令会以交互方式打印 slot 分配计划，确认输入 `yes` 完成创建。

#### 9.2.5 校验集群状态

```bash
# 看集群拓扑（每个 master 应该有 1 个健康 replica）
redis-cli -h 10.0.0.11 -p 7000 -a "${REDIS_PASSWORD}" cluster nodes

# 看 slot 分布（应全部 16384 个 slot 都有 owner）
redis-cli -h 10.0.0.11 -p 7000 -a "${REDIS_PASSWORD}" cluster info

# 写一个 key 验证客户端路由
redis-cli -h 10.0.0.11 -p 7000 -a "${REDIS_PASSWORD}" SET genericim:probe "ok"
redis-cli -h 10.0.0.12 -p 7002 -a "${REDIS_PASSWORD}" GET genericim:probe   # 应返回 "ok"，说明 cluster 路由正常
```

#### 9.2.6 防火墙与内网隔离

```bash
# 仅允许 API 网段访问 Redis 端口
iptables -A INPUT -p tcp --dport 7000:7005 -s 10.0.0.0/24 -j ACCEPT
iptables -A INPUT -p tcp --dport 7000:7005 -j DROP
```

`16379`（cluster bus 端口 = port + 10000）也必须在内网可达，否则节点之间无法通信和选举。

#### 9.2.7 应用侧连接代码（Go）

将 `backend/internal/cache/cache.go` 等单实例客户端改造为 Cluster 客户端：

```go
package cache

import (
    "os"
    "time"

    "github.com/redis/go-redis/v9"
)

// NewClusterClient 返回一个 Redis Cluster 客户端，覆盖三机 6 实例。
func NewClusterClient() *redis.ClusterClient {
    addrs := []string{
        "10.0.0.11:7000", "10.0.0.12:7002", "10.0.0.13:7004",
        "10.0.0.12:7003", "10.0.0.13:7005", "10.0.0.11:7001",
    }
    return redis.NewClusterClient(&redis.ClusterOptions{
        Addrs:        addrs,
        Password:     os.Getenv("REDIS_PASSWORD"),
        DialTimeout:  3 * time.Second,
        ReadTimeout:  2 * time.Second,
        WriteTimeout: 2 * time.Second,
        PoolSize:     50,                // 每节点连接池
        MinIdleConns: 10,
        MaxRetries:   2,
        // 让客户端自动发现新节点并维护 slot 映射
        ReadOnly:           false,
        RouteByLatency:     true,         // 优先选延迟最低的 replica 读（可选）
        ClusterSlotsFunc:   nil,
    })
}
```

`cmd/server/main.go` 启动时把原本的 `redis.NewClient(...)` 替换为 `NewClusterClient()`，`Cache` / `mq.Queue` 内部的 `*redis.Client` 替换为 `*redis.ClusterClient`，对外接口（`Get`/`Set`/`Incr`/`Eval` 等）保持不变。

#### 9.2.8 业务 key 改造清单（必须加 hash tag）

Cluster 下**跨 slot 的事务不可靠**，所有需要"原子读改写"或"分布式锁"的 key 必须用 `{}` 强制同 slot：

| 业务 | 原 key 模式 | Cluster 改造后 |
| --- | --- | --- |
| 钱包 cron 锁 | `genericim:lock:wallet_cron:run` | `genericim:lock:{wallet_cron}:run` |
| 消息序号 | `genericim:msg:seq:{chatID}` | `genericim:msg:{chatID}:seq`（已有 `{chatID}`） |
| 在线状态 | `presence:user:{uid}` | `presence:{uid}` |
| 会话未读 | `unread:{chatID}:{uid}` | `unread:{chatID}:uid`（chatID 在大括号内） |
| Streams 事件总线 | `genericim:ws:events` | `genericim:{ws}:events`（同 slot 保证消费者组共享） |

> Streams / Pub/Sub 本身**可以跨 slot 工作**，但消费者组的 pending list 会分布在不同分片；为了简化运维，建议给 Streams key 也加 hash tag，让所有事件落在同一个 slot（M1），便于监控和排障。

#### 9.2.9 备份与监控

- **RDB 快照**：每实例 `save 3600 1` + `save 300 100`，配合 AOF 持久化。
- **监控指标**：`cluster_enabled`、`cluster_known_nodes`、`cluster_size`、`connected_slaves`、`used_memory`、`instantaneous_ops_per_sec`、`slowlog`。
- **告警阈值**：任意 master `cluster_known_nodes < 3` 持续 30s 触发；任意实例 `used_memory > 80%` 触发；`instantaneous_input/output_kbps` 持续 > 100MB/s 触发。
- **数据备份**：每天从 1 个 replica 执行 `BGSAVE`，归档到 MinIO 或异地 OSS；恢复时通过 `redis-cli --cluster import` 重建。

### 9.3 MySQL（node1 单实例）

**风险明确：MySQL 仍是单点。** 补偿措施：

- **每日全量备份** + **binlog 实时归档**（异地）。
- **强同步从库**：node2 或 node3 可选作为 MySQL 从库（仅读、不提升主）。增加从库不会增加单点风险，但能在主库故障时提供只读服务。
- 监控主库 `Seconds_Behind_Master`、`Innodb_log_waits`、磁盘 IO。
- 故障切换流程要求 30 分钟内完成（人工或半自动）。

不建议在没有 DBA 的情况下使用 MHA / Orchestrator；托管 RDS / Aurora 是更优选择。

### 9.4 对象存储（node1 单实例）

详见 §5.1 方案 A/B 选择。建议使用 MinIO 走 S3 协议，便于未来无缝迁移到云 OSS。

## 10. 安全和隔离

- API、数据库、Redis 只开放内网端口（数据库 3306/27017/6379 不对外）。
- 三台机器之间使用 VPC 私有 IP 互通，公网入口只开 Nginx 的 443。
- Redis 必须设置密码或 ACL，禁止公网访问。
- 对象存储使用最小权限 IAM 或 access key。
- WebSocket origin 白名单不能使用 `*`。
- 节点之间的内部事件不携带明文密码、短信验证码或完整 token。
- 日志中只记录 `event_id`、用户 ID 摘要和节点 ID。
- 所有节点使用统一时钟同步（chrony / ntpd）。
- 发布包、配置、密钥和数据库备份分离管理。

## 11. 单点与故障应对

| 单点 | 影响范围 | 缓解措施 |
| --- | --- | --- |
| MySQL（node1） | 全部 API 写请求失败 | 每日全量 + binlog 备份；可选 node2/node3 加只读从库；监控主从延迟 |
| 对象存储（node1） | 文件上传/下载失败 | MinIO/EC 自动修复；或上 S3 / OSS；媒体文件每日异地备份 |
| Nginx（node1） | 整个入口 502/504 | 云 LB 替代；或 node1+node2 keepalived 漂移 |
| MongoDB primary | 写入短暂阻塞（自动选主 ~5s） | 副本集容忍 1 节点故障；驱动自动重试 |
| Redis master（M1/M2/M3 任一） | 该分片短暂写入阻塞（Cluster 选举 ~5s） | 业务侧容忍；任务锁靠 hash tag + 幂等兜底 |

**MongoDB / Redis 故障时的预期行为**：

- MongoDB 1 个 secondary 宕：业务无感知。
- MongoDB primary 宕：自动选主，~5s 短暂写入阻塞，业务可恢复。
- Redis 1 个 replica 宕：Cluster 把对应 replica 标记为下线，对应 master 仍可写；replica 由 cluster 触发替换（需新空实例加入，或通过 `cluster replicate` 将其他 replica 重定向）。业务可恢复。
- Redis 任一 master 宕：Cluster 自动从对应 replica 晋升新 master，~5s 该分片写入阻塞，业务可恢复。
- Redis 1 台整机宕（含 1 主 1 从）：剩余 2 主机 4 节点仍能对外服务，丢失的 master 分片由另一 replica 晋升，业务可恢复；Streams 消费者组会触发重连。
- Redis 2 台整机宕（极端）：Cluster `cluster-require-full-coverage yes` 下客户端收到 `CLUSTERDOWN`，业务不可用；建议临时改为 `no` 配合人工介入，或从备份恢复。

## 12. 分阶段开发计划

### P0：集群基础

- 增加 `node_id` 和集群配置。
- 增加 `/health`、`/ready` 和优雅停机。
- 增加跨节点日志字段。
- 增加 API 节点扩缩容脚本。

验收：三个 API 节点同时启动，REST 登录、聊天列表、联系人和管理端请求均正常。

### P1：WebSocket 跨节点

- 新增 Redis Streams 事件总线。
- 将消息、撤回、编辑、成员变化和系统通知接入事件总线。
- 增加每节点独立 consumer group。
- 增加事件幂等和 pending reclaim。
- typing 等瞬时事件接入 Pub/Sub。
- 增加全局在线状态 TTL。

验收：客户端 A 连接 API-node1，客户端 B 连接 API-node3，双方聊天、撤回、群事件和在线状态均正常。

### P2：共享媒体和后台任务

- 默认生产 storage provider 切换为 S3/MinIO。
- 媒体处理改为对象存储输入输出。
- 为所有 cron 增加 Redis 锁。
- 增加任务幂等和失败重试。

验收：文件上传到 API-node1 后从 API-node3 下载成功；三个节点同时执行任务时业务只生效一次。

### P3：Mongo 副本集 + Redis Cluster 切换

- MongoDB 切换为 3 节点副本集。
- Redis 切换为 3 主 3 从 Cluster（每机 2 实例）。
- 应用从 `redis.NewClient` 改造为 `redis.NewClusterClient`，业务 key 加 hash tag。
- 修改应用连接配置。
- 验证分片主从切换和故障恢复。

验收：MongoDB primary 宕机后业务在 30s 内恢复；Redis 任意 master 节点宕机后该分片业务在 10s 内恢复；单机宕机（含 1 主 1 从）后整体业务仍可用。

### P4：数据层高可用（可选，下一阶段）

- MySQL 增加只读从库。
- 对象存储迁移到云 OSS / S3。
- Nginx 替换为云 LB 或 keepalived。
- 跨机房容灾设计。

## 14. 发布、灰度和回滚

发布顺序：

1. 先部署兼容旧版本的 API（node_id、cluster.enabled 等新增配置默认关闭）。
2. 在 node1 部署新版本，灰度开启 cluster.enabled = true。
3. 验证 node1 节点的 WebSocket、任务锁和日志正常。
4. 滚动部署 node2、node3，每部署完一台观察 5 分钟。
5. 开启三节点之间的流量（调整 Nginx upstream 权重）。
6. 观察消息延迟、重复率、Redis pending 和 WebSocket 重连率。

回滚要求：

- 新旧 API 都能读取同一数据库数据。
- 事件格式向后兼容，新增字段不能改变旧节点解析。
- 可通过 `cluster.enabled: false` 配置回退到单节点模式（仅 node1 提供流量）。
- 回滚不能删除 Redis Stream、数据库业务记录或对象存储文件。
- Mongo 副本集和 Redis Cluster 不需要回滚（它们对单节点 API 也是兼容的：Mongo 单节点可作为 1 节点副本集，Redis Cluster 可降级为单 master + 多 slave 模式继续对外服务，但**应用必须使用 Cluster 客户端**）。

## 15. 从 3 机扩展到更多节点

如果未来需要扩展到 5/7 节点或更多，按以下步骤：

1. **MongoDB**：增加新节点到副本集，调整 `priority` 和 `votes`。
2. **Redis Cluster**：将新机器作为新 master 加入集群，重新分配 slot（`redis-cli --cluster reshard`），让数据分布更均匀；客户端无需改配置，Cluster 内部会自动通过 `-MOVED` 重定向。

   > Cluster 与 Sentinel 是两套互斥的高可用方案，本方案已采用 Cluster，无需保留 Sentinel 进程。Cluster 本身没有外部"监控进程"概念，所有节点都是对等的 gossip + 选举成员。
3. **API**：新机器直接 `docker compose up -d`，注册到 Nginx upstream。
4. **MySQL / 对象存储**：单点问题不会因 API 扩展而消除；如果仍未解决，建议直接迁移到托管 RDS / 云 OSS。
5. **Nginx**：如果使用云 LB，只需在 LB 后端添加新实例；如果是自建 Nginx，需要 reload 配置。

扩展时**不需要拆分 worker 服务**，因为锁粒度足够细；只有在任务量（QPS / 任务时长）真正超过单 API 节点承载时再考虑拆分。

## 16. 与原方案的关系

本方案是《IM 完整集群部署与改造方案》第一阶段的**成本优化版**，差异如下：

| 维度 | 完整集群方案 | 本三机方案 |
| --- | --- | --- |
| API 节点 | 多个，不绑定机器 | **3 个，每机一份** |
| MySQL | 第一阶段单实例 | **只在 node1，保留单点** |
| MongoDB | 第二阶段副本集 | **第一阶段就上副本集** |
| Redis | 第二阶段 Sentinel/Cluster | **第一阶段就上 Redis Cluster（3 主 3 从）** |
| 对象存储 | 第二阶段切 S3/OSS | **第一阶段保留在 node1**，推荐 MinIO |
| Nginx | 多 LB | **推荐云 LB**，否则单点 |
| 适用阶段 | 长期演进 | **当前上线版本** |

后续如果 MySQL 成为瓶颈、对象存储需要消除单点，再参考原方案的 P3/P4 阶段做数据层升级即可。

## 17. 最终建议

按以下顺序落地：

```text
node1: MySQL + MongoDB(primary) + Redis M1+S1(7000/7001) + MinIO + API + Nginx
node2: MongoDB(secondary) + Redis M2+S2(7002/7003) + API
node3: MongoDB(secondary) + Redis M3+S3(7004/7005) + API

P0: cluster 开关、node_id、健康检查、优雅停机
P1: WebSocket Redis Streams 事件总线（hash tag 同 slot）
P2: MinIO + Redis 任务锁（hash tag 保证 SET NX EX 原子）
P3: MongoDB 副本集 + Redis Cluster 上线（应用改 ClusterClient）
```

完成后系统即可对外宣称"支持 3 机集群部署"。MySQL 和对象存储的单点问题通过备份、监控和云服务替换解决，不应阻塞 API 横向扩展的进度。Redis Cluster 的引入不改变单节点 API 模式（应用始终连 `redis.NewClusterClient`，集群规模只是 `Addrs` 列表里的地址数）。
