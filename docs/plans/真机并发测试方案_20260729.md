# 通用 IM Android 真机群聊 100/500 人并发测试方案

日期：2026-07-29  
适用客户端：Flutter Android，包名 `com.genericim.app`  
适用环境：本地 Docker 或独立测试环境，禁止直接对生产环境执行并发压测

## 1. 测试目标

本方案不是单纯在手机上快速点击，而是重点回答两个容量问题：群聊能否准确容纳 `100` 人和 `500` 人，以及这些成员同时发消息时服务端 ACK、消息投递和真机页面是否卡顿。同时保留私聊、回执、推送、断网和通话等回归场景。

1. 两台或多台真机同时操作时，客户端不崩溃、不白屏、不出现错误状态。
2. 多个账号、多个设备和多个请求同时进入系统时，消息、未读、已读、推送、通话和上传结果保持一致。
3. 在并发叠加断网、后台、锁屏、杀进程等干扰后，客户端能恢复到服务端最终状态。

核心发布标准：群成员数准确；消息不丢、不重、不乱序；发送 ACK 不被同步放大阻塞；未读和已读最终一致；前台同群不产生系统推送；真机无持续高 CPU、崩溃和 ANR。

## 2. 测试边界

### 2.1 本轮覆盖

- 私聊双向同时发消息。
- 群聊多账号同时发消息。
- 同一账号多设备在线、已读同步和推送去重。
- 文本、图片、视频、文件并发发送。
- 语音/视频呼叫碰撞、快速挂断和立即重拨。
- 前台、后台、锁屏、普通进程被杀后的消息与推送。
- 并发期间断网、切换 Wi-Fi/移动网络和恢复。
- 登录、Token 刷新、WebSocket 重连与消息补拉。
- 服务端接口延迟、错误率、限流、数据库连接和容器资源。
- 100 人群、500 人群的创建、成员完整性、同秒发送和三轮突发。
- Redis `SCAN`、群成员投影更新、回执广播和推送的放大倍数。

### 2.2 不混为同一个结论的两类并发

| 类型 | 作用 | 能证明什么 | 不能证明什么 |
| --- | --- | --- | --- |
| 真机操作并发 | 多台手机在同一时间执行 UI 操作 | 客户端状态、系统权限、推送、前后台、真实网络和交互稳定性 | 大规模服务端容量 |
| API 虚拟用户并发 | 电脑侧并行调用登录、消息、通话信令和上传接口 | 服务端吞吐、限流、数据一致性和资源瓶颈 | 真机渲染、系统推送和真实 RTC 音视频质量 |

两台真机只能验证一组真实 RTC 通话以及双方同时发起呼叫的冲突处理。若要证明“多路真实音视频同时通话”，至少准备 4 台真机形成 2 路通话；建议 6 台形成 3 路通话。API 调用只能压测通话信令，不能替代真实摄像头、麦克风、编码、弱网和发热测试。

### 2.3 禁止事项

- 禁止使用生产账号、真实钱包余额或真实支付通道。
- 禁止在生产环境绕过限流或执行批量注册、批量发消息。
- 默认不执行 `pm clear`、卸载或覆盖安装，除非用例明确要求且已人工确认。
- 不把系统 `force-stop` 后收不到推送判为客户端缺陷；Android 强行停止后系统会阻止应用接收广播，必须与普通划掉后台、`am kill` 分开记录。
- 不把 API 压测通过直接写成“真机并发通过”，也不把两台真机通过写成“服务端高并发通过”。

### 2.4 已完成的 99 账号真机基线

2026-07-29 已在本地 Docker 和华为 ELS-AN00 真机完成一次 100 人群基线：群内保留 1 台真机，另外 99 个账号并发发送 3 轮，共 297 条消息。

| 指标 | 已测结果 | 判断 |
| --- | ---: | --- |
| 总耗时 | 24.48 秒 | 不通过 |
| ACK 平均值 | 4.40 秒 | 不通过 |
| ACK P50 / P95 / Max | 4.45 秒 / 7.58 秒 / 8.05 秒 | 严重阻塞 |
| Redis `SCAN` 增量 | 438,567 次 | 严重放大 |
| 平均每条消息 `SCAN` | 约 1,477 次 | P0 |
| 真机送达/已读请求 | 297 / 297 次 | 逐消息回执放大 |
| 已读 WebSocket 投递上限 | 29,403 次，即 297 x 99 | O(N²) 放大 |
| `user_chats` 更新 | 297 次群更新，约 29,700 行 | 同步写放大 |
| 前台同群 HMS 推送 | 297 次 | 推送策略错误 |
| 真机 CPU | 群详情空闲 126%-133%，设置页 0%-1% | 页面持续重绘 |
| 稳定性 | 无 Crash、ANR、OOM；PSS 约 350 MB 降至 333 MB | 内存不是主因 |

本次基线已经确认，主要问题不是网络或内存，而是服务端同步放大导致 ACK 堵塞，客户端逐消息回执、推送和持续重绘进一步加重卡顿。

已确认的主要路径：

1. `backend/internal/handlers/message_handler.go:1304` 在每条消息 ACK 路径中清理所有群成员会话缓存。
2. `backend/internal/cache/cache.go:120` 的 `DeleteByPattern` 每次从 cursor 0 扫描 Redis。
3. 真机为每条消息分别提交 delivered/read，服务端再向其余群成员广播回执。
4. `android/app/src/main/kotlin/com/genericim/app/GenericHmsMessageService.kt:29` 收到 HMS 消息后直接展示通知，没有前台同群抑制。
5. 客户端存在重复实时消息入口、状态复制/扫描和不可见动画持续运行的问题。

基线证据：

- [完整真机报告](../../artifacts/real-device-qa/group-burst-20260729-125626/summary.md)
- [原始压测数据](../../artifacts/real-device-qa/group-burst-20260729-125626/burst-report.json)
- 同目录包含 API 日志、logcat、截图、UI 树、CPU、PSS、Redis 和 Docker 指标。

在 P0 优化完成前，当前系统的“已验证稳定容量”不能写成 100 并发；现有结论是“100 人群可以建立和收消息，但 99 个账号同发时 ACK 与真机 CPU 不达标”。

| 服务端 | 本地 Docker/独立测试环境 | 独立测试数据 | API、WebSocket、Redis、MySQL、MongoDB、推送 |

### 3.2 推荐发布前配置

| 设备 | 建议系统 | 角色 |
| --- | --- | --- |
| A | 华为/Honor Android | HMS、后台限制、主叫 |
| B | Google/GMS Android | FCM、锁屏、被叫 |
| C | 小米/OPPO/VIVO Android | 厂商后台策略、第二路通话 |
| D | iPhone | 跨平台消息、APNs、CallKit、第二路通话 |

Windows 侧只能直接用 ADB 编排 Android。iPhone 的安装、日志和自动化应由 macOS 执行机完成，但使用相同的 `run_id`、账号前缀和时间基准汇总证据。

### 3.3 账号与数据隔离

- 每轮生成唯一 `run_id`，格式为 `conc-YYYYMMDD-HHmmss`。
- 真机固定角色账号可复用，但测试消息必须带 `run_id + 场景号 + 序号`。
- API 虚拟用户使用 `qa_vu_<run_id>_001...N`，不得复用普通测试账号。
- 100 人群精确创建 100 个成员账号，500 人群精确创建 500 个成员账号；三台真机账号包含在总人数内，不能额外加成 103/503 人。
- 三台真机账号可同时持有独立 API 会话，由 API 会话参加统一起跑，真机负责观察真实接收和渲染。
- 私聊、群聊、上传对象和通话记录都记录服务端 ID，便于结束后核对。
- 清理测试数据必须按 `run_id` 精确执行，清理动作不属于自动测试默认步骤。

### 3.4 当前人数与限流边界

当前代码和本地配置必须在报告中冻结记录：

| 项目 | 当前值 | 对测试的影响 |
| --- | ---: | --- |
| 全局群人数上限 `group_max_members` | 200,000 | 不是本轮 500 人瓶颈 |
| 普通账号群上限 | 100 | 可创建精确 100 人群 |
| VIP 群上限 | 500 | 500 人群主必须有有效 VIP 权益 |
| SVIP 群上限 | 1,000 | 可作为 500 人对照，但不能掩盖 VIP 规则 |
| 全局 IP 限流 | 100 请求/秒 | 单台压测机直发 500 请求会先测到 429，而不是后端容量 |

500 人测试账号的 VIP 只能通过测试环境夹具或后台正常授权，不允许修改生产会员数据。创建后必须查询群详情和成员分页，确认 `member_count=500` 且 500 个 UUID 集合完全一致；接口即使返回成功，只要被静默截断为 100 人也判失败。

## 4. 并发模型与负载阶梯

并发数和每秒请求数必须分别记录。所有账号先完成注册、登录、入群、Token 获取和 WebSocket 预热，这些准备动作不计入消息 ACK 耗时。每个发送者在同一个 UTC 起点释放请求，时间偏差目标不超过 20ms。

| 阶段 | 群总人数 | 同时发送者 | 消息数 | 模式 | 升档条件 |
| --- | ---: | ---: | ---: | --- | --- |
| B0 已有基线 | 100 | 99 | 297 | 3 轮 x 每人 1 条 | 已完成，当前不通过 |
| G100-1 | 100 | 100 | 100 | 同秒单轮 | P0 修复后首先复测 |
| G100-3 | 100 | 100 | 300 | 3 轮，轮间静置 30 秒 | G100-1 无丢重乱序且 ACK 达标 |
| G100-S | 100 | 100 | 10 分钟稳态 | 每账号 5-10 秒 1 条并加随机抖动 | G100-3 通过 |
| G200-1 | 200 | 200 | 200 | 同秒单轮 | G100 全部通过 |
| G300-1 | 300 | 300 | 300 | 同秒单轮 | G200-1 通过 |
| G500-1 | 500 | 500 | 500 | 同秒单轮 | G300-1 通过且资源有余量 |
| G500-3 | 500 | 500 | 1,500 | 3 轮，轮间静置 60 秒 | G500-1 通过 |
| G500-S | 500 | 500 | 10 分钟稳态 | 每账号 10-20 秒 1 条并加随机抖动 | G500-3 通过 |

每个档位拆成三种观测层，不能混报：

1. ACK 隔离层：100/500 个已入群账号只调用发送接口，测落库、seq 和 ACK，不建立全量 WebSocket。
2. 在线放大层：建立 100/500 条 WebSocket 连接，测消息广播和聚合回执；不允许 500 个连接逐消息形成 500 x 499 的已读风暴。
3. 真机体验层：三台真机停留在群详情、聊天列表和后台三种状态，测消息收敛、CPU、帧耗时、推送和交互响应。

当前全局限流为单 IP 每秒 100 请求，必须分别执行：

- 策略模式：保留 100 req/s 限流，验证 100/500 请求的 `429` 数量、提示和恢复。此模式不能用于声明后端最大吞吐。
- 容量模式：仅在独立测试环境临时把限流提高到大于 600 req/s，或使用多个独立源 IP；配置值写入 `manifest.json`，测试完成后恢复。此模式用于测真实消息链路容量。

执行规则：

1. 每档开始前静置 2 分钟并采集基线。
2. 必须按 100、200、300、500 逐档增加，不允许从当前失败的 100 档直接跳到 500。
3. 当前档出现消息丢失、数据错乱、崩溃或 ANR 时立即停止升压并保留现场。
4. `429` 必须单独统计。功能回归可按脚本退避重试；容量测试不得用无限重试掩盖限流。
5. 达到峰值后回落到 G100-1，再跑 5 分钟，验证系统不是“压完即坏”。
6. G100 任一轮再次出现 ACK P95 超过 500ms、Redis `SCAN` 非零或真机空闲 CPU 超过 5%，停止升档并回到 P0 优化。

## 6. 核心并发场景

### C01 双向同时发送文本

前置条件：A 与 B 打开同一私聊，聊天历史已同步。

步骤：

1. 倒计时后 A、B 同时各发送 20 条消息。
2. 消息格式为 `<run_id>-C01-A/B-001...020`，每条必须唯一。
3. 发送间隔依次跑 `1000ms`、`300ms`、`100ms` 三档。
4. 双方返回列表再进入会话，随后强杀并冷启动一次。
5. 从服务端按会话 `seq` 拉取消息，与两台手机最终 UI 对账。

断言：服务端和两端都恰好存在 40 条测试消息；`msg_id` 唯一；无永久“发送中”；同一会话按服务端 `seq` 展示；最后消息一致；重启后不丢失。

### C02 100/500 人群同秒发送

这是本轮主场景，必须分别执行 G100 和 G500，不能用 99 人结果代替 100 人结果，也不能把建群失败当作性能结果。

前置条件：

- 群成员数已通过详情和成员分页核对为精确 100 或 500。
- 所有账号已完成登录、入群、Token 和 WebSocket 预热；预热阶段不计入发送延迟。
- 500 人群主具备有效 VIP/SVIP 权益，且没有静默截断成员。
- 三台真机分别停留在群详情、消息列表、后台/锁屏状态，并开始录屏、logcat、`dumpsys gfxinfo`、`top` 和内存采样。

步骤：

1. 生成唯一 `run_id`，每条消息同时包含 `run_id`、发送者编号、轮次、序号和唯一 `msg_id`。
2. 服务端和压测机记录同一 `start_at`；所有发送 worker 等待到该时间后释放请求。
3. G100-1：100 个成员各发 1 条；G100-3：连续 3 轮；确认通过后执行 G200/G300/G500。
4. G500-1：500 个成员各发 1 条；G500-3：连续 3 轮，共 1,500 条；轮间只允许按方案静置，不重新登录或清缓存。
5. 一台真机保持群详情前台，第二台保持聊天列表，第三台先后台/锁屏再回前台；每台只发送一条带设备标记的观察消息，观察消息不计入容量统计。
6. 发送结束后等待 ACK、WebSocket、回执、缓存和群预览收敛，最长观察 60 秒；随后分页拉取消息并核对全部集合。

必须记录：

- 尝试数、HTTP 状态、业务码、`429`、超时、连接错误和成功数。
- ACK P50/P95/P99/Max、每轮墙钟耗时、实际吞吐（成功消息/秒）。
- 服务端落库数量、`msg_id` 重复、`seq` 缺口/重复、首条/末条收敛时间。
- Redis `SCAN/DEL/UNLINK/GET/SET` 增量、Mongo 写入、MySQL `user_chats` 更新行数。
- WebSocket 连接峰值、广播数、 delivered/read 请求数和回执扇出数。
- 三台真机的前台通知数量、群详情 CPU/内存/帧耗时、消息最终可见时间和 ANR/Crash。

通过条件：服务端成功响应对应的消息 100% 可查；`msg_id` 唯一；`seq` 无缺口且最终顺序一致；三台真机最终能看到群尾消息；前台同群系统推送为 0；没有持续增长的队列、连接、内存或 CPU。

### C02-P0 修复前后对照

同一批账号、同一群规模和同一消息脚本必须至少各跑一次：

| 对照项 | 修复前记录 | P0 修复后门槛 |
| --- | --- | --- |
| G100 ACK P95 | 已有基线 7.58 秒 | `< 500ms` |
| G100 ACK Max | 已有基线 8.05 秒 | `< 1s` |
| Redis `SCAN` | 已有基线 438,567 | `0` |
| delivered/read | 已有逐消息 297/297 | 每群每 300-500ms 合并到最高 seq |
| 已读 WebSocket 扇出 | 已有最高 29,403 | 不得按成员平方级增长 |
| 前台同群 HMS | 已有 297 | `0` |
| 真机群详情空闲 CPU | 已有 126%-133% | 稳定后 `< 5%`，峰值另行记录 |
| Crash/ANR/OOM | `0` | `0` |

如果 P0 修复后 G100 仍不达标，不执行 G500；报告结论写“100 人群容量功能可用，但并发性能未达标”。

### C03 同账号多设备与已读竞争

前置条件：B 账号同时登录设备 B 和一个独立 API 会话；如果产品限制单设备登录，则改为验证旧会话被准确踢下线。

步骤：

1. A 连发 20 条，B 真机保持后台，API 会话保持在线。
2. B 真机与 API 会话同时提交不同 `msg_seq` 的已读位置。
3. B 真机回前台，再由 A 补发 5 条。
4. 检查会话列表、详情、角标、推送记录和两个设备的已读位置。

断言：已读位置只能单调前进，不能回退；最终未读数正确；多设备不会重复插入同一消息；推送策略符合产品规则；单设备登录模式下只有一个明确有效会话。

### C04 文本与媒体并发

步骤：

1. A 同时选择 3 张图片发送，B 连续发送文本。
2. 叠加 1 个视频和 1 个大文件上传；记录文件大小、网络和对象存储 key。
3. 上传过程中切后台 10 秒再返回；另跑一次切网恢复。
4. 对成功消息下载并校验文件大小或 SHA256；失败项点击重试一次。

断言：文本不能被上传阻塞；媒体进度互不串线；消息与上传对象一一对应；失败不会生成可见但永久打不开的消息；重试不重复扣业务次数、不重复消息。

### C05 呼叫碰撞、挂断和重拨

步骤：

1. A、B 在同一倒计时结束时互相发起语音呼叫。
2. 验证系统只能形成一个有效通话或按产品规则同时返回明确冲突状态。
3. 分别执行取消与接听、拒绝与取消、双方同时挂断。
4. 每次结束后 1 秒内反向重拨，共 20 轮；语音和视频各跑一组。
5. 通话中执行 HOME、锁屏、静音、扬声器、前后摄像头和 10 秒断网恢复。

断言：同一用户不存在两个进行中通话；终态只有一个且双方一致；挂断资源释放完成；立即重拨不被旧 `call_id` 阻塞；聊天中的通话记录与最终原因一致；无持续占麦、占摄像头或假来电。

### C06 后台、锁屏与推送风暴

步骤：

1. B 依次处于前台、HOME 后台、锁屏、普通划掉后台四种状态。
2. 每种状态由 A 和虚拟用户在 10 秒内发送 20 条消息。
3. 记录服务端推送请求、厂商/FCM/APNs 返回、系统通知数量和点击路由。
4. 点击其中一条通知进入对应会话，检查消息、未读和角标。
5. `am force-stop` 只作为系统行为对照组，单独标记，不纳入推送可达率。

断言：业务消息全部补齐；通知聚合符合产品规则；点击路由正确；角标最终与未读一致；不会因通知重复导致消息重复。

### C07 断网与 WebSocket 重连

步骤：

1. B 关闭 Wi-Fi 和移动数据，A 与虚拟用户继续发送。
2. B 离线期间累计 20 条后恢复网络。
3. 恢复瞬间 A、B 再次双向发送，各 10 条。
4. 重复执行 Wi-Fi 到移动网络切换、弱网、10 秒抖动和 App 冷启动。

断言：WebSocket 只形成预期连接数；离线消息补齐；实时消息与补拉消息去重；`seq` 无缺口；恢复时间满足门槛；无无限重连或请求风暴。

### C08 登录和 Token 刷新竞争

步骤：

1. 在专用测试环境缩短 Token 有效期或使用可控的过期 Token。
2. Token 过期瞬间，让聊天列表、消息发送、资料读取和上传同时发请求。
3. 观察客户端是否只执行一次有效刷新，其余请求等待并复用结果。
4. 再跑刷新失败、账号在另一设备登录、服务端返回 401 三种分支。

断言：无刷新风暴；请求不会携带多个互相覆盖的 Token；成功刷新后业务请求只补发一次；失败时统一回登录页且不出现半登录状态；本地账号数据不串号。

### C09 混合稳态

持续 60 分钟循环以下业务比例：文本 60%、图片 15%、会话列表/历史 10%、已读 5%、登录/资料 5%、通话信令 5%。两台真机每 5 分钟执行一次前后台切换，每 15 分钟执行一次断网恢复。

断言：错误率和延迟不持续恶化；内存、goroutine/线程、数据库连接、WebSocket 和队列无单调增长；停止流量后 5 分钟内积压清零并恢复基线。

### C10 P0 优化验收

在同一 G100-3 账号和群数据上按以下顺序对照，不允许只看 ACK：

1. 移除发送 ACK 路径中的 Redis glob `SCAN`，改为明确 key + Pipeline `UNLINK` 或用户/会话版本号。
2. 消息落库和 seq 分配完成后立即返回 ACK；缓存失效、会话预览、推送和状态广播进入有界异步队列，并按 `msg_id` 幂等。
3. 成员游标一次批量查询；客户端 delivered/read 在 300-500ms 内合并，只上报最高 seq；大群不逐人广播每一条已读。
4. 服务端只对离线设备调用厂商推送；HMS/FCM/APNs 和本地通知在前台且当前会话匹配时全部抑制。
5. 客户端合并重复 WebSocket 新消息入口，按 seq 增量插入并批量写 Isar，活动窗口限制约 200 条，暂停不可见动画/ticker。
6. 群锁只覆盖 seq 分配和消息落库，缓存、推送、WebSocket 和成员投影不能持有同群锁。

每一步都保留独立结果；任何一步导致消息丢失、重复、乱序、ACK 错误或状态不收敛，不能进入下一步。

## 8. 观测指标与初始门槛

下列是首次执行建议门槛。正式测试前应根据产品 SLA 和测试环境容量冻结，测试中途不得为了通过而调整。

| 维度 | 指标 | G100 修复后门槛 | G500 记录/门槛 |
| --- | --- | --- | --- |
| 消息 | 已确认成功的消息丢失率 | `0` | `0`，否则立即停止 |
| 消息 | 重复消息、`msg_id` 冲突、seq 缺口 | `0` | `0` |
| ACK | P50 / P95 / Max | `<200ms / <500ms / <1s` | G500 目标 `<500ms / <1s / <3s`，实际以容量曲线记录 |
| 吞吐 | 成功消息/秒 | 记录基线 | 记录接受吞吐、落库吞吐和末条收敛吞吐 |
| Redis | `SCAN` 增量 | `0` | `0` |
| 回执 | delivered/read 请求 | 每群每秒少量合并请求 | 禁止 1:1 随消息增长；记录扇出 |
| 推送 | 前台当前群系统推送 | `0` | `0`；后台/锁屏按通道单独记录 |
| 真机 | 群详情稳定后空闲 CPU | `<5%` | `<10%`，峰值另记录 |
| 真机 | 最后一条消息可见 | P95 `<3s` | P95 `<5s` |
| API | 非预期错误率 | `≤0.1%` | `≤0.5%`，429 单独列出 |
| 限流 | HTTP/业务 `429` | 容量模式 `0`；策略模式按配置 | 必须区分策略模式与容量模式 |
| 稳定性 | App Crash、ANR、FlutterError、OOM | `0` | `0` |
| 资源 | 停压 5 分钟回落 | 无持续增长 | CPU、内存、连接、队列、SCAN 曲线 |

`429`、超时、断网和用户取消要区分“预期失败”和“系统缺陷”。任何失败都必须关联 `run_id`、场景、worker、账号、设备、`msg_id/call_id/upload_id` 和时间戳。

## 9. 停止条件和问题分级

满足任一条件立即停止升压并保存现场：

- 出现 App 崩溃、ANR、服务端进程退出或数据库不可用。
- 已返回成功的消息丢失、重复、串会话或顺序无法收敛。
- 同一用户出现多个进行中通话，或通话结束后持续占用麦克风/摄像头。
- 未读数出现负数、回退或长时间无法收敛。
- 错误率连续 2 分钟超过门槛。
- 服务端 CPU 连续 5 分钟超过 90%，内存接近限制，数据库连接池耗尽或积压持续增长。
- Redis `SCAN`、数据库群成员逐行更新或已读广播出现按成员平方级增长。
- 真机温度、电量或网络状态已不适合继续，结果可能失真。

问题分级：

| 等级 | 定义 | 处理 |
| --- | --- | --- |
| P0 | 数据丢失/串号、崩溃、ANR、通话无法结束、服务不可用 | 停止全场，修复后从 L0 重跑 |
| P1 | 稳定复现的重复/乱序、未读错误、推送主路径失败、G100 ACK 超门槛 | 停止升压，保留当前档复现 |
| P2 | 峰值下限流提示不清、恢复慢、资源回落慢 | 完成当前档后分析 |
| P3 | UI 抖动、轻微发热、偶发非主路径体验问题 | 记录并安排常规修复 |

## 10. 对账方法

每个消息场景必须以集合和顺序两层对账，不能只看最后一条消息。

1. 从每个 worker 保存发送清单：`msg_id`、发送者、会话、客户端序号、请求时间、响应时间和结果。
2. 从服务端按 `run_id` 查询落库消息，核对成功集合、唯一性、群成员集合和 `seq`。
3. 从 A、B、C 最终 UI/本地数据允许的观测面核对群尾消息、排序、可见时间和页面状态。
4. 核对会话列表最后消息、未读数、详情消息、推送记录、回执请求和广播扇出。
5. 失败时保留同一时间窗前后至少 60 秒的客户端、API、WebSocket、数据库和推送日志。

推荐结果状态只使用：`PASS`、`FAIL`、`BLOCKED`、`SKIP`。`BLOCKED` 和 `SKIP` 必须写原因，不能计入通过率。

## 11. 执行顺序

1. 把现有 99 账号报告登记为 B0 修复前基线，不重复制造无意义的 Redis `SCAN` 风暴。
2. 完成 P0：移除 ACK 路径 `SCAN`、异步化放大工作、合并回执、修复前台推送；每项先跑单元/集成测试。
3. 冻结 App、后端、Docker 资源、群权益、限流策略、三台真机版本和通过门槛，创建 `run_id`。
4. 预创建 500 个专用账号和 Token；分别创建精确 100 人、500 人群并做成员集合对账。
5. 执行 G100-1 和 G100-3 的 ACK 隔离层；不达标则停止，不进入 500。
6. 执行 G100 在线放大层和三真机体验层，验证回执、推送和 CPU。
7. 按 G200-1、G300-1、G500-1 逐档升压，每档结束立即对账并等待资源回落。
8. G500-1 通过后执行 G500-3，再执行 G100-S/G500-S 稳态。
9. 在策略模式重新执行 G100/G500 单轮，单独验证 100 req/s 限流和 429 恢复，不能覆盖容量模式结果。
10. 再跑一次 G100-1、低负载私聊和通话立即重拨，证明停压后核心能力正常。
11. 汇总报告；消息丢重乱序、G100 不达标、Redis `SCAN` 非零、前台同群推送非零时结论只能为“不通过”。
