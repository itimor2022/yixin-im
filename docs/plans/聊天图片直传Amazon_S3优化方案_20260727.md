# 聊天图片直传 Amazon S3 P0/P1/P2 开发方案

> 项目：`genericim-tongba`  
> 日期：2026-07-27  
> 状态：P0 已于 2026-07-27 完成开发与本地验收；P1/P2 待实施  
> 目标：后端下发短期上传凭证，前端直接上传文件到 Amazon S3，后端负责鉴权、校验、绑定和生命周期管理

## 1. 方案结论

客户提出的“上传文件从后端获取配置，再由前端传送文件”，与本方案一致。

准确实现方式不是把 AWS Access Key、Secret 等真实配置下发到前端，而是：

```text
前端选择文件
  → 后端鉴权并生成短期预签名上传地址
  → 前端直接上传到 Amazon S3
  → 前端调用后端 complete
  → 后端校验 S3 对象
  → 后端返回 media_id
  → 前端发送消息并绑定 media_id
```

推荐采用：

> **P0 完成安全和生命周期闭环 → P1 上线移动端聊天图片直传 → P2 扩展全平台和其他图片入口。**

旧的 `/upload/image` 代理上传接口继续保留，服务旧版本和受控回退场景，不进行一次性全量切换。

## 2. 直传带来的收益

### 2.1 用户体验

- 图片不再经过业务服务器二次中转，减少服务器排队和中转耗时。
- 图片气泡可以显示真实上传进度、取消、失败和重试。
- 选择图片后立即显示本地缩略图，不必等待上传完成。
- 多图发送可以并发上传，建议最大并发 3 张，弱网下降为 1～2 张。
- 断网、切后台或 App 重启后，可以使用同一个 `client_request_id` 恢复任务。

### 2.2 服务端容量

- API 服务器不再接收和转发完整图片二进制。
- 降低业务服务器入口、出口带宽和流量成本。
- 降低 Nginx、Go 服务、容器的连接、内存和超时压力。
- 多用户并发发图时，主要数据流量由 Amazon S3 承担。
- 后续增加图片大小和并发量时，不需要持续提高业务服务器上传限制。

### 2.3 运维能力

- 可分别统计初始化、S3 PUT、完成校验、消息绑定四个阶段。
- 可记录 S3 Request ID、网络类型、失败原因和各阶段耗时。
- 可按客户端版本、平台、账号或比例灰度。
- 出现异常时可以关闭直传开关，新请求立即恢复代理模式。

### 2.4 收益边界

- 直传主要解决业务服务器中转和并发瓶颈。
- 不能保证所有小图片都明显更快。
- 中国大陆到新加坡 S3 仍可能存在跨区域网络波动。
- `init` 和 `complete` 会增加少量控制请求，因此必须通过真实数据对比 P50、P90、P95。

## 3. 总体架构

### 3.1 上传主流程

```text
1. 前端选择、拍摄或编辑图片
2. 前端压缩图片，确定最终 MIME、扩展名、宽高和文件大小
3. 前端计算 SHA256
4. 前端调用 POST /api/v1/media/uploads/init
5. 后端校验登录状态、会员额度、格式、大小和频率
6. 后端生成唯一 object key 和 5～10 分钟有效的预签名 PUT URL
7. 前端直接 PUT 到 S3，并显示真实上传进度
8. 前端调用 POST /api/v1/media/uploads/{media_id}/complete
9. 后端通过 HeadObject、Range GET、文件头和 SHA256 校验对象
10. 后端将对象状态更新为 uploaded
11. 前端发送消息并携带 media_id
12. 后端再次校验归属并将对象状态更新为 bound
```

### 3.2 媒体状态机

```text
uploading
  ├─ complete 成功 → uploaded
  ├─ 消息绑定成功 → bound
  ├─ 用户取消 → deleting → deleted
  ├─ 未绑定超时 → deleting → deleted
  └─ 校验失败 → failed/quarantined → deleting → deleted
```

### 3.3 前端气泡状态

```text
压缩中
  → 上传 0%～100%
  → 校验中
  → 发送中
  → 已发送
```

失败时保留本地消息和原 `client_request_id`，允许重试，但不能直接创建新的 S3 对象。

## 4. P0：安全、校验和生命周期闭环

### 4.1 目标

P0 不急于扩大前端直传范围，先保证直传后不会产生隐私、重复对象和数据完整性问题。P0 是 P1 灰度上线的前置门槛。

### 4.2 后端安全

- App、H5、安装包和接口响应中不得出现 AWS Access Key、Secret。
- 预签名地址必须由登录态后端生成。
- object key 只能由后端生成，前端不能传入任意 S3 路径。
- 图片预签名有效期收紧为 5～10 分钟。
- 签名限定 Bucket、object key、Content-Type、Cache-Control 和必要的 checksum 请求头。
- `client_request_id` 按用户唯一，初始化和完成接口必须幂等。
- 发送消息时再次校验 `media_id` 的归属、类型、状态、有效期和会话权限。
- Bucket 使用私有读取，不允许聊天图片长期公开访问。
- 图片查看和下载通过短期签名 URL 或受控 CDN 鉴权地址。

### 4.3 文件校验

前端在 `init` 时提交：

```json
{
  "client_request_id": "本地消息ID",
  "category": "image",
  "file_name": "image.png",
  "size": 16372,
  "mime_type": "image/png",
  "checksum_sha256": "64位十六进制SHA256"
}
```

后端 `complete` 必须校验：

- S3 对象是否真实存在；
- 实际大小是否与初始化一致；
- Content-Type 是否一致；
- JPG、PNG、GIF、WebP、AVIF、HEIC/HEIF 文件头是否合法；
- S3 checksum 或服务端校验和是否与客户端 SHA256 一致；
- 对象是否属于当前用户；
- 对象是否仍处于允许完成的状态。

补充防护：

- 图片像素总量上限；
- GIF 帧数和解码资源限制；
- 伪造后缀、MIME 和文件头拒绝；
- 解码失败或可疑图片进入 `quarantined`，不能绑定消息。

### 4.4 生命周期修复

本轮真机测试已经发现：消息撤回后，媒体对象没有自动释放引用。

P0 必须修复：

- 撤回消息时减少 `reference_count`；
- 删除消息时减少 `reference_count`；
- 删除会话或清理历史消息时复用同一套引用释放逻辑；
- 引用归零后进入删除队列；
- S3 删除成功后更新为 `deleted`；
- 删除失败进入重试队列；
- 重复撤回、重复删除保持幂等；
- 共享引用对象不能被提前删除；
- 未绑定的 `uploaded` 对象在 24 小时内自动清理。

### 4.5 已知兼容问题同步处理

- PNG 保存到相册时不能固定使用 `.jpg` 文件名。
- 保存文件的扩展名、MIME 和真实内容必须一致。
- 直传图片返回的 URL、media_id、宽高、大小和 MIME 必须与代理上传保持相同消息结构。

### 4.6 性能与日志

- 缓存并复用 S3 Client、HTTP Transport 和 Keep-Alive 连接。
- 存储配置变更时主动使 S3 Client 缓存失效。
- 分别记录 `init`、`presign`、S3 PUT、`HeadObject`、Range GET、数据库更新和消息绑定耗时。
- 记录直传成功率、校验失败率、孤儿对象数量和清理失败数量。

### 4.7 P0 验收标准

- AWS Secret 不出现在客户端、日志和接口响应中；
- 非本人不能使用他人的 `media_id`；
- 超额、伪造 MIME、伪造文件头和错误 SHA256 必须被拒绝；
- 预签名过期后不能继续创建新上传；
- `complete` 重试不会创建重复对象；
- 撤回和删除消息后引用正确释放；
- 未绑定对象自动清理；
- Bucket 私有读取生效；
- 旧版 App 的 `/upload/image` 不受影响。

### 4.8 P0 工作量

预计 1.5～2.5 个工作日。

交付物：

- 后端安全与校验补强；
- 媒体引用释放和删除重试修复；
- 私有访问策略；
- SHA256 闭环；
- 后端自动化测试；
- P0 验收报告。

## 5. P1：移动端聊天图片直传

### 5.1 目标

Android、iOS 聊天图片优先直传 S3，同时保证旧版本兼容、失败可恢复、异常可回滚。

### 5.2 首期功能范围

- 相册单图发送；
- 相册多图发送；
- 相机拍照发送；
- 图片编辑、裁剪后发送；
- JPG、PNG、WebP、GIF、HEIC/HEIF；
- 原图和压缩图逻辑；
- 上传进度；
- 主动取消；
- 上传失败重试；
- 弱网、断网恢复；
- App 切后台和重启恢复；
- 上传完成但消息发送失败后的继续发送。

首期不包含：

- 头像和群头像；
- 动态和发现页图片；
- 自定义表情；
- 会员徽章；
- 管理后台素材；
- H5。

### 5.3 客户端接入

现有视频和文件已经使用 `S3DirectUploadService`。P1 将聊天图片入口接入同一套服务：

1. 图片压缩完成后计算 SHA256；
2. 使用本地消息 ID 作为 `client_request_id`；
3. 调用 `S3DirectUploadService.tryUpload(category: image)`；
4. 将上传进度绑定到本地消息气泡；
5. PUT 完成后调用 `complete`；
6. 使用返回的 `media_id` 发送消息；
7. 消息发送失败时复用原 `media_id`；
8. 用户取消时调用 `abort`。

### 5.4 多图策略

- 默认最大并发 3；
- 4G/5G 弱网或高丢包下降为 1～2；
- 保持用户选择顺序；
- 单张失败不阻塞其他图片；
- 文字消息和 WebSocket 不应被多图上传阻塞；
- 每张图片拥有独立 `client_request_id` 和进度状态。

### 5.5 回退规则

保留 `/upload/image`，但不能遇到任何错误都自动回退。

允许回退：

- 后端明确返回未启用 S3 直传；
- 后端版本不支持直传接口；
- 灰度开关关闭；
- 当前平台未进入直传范围。

不能立即回退：

- S3 PUT 超时但结果未知；
- PUT 成功但 `complete` 超时；
- App 切后台；
- 网络瞬断。

以上场景应先按原 `client_request_id` 查询任务状态，重试 `complete` 或恢复上传，确认对象不存在后才能重新上传。

### 5.6 灰度开关

新增后台配置：

```text
chat_image_direct_upload_enabled
chat_image_direct_upload_platforms
chat_image_direct_upload_rollout_percent
chat_image_direct_upload_max_concurrency
chat_image_direct_upload_url_ttl_seconds
```

灰度顺序：

```text
内部测试账号
  → Android 10%
  → Android 50%
  → Android 100%
  → iOS 10%
  → iOS 50%
  → iOS 100%
```

异常时关闭开关，新请求立即回到代理上传；已开始的任务根据原状态完成、取消或清理。

### 5.7 P1 验收矩阵

图片档位：

- 100KB；
- 1MB；
- 5MB；
- 10MB；
- 高分辨率图片；
- 动图；
- HEIC/HEIF。

网络：

- Wi-Fi；
- 4G/5G；
- 高延迟；
- 丢包；
- 上传中断网；
- 上传中切后台；
- 上传中强制关闭 App。

业务：

- 单图；
- 20 张连续发送；
- 图片加文字；
- 图片编辑后发送；
- 上传完成但发送消息失败；
- 消息发送成功后撤回和删除；
- 另一台真机接收、显示、下载；
- App 重启后重新加载。

### 5.8 P1 指标

- 直传上传成功率不低于 99.5%；
- 受控回退率低于 1%；
- 同网络下 P50 相比代理方案降低至少 30%；
- 20 张连续发送不阻塞文字消息和 WebSocket；
- 选择图片后 100 毫秒级显示本地气泡；
- 不产生重复消息、重复对象和无法清理的孤儿对象；
- 原文件、S3 文件和接收端保存文件 SHA256 一致；
- Android/iOS 新旧版本可以同时使用。

不承诺“所有图片始终低于 1 秒完成”，以真实网络下的 P50、P90、P95 和成功率作为验收依据。

### 5.9 P1 工作量

预计 2.5～4 个工作日。

交付物：

- Android/iOS 聊天图片直传；
- 真实进度、取消、重试和恢复；
- 多图并发控制；
- 灰度开关；
- 双真机、弱网和旧版本兼容报告。

## 6. P2：全平台与图片业务扩展

### 6.1 桌面端

- Windows/macOS 文件选择；
- 拖拽图片；
- 剪贴板粘贴图片；
- 图片编辑后发送；

- EXE 登录、窗口关闭和上传任务生命周期兼容；

### 6.2 H5

- H5 图片直传；
- 正式域名和测试域名独立配置；
- S3 CORS 精确限制 AllowedOrigins；
- AllowedMethods 使用 PUT、GET、HEAD；
- AllowedHeaders 只开放必要的 Content-Type、Cache-Control 和 `x-amz-*`；
- ExposeHeaders 开放 ETag、checksum 和必要 Request ID；
- 生产环境不长期使用 `*` Origin；
- 浏览器刷新、切标签页和网络恢复测试。

### 6.3 其他图片入口

聊天图片稳定后，按独立开关逐项扩展：

1. 头像和群头像；
2. 个人资料背景；
3. 动态和发现页图片；
4. 自定义表情；
5. 视频缩略图；
6. 会员徽章；
7. 管理后台素材。

这些入口的权限、裁剪、缓存刷新、审核和删除规则不同，不能直接共用聊天图片开关一次性上线。

### 6.4 网络与分发优化

如果主要客户长期位于中国大陆，P2 根据实际监控数据评估：

- S3 Transfer Acceleration；

- CDN 分发；
- 国内对象存储双云策略；
- 图片缩略图和多尺寸派生；
- WebP/AVIF 自适应输出。

是否启用必须通过同一批设备、网络和图片集做 A/B 测试，并核算额外费用，不根据理论速度直接开启。

### 6.5 审核与安全扩展

- 图片解码检测；
- 恶意文件扫描；

- EXIF 隐私信息清理；

### 6.6 P2 验收标准

### 6.7 P2 工作量

交付物：

## 8. 上线和回滚

### 8.1 上线

- P0 完成后先部署后端，不立即开启图片直传；
- 内部账号开启 P1；
- 观察成功率、P95、回退率、孤儿对象和删除失败；
- 达标后按平台和比例逐步扩大；
- 每个阶段至少保留一个完整业务高峰观察周期。

### 8.2 自动止损条件

出现以下任一情况时关闭新请求直传：

- 连续 5 分钟直传成功率低于 98%；
- `complete` 失败率超过 1%；
- 孤儿对象或删除失败持续增长；
- S3 403、签名错误或跨域错误异常上升；
- 消息已发送但媒体不可访问；
- 同一消息出现重复对象或重复消息。

### 8.3 回滚原则

- 只关闭功能开关，不回滚已经成功绑定的对象；
- 旧版本继续走 `/upload/image`；
- 新版本在开关关闭后走代理接口；
- 已进入 `uploading` 的对象继续查询、完成、取消或清理；
- 不允许将未知状态任务直接重新上传。

## 9. 最终建议

建议确认以下实施顺序：

```text
P0
修复撤回/删除媒体生命周期
  + 私有读取
  + SHA256 强校验
  + 幂等和孤儿清理

P1
Android/iOS 聊天图片直传
  + 进度
  + 取消/重试
  + 弱网恢复
  + 灰度和代理回退

P2
Windows/macOS/H5
  + 其他图片入口
  + CORS/CDN/网络优化
  + 审核和成本优化
```

这是当前代码基础上收益最大、风险最可控的实施方式。先保证安全和数据生命周期，再扩大直传范围，可以避免为了提速引入隐私、重复对象和兼容性问题。
