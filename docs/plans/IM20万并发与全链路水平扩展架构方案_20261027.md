# IM 20 万并发与全链路水平扩展架构方案

日期：2026-10-27
适用项目：`genericim`（`backend` 目录，Go 1.24 + Gin + MySQL 8 + MongoDB 7 + Redis 7）
基线分支：`v5.2`
目标：在不改变客户端协议语义的前提下，把 IM 服务从"单进程 + 单实例中间件"改造为
**接入层、业务层、数据层、中间件全部可无限水平扩展**的架构，并证明该架构在
**20 万并发 WebSocket 连接**下仍满足既定的延迟、可靠性与资源水位门槛。

与既有方案的关系：

## 1. 结论

### 1.1 能不能做到 20 万并发

**能，但必须同时改造服务层和数据层，且不能只靠"加机器"。**

当前代码（`v5.2`）在架构上有 6 个硬约束，其中任意一个都会在 20 万连接量级下成为瓶颈：

| # | 约束 | 代码位置 | 20 万连接下的后果 |
| --- | --- | --- | --- |
| C1 | WebSocket 连接与订阅只存在于单进程 `Hub` | `internal/ws/hub.go:17-41` | 跨节点用户收不到消息；节点数无法超过 1 |
| C2 | 群消息广播需先把全部成员 UUID 读出到内存再逐个发送 | `internal/services/message_service.go:296-311`、`internal/ws/hub.go:389-401` | 万人群广播 = 1 万次 `send`，内存与 CPU 线性放大 |
| C3 | 在线状态广播对每个订阅者逐个查 MySQL | `internal/ws/hub.go:266-303` | 连接风暴时 = O(订阅数) 次 DB 查询，直接打满连接池 |
| C4 | 慢客户端缓冲满即丢弃事件，缓冲仅 512 条 | `internal/ws/client.go:21,193-220` | 大群突发时大量丢包，客户端靠 seq 补偿产生补偿风暴 |
| C5 | 消息队列是 Redis List + `BRPOP`，无消费组、无 ack | `internal/mq/queue.go:41-48,155` | 多节点会重复消费同一条消息；节点崩溃即丢消息 |
| C6 | Redis 用 `SCAN` 删除会话列表缓存 | `internal/cache/cache.go:161-187` | 缓存失效成为 Redis 阻塞源，且在 Cluster 模式下 `SCAN` 只扫单 slot |

### 1.2 目标架构一句话

> **连接状态外置（Redis）+ 事件总线驱动（Redis Cluster Streams）+ 业务节点无状态 + 数据层分片（MySQL 分库分表 / MongoDB 分片 / Redis Cluster）+ 消息链路全异步 + 群广播按分片路由扇出。**

### 1.3 容量目标与验收门槛

| 指标 | 目标值 | 门槛（不达标即视为未完成） |
| --- | --- | --- |
| 并发 WebSocket 连接 | 200,000 | 建立成功率 ≥ 99.5% |
| 峰值消息吞吐 | 20,000 msg/s | 丢失率 = 0，重复率 = 0，seq 缺口 = 0 |
| 端到端投递延迟 | P95 ≤ 800ms，P99 ≤ 2s | 超过门槛持续 5 分钟即中止 |
| 发送 ACK 延迟 | P95 ≤ 500ms | 与现有 Outbox 基线（488.81ms）对比不退化 > 20% |
| 单节点承载连接 | ≥ 20,000 | 节点内存 ≤ 70%、CPU ≤ 65% |
| 扩缩容节点数 | 2 → 100+ | 加节点不需停机、不需数据迁移 |
| 故障恢复 | 单节点摘除 ≤ 30s 收敛 | 消息零丢失（靠 seq 补偿） |

### 1.4 与"无限水平扩展"的关系

本方案所说的"可无限水平扩展"是**工程可达的**：在单机资源上限内，通过加节点、加分片、
加中间件实例线性提升容量，且**每一层扩容都不需要停机、不需要数据搬迁、不需要改客户端**。
它不承诺"任意规模无限"——单机物理上限客观存在（见 §3.3）。

## 2. 现状基线与瓶颈证据

本章只记录**经过代码核对的事实**，作为后续改造与验收的基线。

### 2.1 当前部署形态

```text
Flutter/H5 客户端
       |
   Nginx/SLB（单点）
       |
  genericim-api（单容器，compose.yaml 中 container_name 固定）
       |
   +---+---+---+
   |   |   |
 MySQL MongoDB Redis（均单实例）
```

`compose.yaml` 中 `api` 使用固定 `container_name: genericim-api` 和固定宿主机端口，
无法 `--scale api=N`；MySQL `--max-connections=600`，Redis `--maxmemory 512mb`。

### 2.2 WebSocket 层

**连接与订阅是进程内状态**（`internal/ws/hub.go:17-41`）：

```go
type Hub struct {
    clients         *shard.ShardedMap[*ClientSet] // userID -> []*Client
    chatSubscribers *shard.ShardedMap[*ClientSet] // chatID -> []*Client
    ...
}
```

分片 map（`internal/shard/shard_lock.go`，`shard.count: 64`）只解决**单进程内的锁竞争**，
不解决跨进程可见性。结论：**C1 成立**。

**广播是全量遍历**（`internal/ws/hub.go:389-401`）：

```go
func (h *Hub) sendToChat(chatID string, data []byte, excludeID string) {
    if subs, ok := h.chatSubscribers.Get(chatID); ok {
        subs.Range(func(c *Client) { if c.ID != excludeID { c.Send(data) } })
    }
}
```

**在线状态广播存在 DB 放大**（`internal/ws/hub.go:266-303`）：对每个 `chatSubscribers`
分组，先 `Range` 找目标用户，再对组内每个客户端调用
`privacy.CanViewerSeeOnlineStatusByUUID(h.db, ...)`——该函数每次执行
`SELECT id, uuid FROM users WHERE uuid IN (?, ?)`（`internal/privacy/online_visibility.go:44-71`）。
**每组 1 次 DB 查询 × 会话数**，连接风暴时是 `N` 次查询。结论：**C3 成立**。

**慢客户端直接丢包**（`internal/ws/client.go:193-220`）：`send` 通道容量 512，
满时 `RecordDroppedMessage()` 并丢弃。设计意图是"靠客户端 seq 同步补齐"，
但补齐会触发额外 HTTP 拉取，形成**补偿风暴**。结论：**C4 成立**。

**每连接建连即写库**（`internal/handlers/ws_handler.go:48-81`）：Upgrade 成功后立即
`SELECT/INSERT/UPDATE user_devices` + `UPDATE users SET last_seen`，即
**每条新连接至少 2 次 DB 写**。20 万连接建立瞬间 = 40 万次写操作。

### 2.3 消息写入链路

当前发送链路（`internal/handlers/message_handler.go:914` `SendMessage`）的同步步骤：

1. 限流检查（Redis）。
2. `SELECT * FROM users WHERE uuid = ?`（发送者）。
3. `SELECT * FROM chats WHERE uuid = ?`。
4. `SELECT * FROM chat_members WHERE chat_id = ? AND user_id = ?`（成员校验）。
5. 群聊走 `SELECT chat_members JOIN users` 拿全部成员 UUID（仅私聊在 ACK 前同步取成员）。
6. Redis `INCR` 分配 seq（`internal/cache/cache.go:291-293`）。
7. MongoDB 写消息文档。
8. 写 Outbox 事件（`internal/models/message_outbox.go`）。
9. HTTP ACK。

投影（`user_chats` 最后消息/未读数）在 ACK 之后由 worker 合批执行
（`internal/handlers/message_handler.go:244-313`），但**合批窗口内进程退出仍可能丢投影**——
这正是 Outbox 方案要补的洞（`docs/plans/群聊高并发P3持久Outbox开发方案_20260729.md`）。

### 2.4 群广播扇出（最大的写放大源）

`internal/services/message_service.go:296-311`：

```go
func (s *MessageService) getChatMemberUUIDs(chatUUID string) []string {
    // SELECT chat_members -> user_ids
    // SELECT uuid FROM users WHERE id IN (...)
    return uuids
}
```

该函数在编辑/撤回/成员变更等路径被调用，随后
`hub.Broadcast(&ws.BroadcastMessage{UserIDs: memberUUIDs})` 逐个 `sendToUser`。
万人群 = 1 万次 map 查找 + 1 万次 channel 投递 + 1 次数万 UUID 切片分配。
结论：**C2 成立**。

### 2.5 中间件层

**消息队列**（`internal/mq/queue.go`）：基于 Redis List + `BRPOP`，
队列名固定为 `mq:message:send` / `mq:message:sync` / `mq:push:notify`。
没有消费组、没有 ack、没有 pending reclaim——**`BRPOP` 取出即从队列消失**，
处理失败的节点崩溃即丢消息；多节点同时消费则**互相抢消息**，而很多 handler 是
"每个节点都该执行一次"（如推送合批、投影合批）语义。结论：**C5 成立**。

**Redis 用法**：`SCAN` 删除会话列表缓存（`internal/cache/cache.go:161-187`）在
`message_service.go:1406` 与 `chat_auto_message_service.go:311` 被调用。
在 Redis Cluster 模式下 `SCAN` 只作用于**单个 slot**，无法跨 slot 删除，
语义直接失效。结论：**C6 成立**。

**在线状态**：`cache.go:224-240` 用 `user:online:{userID}` Hash 存设备，
但 `hub.go` 的在线判定走的是**进程内** `h.clients`，两者不是同一真相源。

### 2.6 数据层写热点

| 表/集合 | 热点 | 20 万连接下的写放大 |
| --- | --- | --- |
| `users` | `last_seen` 每次建连/断开都更新 | 20 万连接 = 40 万次写 |
| `user_devices` | 每次建连 `SELECT` + `INSERT`/`UPDATE` | 20 万次 |
| `user_chats` | 群消息投影更新**全体成员**行 | 万人群每条消息 = 1 万行更新 |
| `chat_members` | 广播前全量读取 | 每条群消息 1 次万行查询 |
| `message_outbox_events` | 每条消息 1 行 | 20 万 msg/s = 20 万行/s |
| Mongo `messages_YYYYMM` | 消息正文 | 按月分集合，天然横向切分 |

### 2.7 已确认的编译阻塞（必须先修）

`v5.2` 分支的 `backend/cmd/server/main.go:17-18,71,79-93,100,105` 已引用：

- `genericim/internal/redisclient`（`redisclient.New` / `redisclient.IsCluster`）
- `genericim/internal/ws/crossnode`（`crossnode.Publisher` / `NewRedisPublisher` / `NewNoopPublisher`）
- `cfg.Cluster.*`（`Enabled` / `NodeID` / `Channel` / `ShardedQueue` / `QueueShards`）
- `cfg.Redis.Addrs`（多地址 → Redis Cluster）
- `ws.NewHub(mysqlDB, crossNodePub)` 与 `mq.NewMessageQueue(redisClient, workers, queueShards)` 的**新签名**

但工作区**缺失** `backend/internal/redisclient/` 与 `backend/internal/ws/crossnode/` 两个包，
`internal/config/config.go` 也**没有** `ClusterConfig` 与 `RedisConfig.Addrs`。
实测 `go build ./cmd/server` 输出：

```
cmd/server/main.go:15:2: package genericim/internal/redisclient is not in std
cmd/server/main.go:18:2: package genericim/internal/ws/crossnode is not in std
```

**结论：当前 `v5.2` 工作区不能编译。** 这些包在 `cluster` 分支中存在
（`git ls-tree cluster -- backend/internal/redisclient backend/internal/ws/crossnode` 可验证），
但用户已明确"不用管 cluster 分支"。因此本方案把**补齐这两个包 + 对应配置字段**列为
**P0 第一项**，并在 §9.1 给出它们必须满足的接口契约（按本方案目标重写，而非搬运旧实现）。

## 3. 容量模型

### 3.1 连接内存模型

单连接常驻内存（Go runtime + gorilla/websocket + 业务结构）：

| 项 | 估算 | 说明 |
| --- | --- | --- |
| `Client` 结构体 | ~200 B | 含 2 个 map（`authResultCache` / `authCheckedAt`） |
| 读缓冲 + 写缓冲 | 4 KB + 4 KB | `websocket.read_buffer_size` / `write_buffer_size` |
| `send` 通道 | 512 × 指针 + 槽位 ≈ 4 KB | `sendBufferSize = 512` |
| gorilla 连接对象 + 帧缓冲 | ~4 KB | |
| goroutine 栈 | 2 × 8 KB 起步 | `readPump` / `writePump` |
| **合计** | **≈ 25–30 KB/连接** | 不含 GC 头与临时分配 |

**20 万连接 ≈ 5–6 GB**。按 Go GC 目标 2 倍存活堆规划，
**单节点 32 GB 内存**可承载约 **10 万连接**（含 50% GC 余量）；
若把缓冲调小（读写缓冲 2 KB、`sendBufferSize` 128），可降至 ≈ 16 KB/连接，
单节点 32 GB 承载 **≈ 16–18 万连接**。

### 3.2 CPU 与网络模型

**心跳开销**：每个连接每 `ping_period`（54s）一次 ping + 一次 pong。
20 万连接 → 20 万 / 54 ≈ **3,700 次/秒** 双向小包，CPU 开销可忽略。

**广播开销**：这是真正的 CPU 大头。设峰值 20,000 msg/s，
平均每条消息扇出到 F 个客户端，则网络发送包速 = 20,000 × F。

| 场景 | 扇出 F | 出站包速 | 带宽（按 200 B/包） |
| --- | --- | --- | --- |
| 1v1 私聊 | 2 | 40,000/s | 8 MB/s ≈ 64 Mbps |
| 500 人群 | 500 | 10,000,000/s | 2 GB/s ≈ 16 Gbps |
| 万人群 | 10,000 | 200,000,000/s | 40 GB/s ≈ 320 Gbps |

**万人群 20,000 msg/s 的场景在物理上不可达**（单机万兆网卡都撑不住）。
这说明：**大群的写放大必须靠"分层广播 + 客户端聚合"解决，不能靠加机器解决**。见 §7。

### 3.3 单节点上限与扩缩容公式

| 资源 | 单节点上限（32 GB / 16 vCPU / 10 Gbps） | 20 万连接所需节点数 |
| --- | --- | --- |
| 内存 | ~100,000–180,000 连接 | 2–3 |
| CPU（仅连接维持） | ~50,000–80,000 连接 | 3–4 |
| 网络（1v1 为主） | ~300,000 连接 | 1 |
| **取最严** | **~80,000 连接** | **3** |

**扩缩容公式**（后续章节的设计都围绕它成立）：

```text
节点数 N = ceil(目标连接数 / 单节点安全连接数) × 故障冗余系数
单节点安全连接数 = min(内存上限, CPU 上限, 网络上限) × 0.7
```

20 万连接 → `ceil(200000 / 80000) = 3`，× 1.5 冗余 = **5 个节点**。
这就是目标拓扑的初始规模，也是压测的基线配置。

### 3.4 数据层容量模型

**MySQL**：

- `user_chats`：20 万用户 × 平均 20 个会话 = **400 万行**。单表可承载，但
  群消息投影是**行级写放大**，必须分库。
- 分库分表键：**`user_id`**（会话列表按 user 查）或 **`chat_id`**（群投影按 chat 查）。
  两者冲突 → 见 §5.4 的**双写路由**方案。
- 初始分片：8 库 × 32 表 = 256 分片，可支撑 ~1 亿用户。

**MongoDB**：

- 消息正文已按月分集合（`models.GetMessageCollection` → `messages_YYYYMM`），
  这是**天然的时间分片**，已经是水平扩展的雏形。
- 20 万 msg/s × 1 KB/文档 = **200 MB/s ≈ 1.7 TB/天**。
- 需转为 MongoDB **分片集群**，shard key = `chat_id`（保证同会话消息落同一 chunk，
  避免 scatter-gather）。

**Redis**：

- 连接状态（20 万 × ~200 B）、会话列表缓存、seq 计数器、限流、队列、Streams。
- 预估内存 **8–16 GB**，需 **Redis Cluster**（3 主 3 从起步）。
- 关键：**hash tag** 保证同会话的 seq 计数器与队列 key 落在同一 slot。

### 3.5 消息吞吐模型

峰值 20,000 msg/s 的链路预算：

| 环节 | 每条消息操作数 | 20,000 msg/s 总量 |
| --- | --- | --- |
| Redis seq INCR | 1 | 20,000 ops/s |
| Mongo 消息写 | 1 | 20,000 docs/s |
| MySQL Outbox 写 | 1（批量后 ~0.1） | 20,000 → 2,000 行/s |
| MySQL 投影（500 人群） | 500 行更新（批量后 ~50） | 10,000,000 → 1,000,000 行/s |
| 跨节点事件发布 | 1 | 20,000 events/s |
| **最重环节** | | **MySQL 投影行更新** |

**结论：MySQL 投影写放大是数据层的头号瓶颈**，必须靠三层手段共同解决：
① 按分片路由减少单库压力；② 投影从同步链路剥离为异步合批；
③ 大群降级为"最后消息 + 未读数"增量。

### 4.1 五层扩展契约

每一层都必须满足"**加实例 = 加容量，且不需要停机/不迁数据/不改客户端**"：

| 层 | 状态位置 | 扩容动作 | 是否需要停机 | 是否需要数据迁移 |
| --- | --- | --- | --- | --- |
| 负载均衡 | 无（L4/L7 转发） | 加 LB 实例 + 改 DNS/服务发现 | 否 | 否 |
| WS 接入网关 | 连接在网关内存中 | 加网关实例 | 否（客户端重连到新实例） | 否 |
| 业务/Worker 节点 | 无（连接池级） | 加节点 | 否（滚动） | 否 |
| Redis Cluster | 数据按 slot 分片 | 加主节点 + `reshard` | 否（有热迁移） | **是（在线迁移）** |
| MySQL 分片 | 按分片键 | 加库表 + 新路由表 | 否 | **是（双写 + 存量迁移）** |
| MongoDB 分片 | 按 chunk | 加 shard + `shardCollection` | 否 | **是（在线 balancer 迁移）** |

### 4.2 "无限扩展"的具体含义

用户要求的"服务节点和数据库、中间件都能水平扩展"，在本方案中拆成 4 个可独立验证的能力：

| 能力 | 验收方式 | 对应章节 |
| --- | --- | --- |
| **服务节点无界扩展** | 从 5 节点加到 100 节点，连接总数与消息吞吐线性增长，无热点 | §5.1 / §5.2 |
| **数据库无界扩展** | MySQL 加库、Mongo 加 shard 后，写入吞吐线性增长，路由自动更新 | §6.1–6.3 |
| **中间件无界扩展** | Redis 加主节点后 slot 自动 rebalance，Streams 不丢事件 | §6.4 |
| **扩容零停机** | 任意时刻加/减节点，客户端不需改配置、不需重连风暴 | §13.3 |

**关键前提**：所有节点必须**完全无状态**。任何"节点本地状态 = 权威数据"的设计
都会成为扩展天花板。这也是 C1 必须彻底解决的原因。

## 5. 关键机制设计

### 5.1 WebSocket 连接无状态化

**目标**：把"谁在线、谁订阅了什么"从进程内存搬到 Redis，使任意节点可路由到任意连接。

**数据结构**（Redis Cluster，hash tag 保证同 slot）：

```text
# 连接注册表：user -> 该用户在本节点的所有连接
S{ws:conn}:{userUUID}   -> Hash{ connID -> {node_id, device_id, ts} }
                            TTL = 2 × pong_wait

# 反向索引：connID -> 归属（用于精确摘除）
S{ws:conn}:c:{connID}   -> String{ node_id }
                            TTL = 2 × pong_wait

# 会话订阅表：chat -> 订阅该会话的连接
S{ws:sub}:{chatUUID}    -> Hash{ connID -> ts }
                            TTL = 2 × pong_wait

# 节点心跳（用于故障节点快速摘除）
S{ws:node}:{nodeID}     -> String{ started_at, conn_count }
                            TTL = 15s
```

**要点**：

1. **TTL 自愈**：连接表带 TTL，心跳续期。节点崩溃后无需人工清理，TTL 到期自动摘除。
2. **节点级批写**：不能每条消息同步写 Redis。用**每 1 秒 / 每 500 条**批量续期
   （`HSET` pipeline），把 20 万连接的续期写压到 **20 万 QPS → 400 QPS**。
3. **在线状态判定**统一走 Redis，替换掉 `hub.go` 的进程内 `h.clients` 判定，
   同时解决 §2.2 的 **C3（DB 放大）**：`privacy.CanViewerSeeOnlineStatusByUUID` 的结果
   **批量预计算并缓存 30 秒**，在线状态变化时主动失效。
4. **多设备**：一个 `userUUID` 可有多个 `connID`，符合现有 `clientSet` 语义。

**内存重分配的关键收益**：连接迁出 Redis 后，业务节点的内存占用从
**O(连接数 × 25KB)** 降到 **O(连接数 × 少量元数据)**，
这使"业务节点"可以真正做到无状态、可任意增删。

### 5.2 跨节点事件总线

用 **Redis Cluster Streams**（不是 Pub/Sub）承载持久业务事件，理由：
Pub/Sub 在订阅者断连期间**丢消息**，而 IM 消息不能丢。

```text
Stream:  S{im:evt}:{chatUUID}        # 按会话 hash tag 分 slot
Group:   im-node-{nodeID}            # 每个节点一个消费组（广播语义）
```

**事件信封**（沿用既有集群方案的格式）：

```json
{
  "event_id": "uuid",
  "event_type": "message.created",
  "chat_id": "uuid",
  "user_ids": ["uuid"],
  "seq": 12345,
  "origin_node": "api-a",
  "occurred_at": "2026-10-27T12:00:00Z",
  "payload": {}
}
```

**关键设计**：

1. **消费组 = 广播语义**。每个节点一个独立 group，Redis Streams 会把每条消息投给**每个 group 一次**，
   天然实现"每个节点都要收到"。
2. **幂等**：`event_id` 去重，消费端记录最近 N 个 event_id（本地 LRU 即可）。
3. **Pending reclaim**：节点重启后用 `XAUTOCLAIM` 认领超时 pending。
4. **背压**：`XREADGROUP` 阻塞读取，队列积压时通过 `XLEN` 监控告警。
5. **瞬时事件**（typing、在线状态）走 **Pub/Sub**，允许丢失。

**与既有集群方案的命名协调**：`docs/plans/IM完整集群部署与改造方案.md` §4.3 使用
单流 `genericim:ws:events`。本方案改为按会话 hash tag 分片
（`S{im:evt}:{chatUUID}`），原因是单流在 Redis Cluster 下只能落一个 slot，
会成为写入热点且无法与同会话的 seq 计数器、成员表共置。
**实施时以本方案为准**，既有方案的 `ws_stream_key` 配置项需相应改为
`genericim:im:evt:{chatUUID}` 形式；两者的"每节点一个消费组实现广播"语义保持一致。


### 5.3 群广播的分片路由（解决 C2）

核心思想：**不再"读出全部成员 → 逐个投递"，而是"按分片路由 → 各分片只发本分片的成员"**。

```text
                     业务节点（收到 message.created 事件）
                                |
                    +-----------+-----------+
                    |  按 hash(userID) 分片 |
                    +-----------+-----------+
              shard-0    shard-1   ...   shard-K
                 |          |            |
           查 Redis      查 Redis      查 Redis
           该 shard 的   该 shard 的   该 shard 的
           在线用户      在线用户      在线用户
                 |          |            |
                 +----------+------------+
                            |
                   发到对应 WS 网关节点
```

**实现要点**：

1. **成员分片表**：`S{im:mbr}:{chatUUID}:{shard}` -> 成员的 `userID` 列表（或 bitmap）。
   群成员变更时增量更新，不做全量重建。
2. **在线用户分片表**：`S{im:onl}:{shard}` -> 该分片内在线的 `userUUID` 集合。
3. **发送时只处理"当前在线且在本分片"的成员**，离线成员交给 Outbox 推送链路。
4. **每分片独立处理 + 独立失败**：某个分片 Redis 慢，不阻塞其他分片。
5. **万人群降级策略**（见 §7.3）：超过阈值时不再"逐成员投递"，改为
   **"群状态事件 + 客户端按 seq 拉取增量"**。

**收益量化**：

| 指标 | 改造前 | 改造后 |
| --- | --- | --- |
| 万人群广播内存分配 | 1 万 UUID 切片 (~400 KB) | 每分片 ~625 UUID (~25 KB) |
| 万人群广播 CPU | 1 万次 map 查找 | K 次批量查找（K=16） |
| 广播对单节点的延迟 | 与成员数线性相关 | 与分片数相关（常数） |

### 5.4 MySQL 分库分表与"双写路由"难题

`user_chats` 表同时被两种访问模式命中：

- **按 user 查**：`WHERE user_id = ?` —— 会话列表（`internal/handlers/chat_cache_helpers.go:18-35`）
- **按 chat 查**：`WHERE chat_id = ?` —— 群消息投影（`internal/handlers/message_handler.go:252-278`）

两者分片键不同，无法用单一分片键同时优化。**解决方案：**

**方案 A（推荐）：`user_chats` 按 `user_id` 分片，投影走"反向表 + 异步合并"**

```text
user_chats（按 user_id 分片）           <- 会话列表读取
    ^ 异步投影写入（最终一致）

chat_projection（按 chat_id 分片）        <- 群投影的"权威聚合态"
    chat_id, member_count, unread_total, last_seq, last_msg_*
    ^ 消息发送时 O(1) 更新（与成员数无关）

user_chats.unread_count / last_msg_*     <- 由 chat_projection + 增量事件异步合并
```

`chat_projection` 每群 1 行，投影更新变成 **O(1) 而非 O(成员数)**，
这是消除 §3.5 头号瓶颈的关键。`user_chats` 的 `unread_count` 通过
**消费增量事件**（`unread_delta`）异步合并，保证最终一致；
会话列表的未读数以 `user_chats` 为准，误差窗口控制在 1 秒内。

**方案 B（简单）**：双写两份表

```text
user_chats_by_user（按 user_id 分片）  <- 读路径
user_chats_by_chat（按 chat_id 分片）  <- 写路径 + 合并
```

写放大翻倍但实现简单，适合作为过渡期方案。

### 5.5 MongoDB 分片

1. **shard key = `chat_id`**：保证同会话消息落同一 chunk，避免 scatter-gather。
2. **保留按月分集合**：现有 `messages_YYYYMM` 已是时间分片，
   需改造 `models.GetMessageCollection` 支持"月 × chat 分片"的复合路由。
3. **Balancer**：开启自动 chunk 迁移，新分片加入后自动均衡。
4. **索引随分片下发**：`ensureMessageCollectionIndexes`
   （`internal/services/message_service.go:178-243`）在分片集群下会为**每个分片**建索引，
   需改为由迁移工具统一管理，避免 6 个索引 × N 分片的重复开销。

### 5.6 Redis Cluster

1. **hash tag 强制**：`KeyMsgSeq`（`msg:seq:{chatID}`）必须改为
   `msg:seq:{chatID}` 形式（Redis Cluster 的 hash tag 用 `{}`），使同会话的
   seq 计数器、成员表、事件流落在**同一 slot**。
2. **替换 `SCAN` 删除**（解决 C6）：`cache.DeleteByPattern` 在 Cluster 下不可用。
   改为**版本号失效**（项目已有此模式，见 `chat_cache_helpers.go:43-63` 的
   `bumpUserChatListHotCacheVersions`），全量替换 `message_service.go:1406` 与
   `chat_auto_message_service.go:311` 的 `DeleteByPattern` 调用。
3. **在线状态与限流**：`user:online:` 改为 hash-tag 分片键。
4. **禁 `allkeys-lru`**：现有 `compose.yaml` 用 `allkeys-lru`，在 Cluster 下
   会把 Streams 事件和 seq 计数器一起淘汰，**必须改为 `volatile-lru` + 显式 TTL**。

### 5.7 消息链路异步化

**目标：把 ACK 路径上的所有"非必要同步写"移出。**

```text
【改造前】客户端 -> [DB查 x4] -> [Redis INCR] -> [Mongo 写] -> [Outbox 写] -> ACK
                                          ^ 同步        ^ 同步

【改造后】客户端 -> [Redis INCR] -> [Mongo 写] -> [Outbox 写] -> ACK
                                          ^ 同步        ^ 同步
              +-- 发送者/会话/成员校验改为 Redis 缓存 + 异步校验
              +-- 投影、推送、广播、缓存失效全部走 Outbox 异步
```

**具体改造点**：

| 现状（同步，在 ACK 路径） | 改造后 |
| --- | --- |
| `SELECT * FROM users WHERE uuid=?`（发送者） | Redis `user:profile:{uuid}` 缓存，TTL 5 分钟 |
| `SELECT * FROM chats WHERE uuid=?` | Redis `chat:meta:{uuid}` 缓存，TTL 5 分钟 |
| `SELECT * FROM chat_members WHERE chat_id=? AND user_id=?` | Redis `S{im:mbr}:{chatUUID}:{shard}` 成员分片表（**同时服务于广播**） |
| 群聊 ACK 前取全部成员 UUID | **完全移除**（广播改走 §5.3 分片路由） |
| 投影 `user_chats` 更新 | 移入 Outbox 异步（已部分完成） |

**注意**：成员权限校验从"每次查库"改为"读缓存"会引入**权限变更延迟**。
必须保证：成员被移除时**立即**从 Redis 成员表删除（写路径同步删），
消息写入时若缓存缺失则**回源查库并回填**（缓存击穿保护）。

### 5.8 建连路径优化（连接风暴的关键）

当前每条新连接 = 2 次 DB 写（`ws_handler.go:48-81`）。20 万连接建立 = 40 万次写。

**改造**：

1. `user_devices` 的 `INSERT/UPDATE` 改为**异步合批**（走 Outbox 或独立批量通道），
   按 `device_id` 去重，批大小 200 / 100ms。
2. `users.last_seen` 改为**按分钟粒度**更新（或直接用 Redis 在线状态推导，
   由后台任务低频回写 DB）。
3. 鉴权中间件（`middleware.Auth` -> `authsession.ValidateUserTokenStateWithToken`）
   在 WS 建连时会做 **4-5 次 Redis `EXISTS`/`GET`**（`internal/authsession/*.go:144-178`），
   改为**一次性 pipeline** 或**会话快照缓存**（TTL 30s）。

**目标**：单条连接的建连 DB 写从 2 次降到 **0 次**（全部异步）。

### 5.9 背压与慢客户端治理（解决 C4）

当前：缓冲满 -> 丢包 -> 客户端 seq 补偿 -> 补偿风暴。

**分级背压**：

| 客户端状态 | 判定 | 策略 |
| --- | --- | --- |
| 正常 | `send` 队列 < 50% | 正常投递 |
| 慢 | `send` 队列 >= 50% | 合并**非关键**事件（typing、已读回执） |
| 很慢 | `send` 队列 >= 90% | 只保留**关键**事件（消息、撤回），其余丢弃 |
| 濒死 | 连续写超时 | 主动断开，客户端按 seq 补偿 |

**关键补充**：当前 `send` 缓冲固定 512 且**不可配**（`client.go:21` 是常量）。
需改为可配置，并引入**按消息类型的优先级队列**（两级：critical / normal）。

**补偿风暴防护**：客户端 seq 补偿请求需**合并**（同一会话多次补偿合并为一次
`since_seq` 拉取），服务端需对补偿接口**单独限流但保证不被业务限流误伤**。

## 7. 大群广播分层与背压治理

### 7.1 问题量化

§3.2 已量化：**万人群 x 20,000 msg/s 需要 320 Gbps**，物理不可达。
即使 1,000 人群 x 5,000 msg/s = 10 Gbps，单节点也已达网口上限。

### 7.2 分层广播

```text
第 1 层：群状态事件（所有成员必达）
    { type: "chat_state", chat_id, last_seq, last_msg_preview, unread_delta }
    扇出 = 成员数，但载荷小（~200 B）且可合并

第 2 层：消息正文（仅在线成员）
    载荷 = 消息内容（~500 B-2 KB）
    仅在"成员确实在线"时投递

第 3 层：增量拉取（兜底）
    客户端发现 seq 缺口 -> 调 GET /messages?since_seq=N
    合并补偿请求，避免风暴
```

**第 1 层的合并是关键的降级手段**：把 1 秒内同群的多条消息**合并成 1 条群状态事件**
（携带最高 seq + 预览），扇出量不变但**消息数**降一个数量级。

### 7.3 大群降级策略（按成员数自动切换）

| 成员数 | 策略 | 说明 |
| --- | --- | --- |
| <= 200 | 全量投递 | 现状行为 |
| 200-2,000 | 分片投递 + 事件合并 | §5.3 分片路由 |
| > 2,000 | 群状态事件 + 客户端增量拉取 | **不再逐成员投递消息正文** |

**降级的正确性保障**：客户端必须能通过 `last_seq` 发现缺口并补齐——
这依赖现有的 `seq` 机制（`cache.go:291-293` 的 `INCR`），**已经具备**。

### 7.4 服务端限流与准入

```text
1. 群消息发送速率：按 chat_id 限流（Redis 令牌桶）
   - 普通群：10 msg/s
   - 大群（>2000 人）：2 msg/s，超出返回 429 + 客户端退避
2. 单用户发送速率：现有 checkMessageRateLimit 保留
3. 建连速率：按 IP 限流（防连接风暴）
4. 补偿拉取：单独限流，但保证不被业务限流误伤
```

## 12. 故障域设计与降级

### 12.1 故障域划分

```text
可用区 A              可用区 B              可用区 C
|- WS 网关 x2         |- WS 网关 x2         |- WS 网关 x2
|- 业务节点 x2        |- 业务节点 x2        |- 业务节点 x2
`- Redis 主 x1  ------+- Redis 主 x1  ------+- Redis 主 x1
        `------------ Redis Cluster (3 主 3 从) ------------'

MySQL 分片：每分片 1 主 1 从，跨可用区
MongoDB：每 shard 1 主 1 从，config server 3 节点
```

### 12.2 降级矩阵

| 故障 | 表现 | 降级行为 | 恢复 |
| --- | --- | --- | --- |
| 单个 WS 网关 | 该网关连接全断 | 客户端重连到其他网关；消息靠 seq 补偿 | 自动，秒级 |
| 单个业务节点 | 该节点连接全断 + 事件消费停滞 | 客户端重连；pending 由 `XAUTOCLAIM` 接管 | 自动，<= 60s |
| Redis 主节点 | 该 slot 不可用 | Cluster 自动切换到从节点；连接表 TTL 过期导致该段连接重连 | 自动，<= 30s（需 `cluster-node-timeout` 调优） |
| MySQL 分片主节点 | 该分片写失败 | 切从；**Outbox 写入失败 -> 消息发送失败**（不降级，避免丢消息） | 自动，<= 60s |
| MongoDB 主节点 | 消息写入失败 | 同上，**返回错误让客户端重试**（幂等 `msg_id` 保证不重复） | 自动 |
| 对象存储 | 媒体上传失败 | 消息文本照常发送，仅媒体失败 | 恢复后重传 |

**重要原则**：**数据层故障时宁可发送失败，也不降级为"假装成功"**。
幂等 `msg_id` 机制（`message_service.go:757-824`）保证客户端重试安全。

### 12.3 客户端侧配套改造

服务端改造需要客户端配合，**必须同步排期**：

| 客户端改造 | 原因 | 优先级 |
| --- | --- | --- |
| 补偿请求合并 | 防止补偿风暴 | P0 |
| 大群增量拉取 | 配合 > 2000 人群降级 | P1 |
| 事件去重（`event_id`） | 消除重复投递观感 | P1 |
| 分级背压感知 | 慢网络时降低发送频率 | P2 |
| 节点地址动态获取 | 接入多网关（`client_bootstrap` 已存在该配置） | P0 |

`config.yaml` 的 `client_bootstrap.ws_endpoints` 与 `api_endpoints` 已经支持
多端点下发，**无需改协议**，只需在服务端配置中填入多个网关地址。

## 13. 风险与回滚

### 13.1 风险登记

| # | 风险 | 概率 | 影响 | 缓解 |
| --- | --- | --- | --- | --- |
| R1 | 分库分表后跨分片查询遗漏 | 中 | 高 | 路由表统一管理；新增查询走 `shard_router` 静态检查；SQL 优化方案索引同步 |
| R2 | 投影异步化后未读数短暂不一致 | 高 | 中 | 增量事件 + 1 秒合并窗口；会话列表容忍 1s 误差；提供"精确未读"接口 |
| R3 | Redis Cluster hash tag 遗漏 | 中 | 高 | 编码期检查工具：扫描所有多键操作，断言同 slot；CI 拦截 |
| R4 | 事件总线积压 | 中 | 高 | `XLEN` 告警 + 消费组 lag 监控 + 自动扩容 Worker |
| R5 | 客户端未同步改造 | 中 | 高 | 服务端保持向后兼容（降级策略可通过配置关闭） |
| R6 | 分片迁移期间数据不一致 | 低 | 高 | 双写 + 校验工具 + 可回滚的迁移状态机 |
| R7 | 权限校验改读缓存后存在延迟窗口 | 中 | 中 | 成员移除**同步**删缓存；缓存缺失回源查库；敏感操作强制回源 |
| R8 | 压测环境与生产差异导致结论失真 | 中 | 中 | 压测前冻结容量基线；阶梯升压；记录环境快照 |

### 13.2 回滚策略

**按阶段独立回滚**，每阶段都有独立开关：

```yaml
cluster:
  enabled: false              # 关闭跨节点扇出，回到单节点模式
  crossnode_enabled: false     # 单独关闭事件总线
  broadcast_sharded: false     # 单独关闭分片广播
  projection_async: false      # 单独关闭异步投影
  large_group_degrade: false   # 单独关闭大群降级
```

**回滚原则**（沿用既有集群方案的约定）：

1. 不删除 Redis Stream、Outbox 表、业务数据。
2. 新旧代码可读写同一份数据。
3. 事件格式向后兼容，新增字段不改变旧节点解析。
4. 迁移工具必须**可暂停、可续跑、可回滚**。

### 13.3 上线顺序

```text
1. 灰度 1 个节点：只补齐 P0（编译修复），cluster.enabled=false
2. 全量部署 P0 + P1 代码，cluster.enabled=true，但只开 1 个消费组
3. 逐步加入第 2、第 3 个节点，验证跨节点投递
4. 开启分片广播（broadcast_sharded=true），观察 CPU 与延迟
5. 开启异步投影（projection_async=true），观察未读数收敛
6. 开启大群降级（large_group_degrade=true）
7. 数据层分片迁移（双写 -> 校验 -> 切读 -> 停旧写）
8. 24 小时长稳 + 扩容演练
9. 全量流量
```

每一步之间必须留 **>= 30 分钟稳定观察期**，且上一步指标全部达标才能进入下一步。

### 14.1 术语

| 术语 | 含义 |
| --- | --- |
| 扇出（Fan-out） | 一条消息投递到的客户端数量 |
| 背压（Backpressure） | 下游处理不过来时向上游施加的限制 |
| 分片（Shard） | 把数据按规则拆到多个存储实例 |
| hash tag | Redis Cluster 中 `{}` 包裹的部分，保证多键同 slot |
| 消费组（Consumer Group） | Redis Streams 的投递语义单元，每组独立收到全量消息 |
| `XAUTOCLAIM` | 认领超时未确认的 pending 消息 |
| 幂等（Idempotent） | 同一操作执行多次与执行一次结果相同 |
| 补偿 | 客户端通过 seq 缺口拉取遗漏消息 |
