# 通话时长限制与 RTC 成本控制方案

> 项目：通用IM（genericim-tongba）  
> 编制日期：2026-07-29  
> 方案状态：待实施  
> 适用范围：一对一语音通话、一对一视频通话、多人会议，以及 Agora/LiveKit RTC 资源

## 1. 背景与目标

部分测试账号长期保持通话，占用声网 RTC 频道和参与者分钟，已经造成不必要的 SDK 成本。现有项目虽然具备 `connect_time`、心跳、残留通话清理和管理员强制结束能力，但没有统一的“单次通话时长”和“每日累计时长”策略。

本方案的目标是：

1. 服务端成为通话时长的唯一裁决方，客户端倒计时只负责展示；
2. 到达上限后可靠释放数据库通话、WebSocket、CallKit 和 RTC 引擎；
3. 防止断网、切后台、重启 App、修改本地时间或伪造请求绕过限制；
4. 对测试账号单独限额，先控制成本，再逐步开放普通用户和会员权益；
5. 提供后台配置、审计、统计和告警，能够定位消耗异常的账号和设备。

## 2. 设计原则

### 2.1 服务端强制，客户端协同

客户端只能显示剩余时间和发起主动结束，不能决定通话是否继续。服务端必须在创建、接听、获取 RTC Token、心跳和结束通话等路径重复检查策略。

### 2.2 计时从接通开始

`calling`/`incoming` 阶段不计入媒体时长；双方进入 `connected` 后，以服务端 `connect_time` 作为唯一计时起点。重连、切后台和恢复页面均不能重置起点。

### 2.3 通话策略快照

通话建立时将当时生效的策略写入通话记录。后台之后修改默认上限，不影响已经接通的通话，也不会让历史统计失真。

### 2.4 结束必须幂等

客户端挂断、服务端超时、心跳清理、管理员强制结束和 RTC 回调可能并发发生。所有结束动作都必须使用数据库行锁或条件更新，只允许第一个终态转换者写入最终原因。

## 3. 推荐产品规则

首版建议使用以下默认值，全部可在后台修改：

| 用户/场景 | 单次上限 | 每日累计上限 | 备注 |
| --- | ---: | ---: | --- |
| 测试账号 | 10 分钟 | 60 分钟 | 默认用于内部测试和客户验收账号 |
| 普通用户 | 60 分钟 | 360 分钟 | 语音、视频分别计入累计时长 |
| VIP | 120 分钟 | 720 分钟 | 以会员权益配置为准 |
| SVIP | 180 分钟 | 1440 分钟 | 可按客户套餐调整 |
| 多人会议 | 60 分钟 | 独立配置 | 同时限制时长和最大参与人数 |

补充规则：

- 单次限制同时适用于语音、视频和视频降级后的语音；降级不重新计时；
- 测试账号默认最多 1 路并发通话；
- 测试账号连续结束后增加 5 秒冷却，防止快速反复创建频道；
- 每日累计按账号的实际 `connected` 秒数统计；多人会议另统计参与者分钟；
- 未接通、拒接、取消和 30 秒无人接听不消耗媒体时长；
- 管理员可以为特定账号设置临时豁免，但必须记录操作者、原因和失效时间。

## 4. 服务端数据模型

### 4.1 `calls` 表增加字段

现有模型位于 `backend/internal/models/call.go`，建议增加：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `max_duration_seconds` | int | 本通电话的单次上限快照 |
| `duration_warning_seconds` | int | 提醒阈值快照，默认 300 秒 |
| `policy_source` | varchar(30) | `test_user`、`normal`、`vip`、`svip`、`override` |
| `daily_limit_seconds` | int | 建立通话时读取的每日上限快照 |
| `daily_used_before_seconds` | int | 建立时已使用的每日累计时长 |
| `limit_expires_at` | datetime | `connect_time + max_duration_seconds` |
| `limit_warning_sent_at` | datetime | 服务端提醒去重时间 |
| `participant_count` | int | 会议或多人 RTC 参与人数快照 |

建议索引：

```sql
CREATE INDEX idx_calls_connected_limit
ON calls(status, limit_expires_at);

CREATE INDEX idx_calls_user_connected_time
ON calls(caller_id, status, connect_time);

CREATE INDEX idx_calls_callee_connected_time
ON calls(callee_id, status, connect_time);
```

### 4.2 系统设置

沿用 `system_settings`，在 `backend/internal/models/system_setting.go` 增加常量：

```text
call_duration_policy_enabled
call_test_user_max_duration_seconds
call_test_user_daily_limit_seconds
call_normal_max_duration_seconds
call_normal_daily_limit_seconds
call_vip_max_duration_seconds
call_vip_daily_limit_seconds
call_svip_max_duration_seconds
call_svip_daily_limit_seconds
call_meeting_max_duration_seconds
call_meeting_max_participants
call_duration_warning_seconds
call_duration_cooldown_seconds
call_rtc_token_grace_seconds
```

默认建议：

```text
call_duration_policy_enabled = true
call_test_user_max_duration_seconds = 600
call_test_user_daily_limit_seconds = 3600
call_normal_max_duration_seconds = 3600
call_normal_daily_limit_seconds = 21600
call_vip_max_duration_seconds = 7200
call_vip_daily_limit_seconds = 43200
call_svip_max_duration_seconds = 10800
call_svip_daily_limit_seconds = 86400
call_duration_warning_seconds = 300
call_duration_cooldown_seconds = 5
call_rtc_token_grace_seconds = 60
```

测试账号识别优先级建议为：显式账号策略 > 测试账号标签/白名单 > 会员等级 > 普通用户默认策略。不要仅按邮箱后缀或昵称判断测试账号。

## 5. 服务端接口改造

### 5.1 创建通话

改造 `POST /call/create`：

1. 查询主叫和被叫是否已有活动通话；
2. 计算主叫当前每日累计时长；
3. 检查每日上限、并发数、冷却时间和账号封禁状态；
4. 生成通话策略快照，但不在 `calling` 阶段扣除时长；
5. 将 `max_duration_seconds`、`daily_limit_seconds` 等写入 `calls`；
6. 如果当天剩余时间不足以开始最小通话窗口，返回明确错误。

建议错误码：

```text
CALL_DURATION_POLICY_DISABLED
CALL_DAILY_LIMIT_REACHED
CALL_CONCURRENT_LIMIT_REACHED
CALL_COOLDOWN_ACTIVE
CALL_ACCOUNT_RESTRICTED
CALL_DURATION_CONFIG_INVALID
```

### 5.2 接听通话

改造 `POST /call/accept`：

- 接听前再次检查通话是否仍为 `calling`；
- 检查策略是否允许该账号接通；
- 事务内写入 `status=connected`、`connect_time`、`limit_expires_at`；
- 只有事务成功后才返回 RTC Token；
- 如果接听过程中已超过策略或通话已终止，不生成 Token。

### 5.3 获取 RTC Token

改造现有 `buildCallRTCResponse` 和 Agora/LiveKit Token 服务：

```text
remaining = limit_expires_at - server_now
token_ttl = min(provider_default_ttl, remaining + rtc_token_grace_seconds)
```

要求：

- `remaining <= 0` 时拒绝发 Token并触发服务端结束；
- 重连只能按剩余时间签发新 Token；
- Token 有效期不得超过通话上限加缓冲时间；
- Token 生成日志只记录 TTL、provider、call_id 和结果，不记录密钥。

### 5.4 通话心跳

改造 `POST /call/heartbeat`：

- 返回 `active`、`status`、`connect_time`、`limit_expires_at`、`remaining_seconds`；
- 心跳进入时先检查时长，再更新 `last_heartbeat_at`；
- 超时使用条件更新把通话改为 `ended`，原因统一为 `duration_limit`；
- 返回 `active=false` 和 `reason=duration_limit`，客户端收到后立即释放 RTC。

心跳不能成为延长通话的依据。心跳只证明连接仍存活，不改变 `limit_expires_at`。

### 5.5 结束通话

沿用现有 `POST /call/end`，增加：

- `duration_limit` 为受信任的服务端结束原因，客户端不得伪造该原因获得特殊逻辑；
- 对已结束通话返回原始 `end_reason` 和 `duration`；
- 服务端自动结束后，向双方发送 `call_ended` 和 `call_released`；
- 结束事务成功后再发送 WS，避免客户端收到已回滚的结束事件。

## 6. 定时清理与异常兜底

现有 `backend/internal/handlers/call_cleanup_service.go` 已按心跳清理残留通话，应扩展查询条件：

```sql
status = 'connected'
AND (
  limit_expires_at <= NOW()
  OR last_heartbeat_at <= NOW() - heartbeat_stale_interval
)
```

处理优先级：

1. `limit_expires_at` 到期：原因 `duration_limit`；
2. 心跳过期但未到时长上限：原因 `heartbeat_timeout`；
3. `calling` 超过振铃窗口：原因 `timeout`。

定时任务建议每 5 秒执行一次，每批最多处理 100 条，并保留现有条件更新和幂等逻辑。服务重启后第一次执行必须立即扫描，不能等待完整周期。

## 7. 客户端实现

### 7.1 `CallService`

在 `lib/core/services/call_service.dart` 增加：

- `connectTime`、`limitExpiresAt`、`remainingSeconds`；
- 服务端时间偏移量，不使用手机本地时间直接判断；
- 每秒更新显示计时器；
- 5 分钟和 1 分钟提醒去重；
- 收到 `call_ended(reason=duration_limit)` 时执行统一 teardown；
- 心跳返回 `active=false` 时立即结束 Agora/LiveKit；
- 重连成功后重新拉取活动通话，沿用服务端剩余时长。

客户端倒计时只用于用户提示，真正的自动结束仍依赖服务端事件、心跳响应和 Token 过期三重保障。

### 7.2 通话页面

在 `lib/features/call/pages/call_page.dart`：

- 在通话计时旁显示“剩余 09:32”；
- 剩余 5 分钟时显示轻提示，不打断通话；
- 剩余 1 分钟时显示明显提示；
- 自动结束时显示“本次通话已达到时长限制”；
- 不允许用户通过最小化、返回桌面或锁屏隐藏限制状态。

### 7.3 会议页面

`lib/features/meeting/pages/meeting_page.dart` 同样读取服务端 `limit_expires_at`。会议超过上限时：

- 服务端结束会议记录；
- 广播会议结束事件；
- 客户端断开 Agora/LiveKit 房间；
- 清理摄像头、麦克风和重连定时器；
- 页面回到会议列表或聊天页。

## 8. 后台管理功能

建议在通话管理页面增加三个区域：

### 8.1 通话策略

- 开关：启用/停用时长限制；
- 测试账号、普通用户、VIP、SVIP 的单次上限；
- 各等级每日累计上限；
- 语音、视频、会议的独立策略；
- 提醒时间和 Token 缓冲时间；
- 修改前显示影响范围，保存后记录审计日志。

### 8.2 测试账号管理

- 添加/移除测试账号；
- 设置账号级单次上限和每日上限；
- 临时豁免开始时间和结束时间；
- 查看当前活动通话并强制结束；
- 查看当日已使用分钟和剩余分钟。

### 8.3 成本与异常统计

至少展示：

- 今日 RTC 总通话分钟和参与者分钟；
- Agora/LiveKit 分 provider 统计；
- 按账号、设备、IP、通话类型排行；
- 自动结束数量及原因；
- 平均通话时长、P95/P99 通话时长；
- 同时在线频道数和峰值；
- Token 生成失败、过期和重复请求数量。

## 9. 计费与统计口径

一对一通话建议记录：

```text
connected_seconds
caller_seconds
callee_seconds
provider
call_type
participant_count
end_reason
```

多人会议按参与者分钟统计：

```text
participant_minutes = Σ(每个参与者实际连接秒数) / 60
```

统计必须使用服务端 `connect_time` 和 `end_time`，不能使用客户端上传的时长。每日统计按业务时区计算，并明确跨午夜通话的归属规则：建议按实际连接秒拆分到两个自然日。

## 10. 安全与绕过防护

- 不信任客户端传入的 `duration`、`connect_time`、`end_reason`；
- 所有策略以用户 ID、会员等级、测试账号标签和后台配置为准；
- 接听、获取 Token、心跳、重连都检查剩余时间；
- 结束后禁止再次获取同一 `call_id` 的 Token；
- 同一用户同时活动通话数量由数据库事务和行锁控制；
- 使用服务端时间，客户端时间只用于展示；
- Token TTL 不得大于通话剩余时间加缓冲；
- 记录策略命中、拒绝、自动结束和管理员豁免审计；
- 管理员豁免必须有操作者、原因、起止时间和审批备注。

## 11. 灰度发布步骤

### 阶段一：只统计不挂断

- 增加策略计算和日志；
- 不自动结束，只记录“如果启用将在哪个时间点结束”；
- 观察测试账号、普通用户和 VIP 的实际分布；
- 校验每日累计统计是否正确。

### 阶段二：仅限制测试账号

- 测试账号单次 10 分钟、每日 60 分钟；
- 开启服务端结束和 Token TTL；
- 观察 24～48 小时；
- 重点检查断网、后台、重连和双端页面释放。

### 阶段三：开放普通用户和会员策略

- 普通用户 60 分钟；
- VIP/SVIP 使用后台配置；
- 继续保留单账号豁免和管理员强制结束；
- 根据 RTC 成本和用户反馈调整额度。

### 回滚方式

- 关闭 `call_duration_policy_enabled`；
- 保留数据库策略快照和结束记录；
- 不删除新增字段；
- Token TTL 是否回滚必须单独评估，避免已经发出的短 Token 行为不一致。

## 12. 测试计划

### 12.1 后端单元测试

- 不同用户等级策略选择；
- 测试账号覆盖普通用户策略；
- 单次上限边界：`599/600/601` 秒；
- 每日累计边界；
- 连接前不计时；
- 重连不重置 `connect_time`；
- 并发结束只有一个终态写入；
- 到期心跳返回 `duration_limit`；
- Token TTL 不超过剩余时间加缓冲；
- 跨午夜累计时长拆分。

### 12.2 双端真机测试

- 两台设备连续通话至 5 分钟提醒；
- 到达 10 分钟自动挂断；
- 主叫挂断、被叫挂断和服务端超时同时发生；
- 通话中切后台、锁屏、杀进程后恢复；
- 短断网恢复和长断网超时；
- 视频转语音不重新计时；
- iOS CallKit、Android 来电页和通话页面同步退出；
- 自动结束后立即重拨，确认新通话拥有新的 `call_id` 和频道。

### 12.3 绕过测试

- 修改手机系统时间；
- 停止客户端心跳；
- 重复请求 Token；
- 伪造较大的客户端 `duration`；
- 重复调用 `/call/end`；
- 断网后保持 Agora 频道连接；
- 多设备同时接听或重复加入频道。

### 12.4 验收标准

- 服务端到期后 5 秒内将通话标记为 `ended`；
- 双端在 10 秒内释放 RTC 引擎和系统通话界面；
- 到期通话无法重新获取有效 Token；
- 重连不能延长原通话；
- 测试账号每日累计达到上限后无法新建通话；
- 结束原因、实际时长和策略来源可在后台查询；
- 自动结束不产生重复通话记录、重复消息或残留频道；
- Go 测试、Flutter 测试、静态分析和双端 Release 构建全部通过。

## 14. 推荐最终口径

本功能不应宣传为“客户端倒计时挂断”，而应定义为：

> 通用IM新增通话时长管理能力。系统根据账号类型和后台策略，对语音通话、视频通话及会议设置单次和每日使用上限。达到限制后，系统会提前提醒并由服务端自动结束通话，以保障服务稳定和资源合理使用。

首期建议立即对测试账号启用 **单次 10 分钟、每日 60 分钟** 的限制，待 24～48 小时观测稳定后，再开放普通用户和会员策略。
