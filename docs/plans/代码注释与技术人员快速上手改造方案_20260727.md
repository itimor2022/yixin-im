# 代码注释补充方案

日期：2026-07-27  
状态：待实施

## 一、目标

只给现有代码补充中文注释，方便其他技术人员快速理解代码。

本次工作严格遵守：

- 不修改业务逻辑。
- 不重构、不拆分文件。
- 不修改接口、字段、配置和数据库结构。
- 不调整 UI、依赖和工程结构。
- 不进行全仓格式化。
- 不新增额外的上手文档。

## 二、注释范围

需要补充注释的代码目录：

| 模块 | 目录 | 主要语言 |
| --- | --- | --- |
| Flutter 客户端 | `lib/` | Dart |
| Go 后端 | `backend/` | Go |
| 运营管理后台 | `admin/src/` | TypeScript、Vue |
| 官方客服后台 | `admin-kf/src/` | TypeScript、Vue |
| H5/PWA | `h5/src/` | TypeScript、Vue |
| 构建和部署脚本 | `scripts/` | PowerShell、Shell、Python、JavaScript |

以下内容不添加注释：

- `*.g.dart` 等自动生成文件。
- `third_party/` 第三方代码。
- `node_modules/`、`build/`、`.dart_tool/`、`dist/`。
- Flutter、Android、iOS、Windows 自动生成的插件注册代码。
- 图片、字体、压缩包等资源文件。
- 一眼就能看懂的简单赋值、getter、setter 和普通 UI 样式。

## 三、需要添加什么注释

### 3.1 文件和模块注释

在核心入口或大型业务文件顶部说明：

- 当前文件负责什么功能。
- 主要调用方和依赖。
- 核心数据从哪里获取。
- 需要特别注意的生命周期或平台差异。

普通小文件不强制添加文件头注释。

### 3.2 类和结构体注释

给以下类型补充职责说明：

- Flutter Provider、Notifier、Service 和核心 Widget。
- Go Handler、Service、Model 和中间件。
- TypeScript Store、Service、Composable 和公共类型。
- Vue 大型页面和核心业务组件。

注释重点说明类型管理什么状态、供谁调用、数据以哪里为准。

### 3.3 方法注释

给以下方法补充注释：

- 对外提供能力的公共方法。
- 业务流程较长的方法。
- 包含权限、事务、并发、重试或缓存的方法。
- 包含多平台兼容逻辑的方法。
- 名称无法完整表达业务含义的方法。

方法注释说明：

- 方法做什么。
- 重要参数代表什么。
- 返回值代表什么。
- 是否存在副作用。
- 失败后如何处理。

### 3.4 复杂逻辑注释

在以下代码附近添加简短行内注释：

- 消息发送、同步、去重和排序。
- WebSocket 连接、重连和事件分发。
- 未读数、已读状态和多端同步。
- 登录、Token 刷新、退出和账号切换。
- 本地缓存写入、失效和清理。
- 图片、视频和文件上传。
- 钱包、红包、转账、充值和提现。
- 通话、会议、心跳和资源释放。
- 权限校验、幂等、锁和事务。
- Android、iOS、Windows、Web 的差异处理。

## 四、注释写法

### 4.1 正确写法

注释重点解释代码背后的原因、规则和限制。

```dart
/// 管理当前账号的消息列表和发送状态。
///
/// 服务端 seq 是消息顺序的最终依据；本地数据库只用于首屏和离线展示。
class MessageNotifier extends StateNotifier<MessageState> {
  // 先显示带 clientMsgId 的临时消息，服务端确认后再替换 msgId 和 seq。
}
```

```go
// SendMessage 校验会话权限、分配消息序号并持久化消息。
// clientMsgID 是幂等键，客户端重试时不能重复创建消息。
func (s *MessageService) SendMessage(...) (...) {
}
```

```ts
/**
 * 保存对象存储设置。
 * 保存成功后只影响新上传文件，不迁移已经存在的媒体对象。
 */
export async function saveStorageSettings(...) {
}
```

### 4.2 错误写法

不要添加重复代码字面含义的注释：

```dart
// 设置加载状态为 true
isLoading = true;
```

不要添加以下类型的注释：

- “这里调用接口”。
- “遍历列表”。
- “返回结果”。
- “创建对象”。
- “以后再优化”。
- 无法确认是否正确的业务推测。
- 注释掉但不再使用的旧代码。

## 五、语言规范

### Dart

- 公共类、Provider、Service 和公共方法使用 `///`。
- 方法内部复杂分支使用 `//`。
- 注释 Provider 的状态来源、作用范围和清理时机。
- 注释异步任务、订阅、Timer、Controller 和媒体资源的释放位置。

### Go

- 导出类型和方法使用 GoDoc 格式。
- 注释 Handler 的权限和参数约束。
- 注释 Service 的事务、锁、幂等和缓存规则。
- 注释 MySQL、MongoDB、Redis 和 WebSocket 之间的数据关系。

### TypeScript / Vue

- 公共方法、Store、Composable 和复杂类型使用 `/** */`。
- Vue 大型页面使用短注释划分业务区域。
- 注释 API 字段与后端字段的对应关系。
- 注释事件监听、轮询、WebSocket 和媒体设备的释放逻辑。

### PowerShell / Shell

- 文件头说明脚本用途、运行条件、参数和产物。
- 部署脚本说明会修改哪些目标。
- 高风险步骤说明失败后的处理方式。
- 注释中不能包含密码、Token 和私钥。

## 七、实施方式

按小批次处理，避免一次修改过多文件：

1. 每批只处理一个业务模块。
2. 每批建议处理 5 至 15 个文件。
3. 只增加或调整注释，不改代码执行逻辑。
4. 不对整个文件或整个仓库执行无关格式化。
5. 每批完成后检查 Git diff，确认没有逻辑改动。
6. 每批单独进行代码评审。

建议批次：

| 批次 | 内容 | 预计时间 |
| --- | --- | ---: |
| 1 | 启动、路由、配置、认证 | 1 人日 |
| 2 | 消息发送、同步、WebSocket | 2 至 3 人日 |
| 3 | 媒体上传和缓存 | 1 人日 |
| 4 | 钱包、通话、会议 | 2 至 3 人日 |
| 5 | 好友、群组、设置、推送 | 2 人日 |
| 6 | Admin、客服端、H5 其他页面 | 2 人日 |
| 7 | 构建、部署和测试脚本 | 1 至 2 人日 |

总预计时间：11 至 14 人日。

## 八、检查标准

每批注释完成后检查：

- [ ] 注释使用简体中文，技术字段保留原英文名称。
- [ ] 注释解释业务规则和原因，没有复述简单代码。
- [ ] 公共类型和复杂方法具备职责说明。
- [ ] 关键状态、数据来源和失败处理已经说明。
- [ ] 注释与当前代码实现一致。
- [ ] 没有添加无法确认的推测。
- [ ] 没有添加密码、Token、账号或私钥。
- [ ] 没有修改业务逻辑。
- [ ] 没有混入重构、UI 或全仓格式化。
- [ ] 生成代码和第三方代码没有被修改。

## 九、验收标准

本次注释工作满足以下条件即可验收：

1. P0 核心文件已经完成注释。
2. P1 高风险业务的关键类和复杂方法已经完成注释。
3. 新增注释能够说明职责、数据来源、状态变化和重要限制。
4. Git diff 中只有注释变化，没有业务逻辑变化。
5. 代码仍能正常通过原有静态检查和测试。
6. 不以注释行数作为验收标准，不给简单代码强行添加注释。
