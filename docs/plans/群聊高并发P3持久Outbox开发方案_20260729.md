# 群聊高并发 P3-1 持久 Outbox 开发方案

## 1. 目标

消息正文已经写入 MongoDB 后，即使 API 进程在 250–500ms 合批窗口内退出，也不能永久丢失以下派生工作：

- MySQL `user_chats` 最后消息、排序、未读数和 @ 状态投影。
- 消息媒体 `binding -> bound` 提交。
- 离线推送。
- 私聊客服会话同步。
- 会话列表缓存失效和当前用户多端状态同步。

## 2. 当前问题

当前这些任务主要保存在 Go channel、map 和 timer 中。它们降低了 ACK 延迟，但进程重启会清空尚未 flush 的任务。

消息正文权威存储是 MongoDB，派生投影和媒体状态位于 MySQL，缓存位于 Redis，推送又是外部服务。当前部署不具备跨 Mongo/MySQL/Redis/推送厂商的分布式事务，因此不能声称所有系统可以严格 exactly-once 原子提交。

## 3. 实现边界

### 本阶段实现

1. 新增 MySQL `message_outbox_events`。
2. Mongo 消息提交后、HTTP ACK 前，批量插入带唯一 `event_key` 的 Outbox 事件。
3. Outbox 插入失败时返回可重试错误；客户端继续使用相同 `msg_id` 重试。
4. 幂等重试发现 Mongo 消息已存在时，仍会补建缺失的 Outbox 事件。
5. worker 使用状态、租约、worker ID、可用时间和重试次数安全认领任务。
6. 进程重启后自动认领 pending/retrying 或租约过期的 processing 事件。
7. MySQL 会话投影和 `db_applied_at` 在同一事务提交，避免重试重复增加未读数。
8. 媒体提交使用条件更新，天然幂等。
9. 缓存和多端状态在数据库投影完成后执行；失败或进程退出时可重试。
10. 推送按群合并最高 seq，失败退避重试。
11. 超过最大次数进入 dead 状态并保留错误原因。

### 本阶段不实现

- MongoDB 与 MySQL 的 XA/分布式事务。
- 外部推送厂商严格 exactly-once。崩溃发生在厂商成功响应与本地完成标记之间时，允许至少一次重试；客户端使用稳定 notification ID 折叠。
- 多 API 实例 WebSocket 事件总线，属于 P3-2。
- 24 小时长稳和大规模云真机，属于 P3-3/P3-4。

## 4. 数据模型

`message_outbox_events` 关键字段：

| 字段 | 作用 |
|---|---|
| `event_key` | 唯一幂等键，格式包含 chat、msg_id、事件类型 |
| `event_type` | projection、media_commit、push、service_conversation |
| `payload` | 事件最小不可变快照 |
| `status` | pending、processing、retrying、completed、dead |
| `attempts` | 尝试次数 |
| `available_at` | 下次可处理时间 |
| `lease_until` | processing 租约截止时间 |
| `worker_id` | 当前认领 worker |
| `db_applied_at` | MySQL 权威派生状态已经应用 |
| `completed_at` | 全部步骤完成 |
| `last_error` | 最近错误，限制长度 |

## 5. 处理语义

### 会话投影

1. 同一轮认领的 projection 事件按 chat 合并。
2. 只用最高 seq 更新最后消息预览。
3. 按消息数和发送者计数批量更新未读数。
4. 投影 SQL 与各事件 `db_applied_at` 在同一个 MySQL 事务完成。
5. 重试发现 `db_applied_at` 已存在时不再增加未读数。
6. 事务提交后执行缓存失效和 `chat_state_changed`。
7. 后置步骤成功后标记 completed；后置步骤重试不会重复数据库投影。

### 媒体提交

1. 批量提取唯一 media_id。
2. 仅把 `binding` 条件更新为 `bound`。
3. 更新与事件完成状态在同一 MySQL 事务完成。

### 推送

1. 同群短窗口内只处理最高 seq，低 seq 事件标记为 superseded/completed。
2. 继续批量筛选在线、静音、无设备成员。
3. 厂商失败进入 retrying。
4. 成功后标记 completed。

### 客服会话

1. 使用会话内最高客户消息 seq 做重复和乱序保护。
2. 已处理相同或更高 seq 时不重复增加客服未读数，也不回退预览。
3. 失败进入 retrying。

## 6. 生命周期

```text
Mongo 消息提交
    |
    +-- ACK 前插入唯一 Outbox 事件
            |
            +-- pending
                    |
                    +-- processing（带租约）
                            |
                            +-- completed
                            |
                            +-- retrying（指数退避）
                            |
                            +-- dead（超过上限）
```

worker 异常退出后，其他 worker 或重启后的进程可以认领 `lease_until` 已过期的 processing 事件。

## 7. 验收门槛

1. Outbox 唯一键重复插入不会生成重复事件。
2. projection 重放不会重复增加未读数。
3. media commit 重放保持 bound 且引用状态正确。
4. API 在任务 pending/processing 时被重启，恢复后 pending/retrying/过期 processing 全部排空。
5. 人工注入失败时 attempts、available_at、last_error 正确推进。
6. 超过最大次数进入 dead，不无限热循环。
7. 100/200/300/500 文本和图片消息无丢失、重复和 seq 缺口。
8. Redis `SCAN=0`。
9. 500 人消息 ACK p95 `<1s`，且相对当前固定基线退化不超过 20%。
10. Go 全量测试通过，容器重启恢复测试有原始证据。

## 8. 发布与回滚

- 表结构只新增，不修改或删除现有业务数据。
- 上线先让 worker 处于关闭状态完成建表，再启用生产者和消费者。
- 回滚代码时保留 `message_outbox_events`，不得删除 pending/dead 证据。
- 恢复上线后可以继续消费历史 pending/retrying 事件。

## 9. 实施结果（2026-07-29）

本方案中的 P3-1 已完成本地实现和 Docker 验收：

- 已新增 `message_outbox_events`、唯一事件键、租约、退避、dead 状态和数据库阶段标记。
- 正常消息发送已从进程内投影/媒体/推送队列切换到持久 Outbox。
- 文本和真实上传图片均通过“ACK 后立即终止 API、重启恢复、相同 msg_id 重试、过期 processing 租约重放”。
- 500 并发集中写入文本/图片 ACK p95 分别为 `488.81ms/624.20ms`，相对上一版 `412.04ms/528.08ms` 基线退化约 `18.6%/18.2%`，未超过 20% 门槛。
- 本轮所有测试事件最终为 completed，pending/processing/retrying/dead 为 0，Redis SCAN 增量为 0。
