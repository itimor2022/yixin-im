# 共同群聊创建显示与解散清理修复验收计划

## 1. 问题

好友资料页的“共同群聊”存在两个需要成对验收的生命周期场景：

1. 双方创建并加入正常群聊后，共同群聊列表和数量应立即包含该群。
2. 群主解散群聊后，成员记录为保留历史消息仍继续存在，但共同群聊列表和数量不应继续包含该群。

当前后端共同群聊查询只按双方成员关系和群类型筛选，没有排除 `status = 2`
的已解散群。解散逻辑又会刻意保留 `chat_members`，因此已解散群仍会被共同群聊
查询命中。

## 2. 本次范围

- 统一共同群聊列表与关系摘要数量的有效群口径。
- 仅把 `status = 0` 的正常群/频道计入共同群聊。
- 保持正常群创建后可被共同群聊查询命中。
- 增加自动化回归测试，覆盖正常、封禁、已解散三种状态。
- 在本地 Docker 后端和物理 Android 设备上验收创建、显示、解散、消失完整链路。
- 留存接口响应、真机截图/UI 树和错误日志证据。

## 3. 不在本次范围

- 不删除已解散群的成员、会话或历史消息。
- 不改变已解散群只读历史会话的现有产品逻辑。
- 不修改好友关系、共同联系人或群成员退出逻辑。
- 不处理与本问题无关的现有工作区改动。
- 不部署到线上生产环境。

## 4. 实现方案

1. 在 `RelationshipService.CommonGroups` 的群查询中增加
   `chats.status = ChatStatusNormal`。
2. 在 `RelationshipService.CommonInfo` 的共同群数量查询中使用相同状态条件。
3. 用回归测试证明：
   - 正常群出现在列表中并计入数量；
   - 封禁群和已解散群不出现在列表中，也不计入数量；
   - 保留的 `chat_members` 不会让已解散群重新出现。
4. 若真机创建后不显示但接口已经正确，继续检查资料页数据刷新时机并修复客户端。

## 5. 验收步骤

### 5.1 自动化

1. 运行 `RelationshipService` 定向测试。
2. 运行后端相关包测试。
3. 运行 Go 格式化和静态检查。

### 5.2 接口

1. 使用测试账号 A、B 登录本地 API。
2. 记录创建前共同群聊列表和数量。
3. A 创建包含 B 的群聊。
4. 验证 A 查询 B、B 查询 A 时列表均包含新群，数量同步增加。
5. A 解散该群。
6. 验证双方查询时列表均不包含该群，数量恢复。
7. 验证数据库仍保留群成员记录，证明修复依赖状态过滤而不是破坏历史数据。

### 5.3 真机

1. 构建绑定局域网本地 API 的当前源码 APK，并安装到两台物理 Android 设备。
2. 两台设备分别登录测试账号 A、B。
3. 在 A 端创建包含 B 的群聊。
4. 在 A、B 的好友资料页检查“共同群聊”数量和列表，新群必须可见。
5. A 解散群聊。
6. 两端重新进入/刷新好友资料页，已解散群必须消失。
7. 保存创建后和解散后的截图、UI 树、接口证据及 logcat；检查无 Fatal、ANR、
   FlutterError。

## 6. 通过标准

- 正常新建群在双方共同群聊列表中可见，数量正确。
- 解散后双方共同群聊列表不再显示该群，数量正确。
- 列表接口与关系摘要接口口径一致。
- 已解散群的历史成员/消息保留逻辑不受影响。
- 定向自动化测试通过。
- 至少两台物理 Android 设备完成可见界面验收，且无相关致命日志。
