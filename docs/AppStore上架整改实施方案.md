# App Store 上架整改实施方案

> 制定日期：2026-07-22
> 目标：按上架同事反馈完成 iOS 审核版整改，优先消除支付合规、演示数据、首次登录和内容质量风险。

## 1. 结论与推荐路线

本次推荐采用“快速合规版”重提：

1. iOS 审核包彻底移除 VIP 购买能力，以及所有从 VIP 引向钱包充值、微信支付、支付宝的入口。
2. 同时限制 iOS 端深链和后端购买接口，不能只隐藏按钮。
3. 保留 Android/后台现有能力，但通过明确的平台能力开关隔离，避免 iOS 包出现第三方支付文案或路径。
4. 清理线上演示账号和仓库种子数据，只保留 2 个正常会话；广场统一为“协同办公/团队沟通”主题。
5. 本次直接删除广场视频内容，先保证秒开和审核稳定；视频优化放到后续版本。
6. 修复首次安装登录竞态，并用真机卸载重装方式重复验收。

当前仓库没有 StoreKit / `in_app_purchase` 依赖，也没有苹果商品、交易验证、恢复购买、退款通知和订单幂等链路。若现在改成苹果内购，预计需要完整开发和 App Store Connect 联调，不适合作为本次快速重提方案。

Apple 当前审核规则 3.1.1 要求：用于解锁 App 内功能的数字会员必须使用苹果内购。当前“钱包充值 -> 钱包余额购买 VIP”仍可能被视为绕过内购，不能只把 VIP 页里的微信/支付宝按钮改名。参考：[App Review Guidelines](https://developer.apple.com/app-store/review/guidelines/)。

## 3. 分项整改方案

### 3.1 清除所有用户可见的“测试/演示”内容

处理范围：

- Flutter 客户端文案与多语言资源。
- 后端接口错误信息、系统公告、发现页配置和默认欢迎语。
- 线上 MySQL/MongoDB 中的用户昵称、备注、会话、消息、动态、评论、话题、举报样本、钱包备注。
- App Store 截图、预览视频、审核说明和版本描述。
- `backend/scripts/seed_demo_data.sql`、`backend/scripts/seed_demo_messages.js`，防止重新部署后脏数据再次出现。

执行原则：

- 删除“测试、演示、样例、已充钱、充值成功、数字占位”等面向用户的内容。
- 保留内部测试代码和测试用例，不把正常词语（例如后台管理员的“测试推送”工具）误删到生产能力损坏；iOS App 不可见的后台工具单独核对。
- 增加发布前关键词扫描清单，至少覆盖：`测试|演示|源码|已充钱|购买源码|联系QQ|加微信`。

### 3.2 iOS VIP 支付合规

#### 本次推荐：从 iOS 审核包删除 VIP 商业化链路

客户端处理：

- 设置页在 iOS 审核构建中不显示“VIP会员”购买入口。
- `/vip`、`/vip/orders`、`/wallet/recharge` 的深链不能绕过开关进入购买流程。
- 移除 iOS VIP 页中的套餐价格、购买按钮、钱包余额、充值按钮、“余额不足/去充值”等文案。
- iOS 钱包页不展示微信/支付宝充值入口；任何可给数字权益充值的路径都必须隔离。
- 创建群/频道遇到会员限制时，iOS 不显示“充值/购买 VIP”引导。若该能力是审核演示必需，应暂时给 iOS 用户开放基础额度，而不是引导外部购买。

服务端处理：

- 为 iOS 审核构建增加可审计的平台能力开关，例如 `ios_vip_purchase_enabled=false`。
- `/vip/purchase` 不能只信任前端按钮状态；根据登录设备平台和客户端版本拒绝 iOS 钱包购买。
- 返回的 bootstrap/系统设置应明确告诉客户端关闭 VIP 购买和在线充值。
- 保持 Android 与后台管理路径不变，避免一次整改扩大到全平台。

验收要求：

- iPhone 上从设置、个人资料、建群/建频道拦截、钱包、搜索、历史订单和深链遍历，均不能进入第三方支付购买 VIP。
- 抓包确认 iOS 不会请求微信/支付宝下单接口，也不能直接调用 `/vip/purchase` 成功。
- App 二进制对应的用户可见多语言文案中不再出现“微信支付/支付宝购买 VIP/去充值开通会员”。

#### 后续可选：正式接入苹果内购

如果产品必须在 iOS 销售 VIP，应另开版本完成：

- App Store Connect 创建月卡/年卡商品；按权益期限选择自动续订订阅，不能继续沿用人民币钱包余额扣款。
- Flutter 接入 StoreKit，完成商品加载、购买中、取消、失败、待处理、恢复购买。
- 后端验证 Apple 签名交易，以 `transactionId/originalTransactionId` 做唯一幂等，不信任客户端传来的成功状态。
- 建立 Apple Server Notifications V2，处理续订、到期、退款、撤销和账单重试。
- 建立 Apple 商品 ID 与现有 VIP 套餐的映射，禁止同账号重复开通或错误降级。
- 用 Xcode StoreKit、本地配置和 Apple Sandbox 覆盖成功、取消、失败、恢复、退款、重复通知等场景。
- 首个 IAP 与新 App 版本一起提交审核，并在 Review Notes 说明入口和审核账号。

Apple 官方配置和测试参考：[配置 In-App Purchase](https://developer.apple.com/help/app-store-connect/configure-in-app-purchase-settings/overview-for-configuring-in-app-purchases/)、[Sandbox 测试](https://developer.apple.com/help/app-store-connect/test-in-app-purchases/overview-of-testing-in-sandbox/)。

### 3.3 删除截图中的“卖源码”内容

当前消息没有附截图，因此先做全量治理，拿到截图后再按账号/动态 ID 二次核销：

- 删除相关动态、评论、私聊消息、群/频道、发现页入口、二维码、外链和联系方式。
- 对发布者执行内容下架；是否封禁账号由运营确认，避免误删正常用户。
- 扫描关键词：`源码、出售、购买、搭建、代搭、授权、联系QQ、加微信、TG、Telegram`，人工复核后删除。
- 图片不能只扫文字字段；对截图、海报、二维码进行人工检查，必要时增加 OCR 审核。
- 检查现有“举报、屏蔽用户、屏蔽内容、客服联系信息”在 iOS 真机上可用。Apple 对用户生成内容要求具备过滤、举报、屏蔽和联系方式能力。

### 3.4 修复首次安装无法登录

高概率根因不是账号密码，而是首次安装时设备 ID / Keychain / SharedPreferences 初始化与登录提交发生竞态：

- `login_page.dart` 在获取设备 ID、设备名称及调用登录时缺少覆盖全流程的 `try/catch/finally`，异常时可能一直处于加载状态或只显示泛化错误。
- `auth_service.dart` 在服务端返回成功后写 TokenStorage；若写入失败，状态会退回未登录，但仍把原始“成功响应”返回，页面随后跳转首页，造成状态与路由不一致。

修复方式：

1. 启动阶段预热 `DeviceService`、SharedPreferences 和 TokenStorage；初始化完成前登录按钮显示准备中。
2. 设备 ID 获取失败时使用本次安装 UUID 的安全兜底，并记录具体失败阶段。
3. 登录提交全流程加 `try/catch/finally`，任何异常都恢复按钮状态，不要求用户杀进程。
4. 只有“服务端成功 + token/user 解析成功 + token 持久化成功 + AuthState=authenticated”四项都成立才允许跳转。
5. TokenStorage 写入失败时返回真正的失败结果，清理半写入状态；可在短延时后自动重试一次，但不把 token 降级明文保存。
6. 增加 `device_init`、`login_api`、`token_persist`、`route_guard` 分阶段日志，提示文案改成用户可理解的“登录初始化失败，请重试”。

真机验收：

- 使用至少 1 台真实 iPhone，连续执行 10 次“删除 App -> 安装 -> 首次启动 -> 同意协议 -> 登录”，要求 10/10 首次成功。
- 每轮都使用提供给审核的 `demo` 账号；密码只放在 App Store Connect Review Notes/安全交接单，不写入 Git 仓库。
- 同时覆盖首次拒绝通知权限、弱网、切后台再回来、连续点击登录、登录后立即杀进程重启。
- 检查失败时无需重启 App，原页面点击一次即可重试成功。

### 3.5 精简审核账号会话

审核账号只保留 2 个会话：

1. `通用IM助手`：正常欢迎语、隐私与安全提示、使用帮助。
2. `项目协作群`：3～5 位正常成员，保留几条工作沟通、文件协作和会议安排消息。

清理内容：

- 删除其他联系人、群、频道、置顶、草稿、未读红点和历史空会话。
- 删除红包、转账、充值、提现、VIP 购买、举报样本、风控样本和自动化测试消息。
- 不展示“演示账号、测试群、客服测试、已充值、高余额”等说明。
- 账号昵称、头像、签名统一为正式产品语气；登录用户名 `demo` 可以保留，但 App 内昵称不使用“demo/演示”。

不要只清客户端缓存；需要清理服务端会话关系、消息库和线上账号数据，再用全新设备登录确认服务器只返回 2 个会话。

### 3.6 重做广场内容

本次统一为“协同办公/团队沟通”主题，与 IM 产品核心能力一致。

建议保留 6 条图片动态：

1. 版本更新：消息同步和会话体验优化。
2. 团队协作：项目群内同步本周任务。
3. 文件协同：文档、图片和文件快速分享。
4. 远程会议：语音/视频会议的工作场景介绍。
5. 日程推进：会议纪要和待办跟进。
6. 安全办公：登录设备管理、隐私和消息保护。

内容要求：

- 每条 1～3 张同一视觉风格的原创或有商用授权图片，不使用来源不明的网图。
- 不出现“测试、演示、已充钱、VIP充值、源码、数字占位、虚假成交、联系方式、二维码”。
- 不做夸张的点赞/评论/浏览数字；可全部从 0 开始，或只保留少量自然互动。
- 不混入外卖、娱乐、充值、红包、博彩、交友等不相关内容。
- 更新日志可以持续发布，但要写成正式版本说明，不写“测试通过/回归完成”。
- 同步改写 `seed_demo_data.sql`，线上数据清理后再次执行种子也不能恢复旧内容。

### 3.7 广场视频处理

本次重提直接删除审核账号和公共广场中的视频动态，只保留优化后的图片内容。这是风险最低、验收最快的方案。

后续若恢复视频，最低要求为：

- H.264/AAC MP4，720p，短视频优先控制在 10 MB 内并生成独立封面。
- CDN/对象存储支持 Range 请求、正确的 `Content-Type`、缓存头和就近加速。
- 信息流只加载封面，用户点击后才创建播放器；只预加载当前项，不同时初始化多个视频。
- 记录首帧时间、失败率和文件大小，4G/弱网下首帧目标不超过 2 秒。

### 3.8 后台动态 iOS 功能配置

管理后台“系统设置 -> 功能设置”增加统一的 iOS 功能配置。开启后可分别控制：

- VIP 入口；
- 钱包入口；
- 钱包充值；
- 广场视频；
- 自定义栏目。

新部署且数据库尚未保存该配置时，默认启用合规模式并关闭上述高风险入口，避免因漏配导致提审包暴露第三方数字内容支付或慢视频。

开关同时作用于 Flutter 页面入口、路由跳转和后端接口；钱包、VIP 不能只隐藏按钮，直接请求接口也必须被拒绝。广场视频关闭后，列表、详情、搜索、我的动态和发布接口都不再向 iOS 提供视频内容。

该配置是面向所有 iOS 正式用户的生产功能配置，不能识别审核账号、审核设备或审核人员，也不能在审核通过后自动恢复第三方数字内容支付。若将来在 iOS 恢复 VIP 购买，必须先完成 Apple In-App Purchase，再开启对应入口。

## 7. 上架审核说明建议

Review Notes 只写正式信息，不出现“为了过审临时隐藏”等表述：

> 本版本已优化首次安装登录流程与内容展示。审核账号登录后可体验私聊、群聊、文件协作、动态广场、举报与屏蔽等主要功能。iOS 版本当前不提供 VIP 购买或第三方支付购买数字权益。审核账号和密码请填写在 App Store Connect 的专用审核账号字段中。

密码不得提交到 Git、公开文档、截图文件名或普通群消息中。
