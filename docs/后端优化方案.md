# 后端优化方案

更新时间：2026-06-23

## 1. 目标

这份方案的目标不是一次性大重构，而是用可回归、可上线的小步迭代，把后端从“功能能跑”逐步整理成“好维护、好扩展、好排查、好压测”的结构。

当前后端已经覆盖 IM、群/频道、消息、钱包、音视频、推送、发现、后台管理等核心能力，功能面比较全。主要问题不在“缺功能”，而在业务逻辑集中在 handler、权限判断分散、查询链路难复用、测试和观测不够系统。后续新增功能越多，这些问题会放大。

## 2. 当前主要问题

### 2.1 Handler 过大，业务逻辑和 HTTP 层混在一起

目前大文件比较明显：

| 文件 | 当前规模 | 风险 |
| --- | ---: | --- |
| `backend/internal/handlers/chat_handler.go` | 约 3700 行 | 群管理、成员、权限、消息入口混杂 |
| `backend/internal/handlers/user_handler.go` | 约 3100 行 | 用户资料、隐私、关系、账号安全混杂 |
| `backend/internal/handlers/message_handler.go` | 约 2000 行 | 消息发送、翻译、转发、媒体、可靠性逻辑混杂 |
| `backend/internal/handlers/setting_handler.go` | 约 2300 行 | 系统配置、第三方接口、后台设置混杂 |

影响：

- 改一个功能容易误伤旁边逻辑。
- 很多逻辑只能通过接口测，单元测试成本高。
- 权限判断、用户解析、群成员解析容易重复实现。
- 新人或后续维护时定位成本高。

### 2.2 权限逻辑分散

群主、管理员、成员、禁言、入群审核、频道权限等逻辑会出现在多个 handler 中。风险是：

- A 接口校验了权限，B 接口漏掉类似校验。
- 同一个权限字段在不同接口解释不一致。
- 后续接 Telegram/微信级别群管理能力时，扩展成本会升高。

### 2.3 数据查询和响应组装耦合

一些接口里同时做：

- 解析当前用户。
- 查询目标对象。
- 查权限。
- 查关联数据。
- 拼装 JSON 响应。

这种写法短期快，长期会导致：

- 同类查询无法复用。
- 查询优化难做。
- 数据返回结构变化时影响范围不清楚。

### 2.4 数据库迁移和索引需要治理

当前后端有 `AutoMigrate`，适合开发期，但正式运营后需要更明确的迁移脚本和回滚策略。

重点关注表：

- `users`
- `contacts`
- `chats`
- `chat_members`
- `chat_admin_permissions`
- `messages`
- `user_chats`
- `join_requests`
- `system_settings`

高频查询需要补充或复核联合索引，例如：

- `chat_members(chat_id, user_id)`
- `chat_members(user_id, chat_id)`
- `contacts(user_id, contact_user_id, status)`
- `messages(chat_id, seq)`
- `messages(chat_id, created_at)`
- `user_chats(user_id, sort_time)`
- `join_requests(chat_id, status, created_at)`

### 2.5 可观测性不足

目前接口能跑，但线上排查需要更完整的链路信息：

- 慢接口日志。
- 慢 SQL 日志。
- 关键业务审计日志。
- WebSocket 在线数、断连数、重连数。
- 消息发送成功率、推送成功率。
- 第三方接口耗时和错误率。

### 2.6 测试覆盖还不均衡

项目已经有一些 handler/service 测试，这是好基础。但核心业务还需要补：

- 群权限测试。
- 消息发送/编辑/撤回/转发测试。
- 入群审核测试。
- 管理员权限边界测试。
- 钱包和支付状态流转测试。
- WebSocket 状态同步测试。

## 3. 优化原则

1. 不做一次性大重构，每次只拆一个业务边界。
2. 保持接口返回结构兼容，前端不需要无意义跟改。
3. 先拆高频、高风险模块，再做底层抽象。
4. 每次改完必须跑测试、重建本地 API、做接口回归。
5. 业务规则进入 service，HTTP 只留参数、响应和错误映射。
6. 权限判断集中化，避免每个 handler 自己写一套。

## 5. 第一阶段：低风险止血

周期：1-2 周

目标：先把最容易继续变乱的业务从 handler 拆出去，不改变接口行为。

### 5.1 用户关系服务

状态：已开始。

已完成方向：

- 把共同群聊、共同联系人、共同信息从 `user_handler.go` 抽到 `RelationshipService`。
- handler 只负责调用 service 和组装响应。
- 修正 UUID/数字 ID 解析边界。
- 避免 GORM 查询复用造成隐性状态污染。

后续补充：

- 最近互动时间。
- 共享媒体统计。
- 共同联系人分页。
- 共同群聊分页。

### 5.2 群权限服务

新增：

```text
backend/internal/services/chat_permission_service.go
```

需要集中处理：

- 是否群主。
- 是否管理员。
- 是否普通成员。
- 是否被禁言。
- 是否有指定管理员权限。
- 是否可邀请成员。
- 是否可删除消息。
- 是否可审核入群。
- 是否可修改群资料。
- 是否可转让群主。

推荐方法：

```go
CanManageChat(ctx, chatID, operatorID uint64) error
CanManageMembers(ctx, chatID, operatorID uint64) error
CanMuteMember(ctx, chatID, operatorID, targetUserID uint64) error
CanRemoveMember(ctx, chatID, operatorID, targetUserID uint64) error
CanTransferOwner(ctx, chatID, operatorID, targetUserID uint64) error
CanApproveJoinRequest(ctx, chatID, operatorID uint64) error
```

收益：

- 群管理接口统一权限口径。
- 后续做 Telegram 风格细分管理员权限更稳。
- 减少 handler 重复代码。

### 5.3 群成员服务

新增：

```text
backend/internal/services/chat_member_service.go
```

承接：

- 添加成员。
- 移除成员。
- 设置管理员。
- 更新管理员权限。
- 禁言/解除禁言。
- 群主转让。
- 成员列表和搜索。

收益：

- `chat_handler.go` 体积明显下降。
- 群设置、成员页、后台管理可以复用同一套逻辑。

### 5.4 入群审核服务

新增：

```text
backend/internal/services/join_request_service.go
```

承接：

- 创建入群申请。
- 审批通过。
- 审批拒绝。
- 审批列表。
- 重复申请去重。
- 审批通知。

需要补充状态：

```text
0 pending
1 approved
2 rejected
3 cancelled
4 expired
```

### 5.5 消息翻译和语音转文字服务

新增：

```text
backend/internal/services/message_translate_service.go
backend/internal/services/voice_transcribe_service.go
```

重点：

- 把 DeepSeek、本地模拟接口、后续第三方接口都封装成 provider。
- handler 不直接关心具体供应商。
- 后台设置只保存 provider 和配置。

推荐接口：

```go
type TextTranslator interface {
    Translate(ctx context.Context, req TranslateRequest) (TranslateResult, error)
}

type VoiceTranscriber interface {
    Transcribe(ctx context.Context, req TranscribeRequest) (TranscribeResult, error)
}
```

## 6. 第二阶段：稳定性和性能

周期：2-4 周

### 6.1 慢 SQL 和索引优化

要做：

- 打开 GORM 慢 SQL 日志。
- 统计高频接口 SQL。
- 对消息列表、会话列表、群成员、联系人、共同信息补索引。
- 给大表分页统一使用游标分页，减少深分页。

重点接口：

- 会话列表。
- 消息列表。
- 群成员列表。
- 全局搜索。
- 共同群聊/共同联系人。
- 媒体列表。

验收标准：

- 常用接口 P95 小于 300ms。
- 消息列表 P95 小于 500ms。
- 群成员 5000 人场景可分页稳定返回。

### 6.2 消息可靠性

要做：

- 发送消息统一进入 `MessageService`。
- 消息写 MySQL、Mongo、用户会话、WebSocket 推送的流程要有明确事务边界。
- 推送失败要进入重试队列。
- 客户端消息 ID 幂等。
- 消息 seq 生成逻辑集中化。

建议流程：

```text
客户端发送
  -> 校验权限/禁言
  -> 写消息主表
  -> 更新 user_chats
  -> 写离线/推送任务
  -> WebSocket 广播
  -> 返回服务端消息 ID 和 seq
```

### 6.3 WebSocket 状态治理

要做：

- 在线设备数统计。
- 用户多端连接管理。
- 心跳超时日志。
- 重连原因统计。
- 发送失败计数。
- 大群广播限流。

收益：

- 排查“消息没收到”会更快。
- 大群/频道能力更容易扩展。

### 6.4 后台设置缓存

系统设置、DeepSeek、本地接口、短信、支付、推送等配置读取频繁，建议：

- 数据库为准。
- Redis 或内存缓存。
- 后台修改后主动失效缓存。
- 关键配置启动时校验。

## 7. 第三阶段：工程化和上线治理

周期：4-8 周

### 7.1 数据库迁移替代纯 AutoMigrate

建议引入：

- `backend/migrations`
- 版本号 SQL 文件。
- 启动时只检查版本，不自动乱改生产表。
- 支持回滚脚本。

示例：

```text
backend/migrations/
  202606230001_create_chat_admin_permissions.up.sql
  202606230001_create_chat_admin_permissions.down.sql
  202606230002_add_message_translate_fields.up.sql
  202606230002_add_message_translate_fields.down.sql
```

### 7.2 统一错误码

现在很多接口主要返回中文 message。建议增加稳定错误码：

```json
{
  "code": 40301,
  "message": "无权限操作",
  "data": null
}
```

分类：

| 范围 | 类型 |
| --- | --- |
| 10000-19999 | 通用错误 |
| 20000-29999 | 用户/账号 |
| 30000-39999 | 联系人 |
| 40000-49999 | 群/频道 |
| 50000-59999 | 消息 |
| 60000-69999 | 钱包/支付 |
| 70000-79999 | 第三方服务 |

### 7.3 审计日志

高风险操作必须有审计：

- 群主转让。
- 管理员任免。
- 管理员权限变更。
- 成员移除。
- 全员禁言。
- 入群审核。
- 用户封禁。
- 钱包配置变更。
- 第三方接口密钥变更。

新增表建议：

```text
operation_audits
  id
  actor_user_id
  actor_admin_id
  target_type
  target_id
  action
  before_json
  after_json
  ip
  user_agent
  created_at
```

### 7.4 配置和密钥治理

要做：

- `.env` 管理本地配置。
- 生产环境密钥不进 Git。
- 后台敏感字段脱敏返回。
- DeepSeek、短信、支付、对象存储密钥加密存储。
- 增加配置连通性测试接口。

### 7.5 CI 检查

建议每次提交至少跑：

```bash
go test ./...
go vet ./...
gofmt -w
```

可选：

```bash
staticcheck ./...
golangci-lint run
```

## 8. 模块拆分优先级

### P0：立即做

## 9. 建议执行顺序

### 第 1 步：继续拆群权限

输出：

- `ChatPermissionService`
- 单元测试覆盖群主、管理员、普通成员、非成员。
- 所有群管理接口改为调用统一权限服务。

验收：

- 普通成员不能移除管理员。
- 管理员不能转让群主。
- 没有 `CanManageAdmins` 的管理员不能设置管理员。
- 群主拥有所有权限。

### 第 2 步：拆群成员和入群审核

输出：

- `ChatMemberService`
- `JoinRequestService`
- 群主转让、管理员设置、禁言、移除、审批都走 service。

验收：

- 接口返回结构不变。
- 前端群设置页无需大改。
- 后端测试覆盖主要权限边界。

### 第 3 步：拆消息 AI 能力

输出：

- `MessageTranslateService`
- `VoiceTranscribeService`
- `AIProviderConfigService`

验收：

- 后台可配置本地接口。
- DeepSeek 和本地 mock 可切换。
- 翻译失败不影响原消息展示。
- 语音转文字失败有清晰错误码。

### 第 4 步：补观测和审计

输出：

- 慢接口日志。
- 慢 SQL 日志。
- 群管理审计日志。
- 第三方接口调用日志。

验收：

- 能查到谁改了群管理员。
- 能查到某次翻译请求用了哪个 provider。
- 能查到消息发送失败发生在哪一步。

## 10. 接口和返回兼容原则

后端优化期间，默认不改前端返回字段。

允许新增字段：

```json
{
  "data": {
    "id": "xxx",
    "name": "xxx",
    "new_field": "允许新增"
  }
}
```

不允许随意改名：

```json
{
  "member_count": 10
}
```

不要改成：

```json
{
  "memberCount": 10
}
```

除非同步修改 iOS、Android、H5、Web、Mac、Windows。

## 12. 风险控制

### 风险 1：拆 service 时改坏接口

控制方式：

- 每次只拆一个业务边界。
- 保持响应字段不变。
- 用真实登录 token 调接口回归。

### 风险 2：权限逻辑改变导致线上行为变化

控制方式：

- 先写权限测试。
- 旧逻辑和新逻辑对照。
- 管理员/群主/普通成员/非成员都测。

### 风险 3：数据库迁移影响已有数据

控制方式：

- 先只加字段和索引。
- 不直接删除字段。
- migration 支持回滚。
- 生产迁移前备份。

### 风险 4：AI 第三方接口不稳定

控制方式：

- provider 超时控制。
- 失败降级。
- 本地 mock provider。
- 调用日志和错误统计。

## 13. 预期收益

完成 P0+P1 后，预期收益：

- `chat_handler.go` 体积下降 30%-50%。
- 群权限问题更容易测试和排查。
- DeepSeek/本地 AI 接口更容易切换。
- 后续新增群运营功能不用继续堆 handler。
- 核心接口回归成本下降。
- 线上问题定位速度明显提升。

完成 P2 后，预期收益：

- 消息可靠性提升。
- 大群/频道能力更稳。
- 支付、推送、AI 调用具备更完整的失败处理。
- 数据库升级更安全。
- 后端更适合长期迭代和商业化运营。

## 14. 下一步建议

下一步建议直接开发：

```text
ChatPermissionService
ChatMemberService
JoinRequestService
```

原因：

- 这是你现在群功能继续扩展的核心地基。
- 能直接降低权限漏洞风险。
- 也能把最大的 `chat_handler.go` 开始拆小。
- 和当前已经开发的群主转让、管理员、入群审核、禁言/移除、群权限开关完全贴合。
