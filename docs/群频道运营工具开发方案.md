# 群/频道运营工具开发方案

> 日期：2026-06-22  
> 范围：Flutter 客户端、H5、Go 后端、Vue 管理后台  
> 目标：补齐群聊和频道的运营治理能力，让群主、管理员、平台后台都能低成本管理成员、内容、入群、权限和频道发布。

## 1. 结论

当前系统已经具备群/频道的基础框架：群主、管理员、成员角色、入群审批、禁言、群公告、置顶消息、公开/私密、邀请链接、后台群/频道管理等能力已经有代码基础。

收益最大的新增方向不是重新做一套群功能，而是把“已有后端能力”补成完整产品闭环：

| 优先级 | 功能 | 价值 | 建议交付 |
| --- | --- | --- | --- |
| P0 | 群主转让用户侧 | 群主不能直接退出的问题已有提示，但用户侧缺少完整转让入口 | 1 个版本 |
| P0 | 管理员与权限细分 | 从“是否管理员”升级为“能管理什么” | 1 个版本 |
| P0 | 成员治理 | 移除、禁言、黑名单、踢出后禁止再入 | 1 个版本 |
| P0 | 入群审批工作台 | 群主/管理员集中处理申请，减少漏处理 | 1 个版本 |
| P0 | 群权限开关补齐 | 谁能发消息、发媒体、发链接、邀请、改资料、置顶 | 1 个版本 |
| P1 | 邀请链接高级管理 | 多邀请链接、过期、人数限制、撤销、审批 | 2 个版本 |
| P1 | 群运营日志 | 谁改了设置、踢了谁、禁言了谁、审批了谁 | 2 个版本 |
| P1 | 频道发布工具 | 定时发布、静默发布、置顶、评论区/讨论群 | 2-3 个版本 |
| P1 | 统计看板 | 新增成员、留存、发言人数、频道阅读/转发 | 2-3 个版本 |
| P2 | 关键词/防刷屏 | 自动治理垃圾消息、广告、刷屏 | 3 个版本后 |
| P2 | 话题/论坛模式 | 类 Telegram Topics，适合大群分区讨论 | 3 个版本后 |

建议先做 P0。P0 做完后，系统会从“能建群”升级到“能运营群”，对商业化、社群留存、客服群、频道内容分发的收益最大。

## 3. 对标差距

### 3.1 对标 Telegram

Telegram 的群/频道运营能力更偏“大规模公开社区”和“内容分发”。核心差距如下：

| 模块 | Telegram 核心能力 | 当前系统状态 | 建议 |
| --- | --- | --- | --- |
| 角色 | Owner、Admin、Member/Subscriber | 已有 owner/admin/member 基础角色 | 保留现有角色，补权限细分 |
| 管理员权限 | 改资料、发频道消息、编辑消息、删消息、封禁、邀请、置顶、添加管理员等 | 当前只有粗粒度管理员 | P0 做权限表 |
| 邀请链接 | 多链接、撤销、过期、人数限制、审批 | 当前单 `invite_link` | P1 做多链接 |
| 加入审批 | 群/频道可开启审批 | 已有 `join_approval` 和 `join_requests` | P0 补 UI 工作台 |
| 频道 | 频道主/管理员发帖，订阅者只读 | 当前频道默认只有管理员发言 | P1 补发布工具 |
| 频道互动 | 评论、讨论群、频道私信 | 当前缺少 | P1/P2 做讨论群 |
| 内容运营 | 定时发布、静默发布、置顶、编辑 | 当前部分有置顶，缺定时/静默 | P1 做 |
| 统计 | 频道/超级群统计 | 当前后台统计较基础 | P1 做群/频道数据看板 |
| 治理 | 管理日志、慢速模式、封禁/限制权限 | 当前禁言基础版 | P1/P2 做慢速和日志 |
| 话题 | 大群 Topics/Forums | 当前缺少 | P2 做 |

### 3.2 对标微信

微信的群能力更偏“熟人社交”和“低学习成本”。核心差距如下：

| 模块 | 微信常见体验 | 当前系统状态 | 建议 |
| --- | --- | --- | --- |
| 群主转让 | 群主管理权转让 | 后台已有，用户侧缺入口 | P0 |
| 群管理员 | 群主可设置管理员 | 后端已有角色，UI 需补齐 | P0 |
| 入群确认 | 进群需群主/管理员确认 | 后端已有，UI 需补齐 | P0 |
| 仅管理员改群名 | 群资料修改权限 | 部分字段已有，需细分 | P0 |
| 群公告 | 公告发布/查看 | 已有公告 API | 补移动端入口和权限 |
| 移出成员 | 群主/管理员移人 | API 已有 | 补 UI 权限和确认 |
| 我在本群昵称 | 成员群昵称 | 字段已有 | 补编辑入口 |
| 群备注 | 个人侧给群设置备注 | 当前不完整 | P1 |
| 保存到通讯录 | 群保存/不保存 | 当前可用会话列表替代，不完整 | P1 |
| 清空聊天记录 | 本端清空 | 已有 clear API | 补入口一致性 |
| 群二维码/邀请 | 二维码、链接分享 | 当前单邀请链接 | P1 增强 |

微信方向建议优先做“简单、稳定、熟悉”的群设置体验；Telegram 方向建议放在频道、公开社群和运营后台。

## 4. 产品目标状态

### 4.1 群聊目标

群聊面向多人互动，目标是“可控地讨论”。

核心能力：

1. 群主可转让群主。
2. 群主可设置/取消管理员。
3. 群主可给管理员分配具体权限。
4. 管理员可按权限审核入群、移除成员、禁言、发公告、置顶消息。
5. 群可设置谁能发消息、发媒体、发链接、邀请成员、改群资料。
6. 入群方式支持公开加入、邀请链接、二维码、审批加入。
7. 支持踢出并加入黑名单，防止反复进群。
8. 支持运营日志，方便追责和回滚。

### 4.2 频道目标

频道面向内容分发，目标是“可管理地发布”。

核心能力：

1. 频道主可转让频道主。
2. 频道主可设置管理员，并指定发布、编辑、删除、查看统计等权限。
3. 订阅者默认只读。
4. 支持频道公告式发布、置顶、静默发布、定时发布。
5. 支持评论区或绑定讨论群。
6. 支持频道数据统计：订阅增长、阅读、转发、互动。
7. 支持频道入群审批、邀请链接高级管理。

### 6.2 群/频道黑名单表

```sql
CREATE TABLE chat_banned_members (
  id BIGINT UNSIGNED PRIMARY KEY AUTO_INCREMENT,
  chat_id BIGINT UNSIGNED NOT NULL,
  user_id BIGINT UNSIGNED NOT NULL,
  operator_id BIGINT UNSIGNED NOT NULL DEFAULT 0,
  reason VARCHAR(500) NOT NULL DEFAULT '',
  banned_until DATETIME NULL,
  created_at DATETIME NOT NULL,
  updated_at DATETIME NOT NULL,
  deleted_at DATETIME NULL,
  UNIQUE KEY uk_chat_user_active (chat_id, user_id, deleted_at),
  KEY idx_chat_id (chat_id),
  KEY idx_user_id (user_id)

```

说明：

- `banned_until` 为空表示永久禁止加入。
- 被移出但不拉黑，只删除 `chat_members`。
- 被拉黑时写入 `chat_banned_members`，再次通过链接/二维码/邀请加入时要拦截。

## 7. 后端 API 方案

### 7.1 群主/频道主转让

新增用户侧 API：

```http
PUT /api/v1/chat/:id/owner
```

请求：

```json
{
  "user_id": "new-owner-user-uuid"
}
```

权限：

- 当前用户必须是 `role = 2`。
- 目标用户必须是当前群/频道成员。
- 目标用户不能是已拉黑成员。
- 群/频道不能处于封禁或解散状态。

事务：

1. 锁定 `chats`。
2. 锁定当前 owner 成员记录和目标成员记录。
3. 更新 `chats.owner_id = target_user.id`。
4. 当前 owner `role` 从 2 降为 1，目标成员 `role` 升为 2。
5. 写 `chat_admin_logs.transfer_owner`。
6. 广播 `chat_owner_transferred`。

```json
  "owner_id": "new-owner-user-uuid"
}
```

- Flutter 和 H5 都使用用户侧 API。

## 11. 权限校验规则

### 11.1 通用规则

1. Owner 永远拥有全部权限。
2. Admin 只能执行自己拥有的权限。
3. Admin 不能操作 Owner。
4. Admin 操作另一个 Admin 时，需要 `can_manage_admins`，且不能提升超过自己的权限。
5. 普通成员不能执行管理操作。
6. 后台管理员操作不受群内角色限制，但必须写后台操作日志。

### 11.2 角色高低

```text
owner(2) > admin(1) > member(0)
```

执行成员操作时：

- 当前操作者角色必须大于目标角色。
- Owner 可以操作所有非 Owner。
- Admin 默认只能操作 Member。
- 如果允许 Admin 管理 Admin，需要额外配置并谨慎开放。

### 11.3 发消息校验

群聊：

1. 群封禁/解散时禁止发送。
2. 成员不存在时禁止发送。
3. 成员被禁言且未到期时禁止发送。
4. 群全局关闭 `can_send_message` 时，普通成员禁止发送。
5. 媒体、链接分别检查 `can_send_media`、`can_send_links`。
6. 慢速模式开启时检查上次发言时间。

频道：

1. 频道主可发。
2. 管理员需要 `can_post_messages`。
3. 普通订阅者默认不能发。
4. 如果频道开启评论，评论走讨论群或评论线程，不直接进入频道主消息流。

## 12. WebSocket 事件

新增或规范事件：

| 事件 | 触发场景 | 接收者 |
| --- | --- | --- |
| `chat_owner_transferred` | 群主/频道主转让 | 全体成员 |
| `chat_member_role_changed` | 设置/取消管理员 | 全体成员 |
| `chat_admin_permissions_changed` | 管理员权限变化 | 目标管理员、Owner |
| `chat_member_muted` | 禁言成员 | 目标成员、管理员 |
| `chat_member_unmuted` | 解除禁言 | 目标成员、管理员 |
| `chat_member_removed` | 移除成员 | 被移除成员、剩余成员 |
| `chat_member_banned` | 拉黑成员 | 管理员 |
| `chat_permissions_changed` | 群权限变化 | 全体成员 |
| `chat_join_request_created` | 新入群申请 | 有审批权限的管理员 |
| `chat_join_request_reviewed` | 申请被审批 | 申请人、管理员 |
| `chat_invite_link_changed` | 邀请链接变化 | 管理员 |
| `chat_admin_log_created` | 新管理日志 | 管理员 |

客户端收到事件后：

- 刷新当前群资料。
- 刷新成员列表。
- 刷新我的权限缓存。
- 如果自己被移除，退出当前聊天页并删除本地会话。
- 如果自己被禁言，输入框立即变为禁言状态。

## 15. 兼容与迁移

### 15.1 数据迁移

上线步骤：

1. 新增表，不影响旧逻辑。
2. 为所有现有 `role = 1` 的管理员生成默认权限。
3. `role = 2` 不需要写权限表，服务端直接视为全部权限。
4. 当前 `chats.invite_link` 保留。
5. 多邀请链接上线后，把旧 `invite_link` 写入 `chat_invite_links` 作为默认链接。

默认权限 SQL 思路：

```sql
INSERT INTO chat_admin_permissions (
  chat_id,
  user_id,
  can_delete_messages,
  can_ban_users,
  can_mute_users,
  can_invite_users,
  can_manage_join_requests,
  can_pin_messages,
  can_manage_invite_links,
  can_view_stats,
  created_at,
  updated_at
)
SELECT
  chat_id,
  user_id,
  TRUE,
  TRUE,
  TRUE,
  TRUE,
  TRUE,
  TRUE,
  TRUE,
  TRUE,
  NOW(),
  NOW()
FROM chat_members
WHERE role = 1;
```

### 15.2 老客户端兼容

老客户端不知道权限细分时：

- 服务端必须拦截无权限操作。
- 老客户端可继续显示“管理员”，但具体操作失败时显示服务端错误。
- 新增接口不破坏旧接口响应字段。
- `role` 数值不变，避免客户端角色错乱。

### 15.3 灰度开关

建议后台系统设置增加：

| key | 默认 | 说明 |
| --- | --- | --- |
| `group_admin_permissions_enabled` | false | 是否启用权限细分 |
| `group_owner_transfer_enabled` | true | 是否允许用户侧转让群主 |
| `group_ban_member_enabled` | true | 是否启用群黑名单 |
| `group_invite_links_v2_enabled` | false | 是否启用多邀请链接 |
| `channel_scheduled_post_enabled` | false | 是否启用频道定时发布 |

## 16. 风险点

| 风险 | 影响 | 处理 |
| --- | --- | --- |
| 角色映射不一致 | 客户端显示错权限 | 固定后端 role 0/1/2，不改语义 |
| 转让群主并发 | 出现两个群主 | 事务锁定 `chats` 和成员记录 |
| 管理员越权 | 普通管理员踢管理员/群主 | 服务端统一权限中间层 |
| 老客户端绕过 UI | 无权限操作仍可请求 API | 服务端强校验 |
| 黑名单和成员表不一致 | 被拉黑仍可入群 | 所有加入入口统一检查 |
| 多邀请链接兼容旧链接 | 老二维码失效 | 保留旧字段并迁移为默认链接 |
| WebSocket 事件遗漏 | 多端状态不同步 | 操作成功后统一广播并提供拉取兜底 |

## 17. 推荐落地顺序

最建议按下面顺序开工：

1. 后端抽 `ChatPermissionService`，集中判断 owner/admin/权限。
2. 做用户侧群主转让 API，复用后台转让逻辑。
3. 新增管理员权限表和我的权限 API。
4. Flutter 群资料页补群主转让、管理员权限、入群审批。
5. H5 同步补群主转让和权限弹窗。
6. 后台详情页补管理日志和权限编辑。
7. 新增黑名单和移出并拉黑。
8. 做多邀请链接。
9. 做频道定时/静默发布。
10. 做频道/群运营统计。
