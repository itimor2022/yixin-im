# Android 消息保活与锁屏收消息平衡方案

## 1. 方案结论

考虑性能、发热、耗电和 Android 系统限制后，最稳的方案不是让 WebSocket 在后台永久在线，而是采用：

```text
前台实时 WebSocket
短后台轻量保活
长锁屏切换系统推送
唤醒后离线消息补偿
后台诊断定位问题
```

这套方案的核心原则是：

- **实时性**：用户正在使用 App 或刚锁屏时，尽量保持 WebSocket 秒级收消息。
- **省电**：后台时间变长后降低心跳和重连频率，不做无限硬保活。
- **稳定性**：长时间锁屏、深度休眠、进程被回收后，依赖厂商推送、FCM、APNs 兜底。
- **不漏消息**：App 被唤醒、用户点通知、网络恢复、WebSocket 重连成功后，立即补拉离线消息。
- **可定位**：管理后台能看到设备 token、推送通道、最后推送结果和失败原因。

一句话口径：

> 短后台尽量实时，长后台靠系统推送，回来后补齐消息。这是性能、发热、耗电和系统限制之间最平衡的方案。

## 2. 为什么不建议永久硬保活

单纯提高后台心跳频率、频繁重连、强行维持 WebSocket，看起来能提高短时间在线率，但长期会带来问题：

- 更耗电，锁屏一晚容易明显掉电。
- 更容易发热，弱网下频繁重连尤其明显。
- 更容易被国产 ROM 判定为高耗电应用，从而杀进程或限制网络。
- Android 12+ 限制后台启动前台服务。
- Android 15 对 `dataSync` 类型前台服务存在累计运行时长限制。
- 用户关闭通知、开启极限省电、强行停止 App 后，代码无法绕过系统策略。

因此不建议把“WebSocket 永久在线”作为目标。真正可交付的目标应该是：

- 在线时快。
- 后台时省。
- 系统休眠时靠推送。
- 恢复后不漏。

## 3. 当前项目基础

项目已经有较好的基础，可以在现有代码上加固：

- `lib/core/services/background_service.dart`
  - Android 前台服务。
  - 后台 keepAlive。
  - 服务守护检查。
  - 前台服务通知更新。

- `lib/core/services/api/websocket_service.dart`
  - WebSocket 连接、ping/pong、断线重连。
  - App 生命周期感知。
  - 后台 keepAlive 触发后检查连接。
  - 网络恢复后重连。

- `lib/core/services/push_notification_service.dart`
  - FCM token 获取和上报。
  - Android 厂商推送 token 桥接。
  - 厂商通道优先，失败后回退 FCM。

- `android/app/src/main/kotlin/com/genericim/app/MainActivity.kt`
  - 华为、小米、OPPO 推送 SDK 可用性检测。
  - 厂商 token 请求桥接。
  - Android 13+ 通知权限请求。

- `backend/internal/services/push_service.go`
  - APNs、FCM、HMS、小米、OPPO、WebPush 发送能力。
  - 新消息推送。
  - 来电推送。
  - 推送错误处理。

- `backend/internal/services/push_channel.go`
  - 推送通道归一化。

方案重点不是从零做保活，而是把现有能力调整成“省电优先、推送兜底、补偿同步”的可靠链路。

## 4. 推荐运行策略

### 4.1 前台模式

适用场景：

- 用户正在聊天。
- App 在前台。
- 通话、会议、发送文件等实时交互场景。

策略：

- WebSocket 保持连接。
- 正常 ping/pong 心跳。
- 消息通过 WebSocket 实时到达。
- 断线后快速重连。
- 网络恢复后立即重连。

建议参数：

| 项目 | 建议 |
| --- | --- |
| WebSocket 心跳 | 20-30 秒 |
| pong 超时 | 8-15 秒 |
| 快速重连 | 允许 |
| 离线同步 | WebSocket 重连成功后触发 |

### 4.2 短后台模式

适用场景：

- 用户刚切到后台。
- 刚锁屏。
- 短时间没有操作。

目标：

- 尽量保持实时消息。
- 控制耗电。
- 不让弱网重连造成明显发热。

建议进入条件：

- App 进入后台后的 0-5 分钟。

策略：

- 继续保留前台服务。
- WebSocket 继续保持。
- 后台心跳降低到 30-60 秒。
- pong 超时后允许重连，但必须做节流。
- 网络不可用时不要持续重连，等待网络恢复事件。

建议参数：

| 项目 | 建议 |
| --- | --- |
| 后台 keepAlive | 30-60 秒 |
| WebSocket 后台 ping | 30-60 秒 |
| 重连退避 | 5 秒、15 秒、30 秒、60 秒递增 |
| 最大连续快速重连 | 3 次 |
| 弱网持续失败 | 进入低频等待 |

### 4.3 长后台省电模式

适用场景：

- 锁屏时间较长。
- App 后台超过 5-15 分钟。
- 系统进入 Doze 或厂商省电策略。

目标：

- 不再强求 WebSocket 永久在线。
- 降低耗电和发热。
- 避免被 ROM 判定为高耗电。
- 主要依赖系统推送收通知。

建议进入条件：

- App 后台超过 5-15 分钟。
- WebSocket 多次失败。
- 系统网络不可用或持续超时。

策略：

- 降低 WebSocket 心跳频率，或允许连接自然断开。
- 不做高频重连。
- 前台服务只做低频状态守护。
- 新消息主要通过厂商推送、FCM、APNs 到达。
- App 被唤醒后立即补拉离线消息。

建议参数：

| 项目 | 建议 |
| --- | --- |
| 长后台 keepAlive | 2-5 分钟 |
| WebSocket 重连 | 低频尝试或暂停 |
| 推送 | 作为主要通知通道 |
| 离线同步 | resumed、通知点击、重连成功时触发 |

### 4.4 深度休眠和进程回收模式

适用场景：

- 长时间锁屏。
- Doze 深度休眠。
- 国产 ROM 冻结后台网络。
- App 进程被系统回收。
- 用户清理后台。

策略：

- 不依赖 WebSocket。
- 不承诺后台服务一定活着。
- 使用厂商推送、FCM、APNs 兜底。
- 通知点击后恢复 App，并同步离线消息。

推送通道优先级：

| 设备 | 首选通道 | 兜底通道 |
| --- | --- | --- |
| 华为/荣耀 | HMS Push | FCM |
| 小米/Redmi | MiPush | FCM |
| OPPO/realme/一加部分机型 | OPPO Push | FCM |
| Google 服务可用 Android | FCM | 无 |
| iOS | APNs | 无 |

## 5. 两种用户模式

为了兼顾普通用户和重度在线用户，建议提供两个模式。

### 5.1 默认省电模式

默认给所有用户使用。

特点：

- 前台实时。
- 短后台轻量保活。
- 长后台主要靠推送。
- 重连退避更保守。
- 耗电和发热较低。

适合：

- 普通聊天用户。
- 大多数客户交付场景。
- 对续航敏感的用户。

建议默认开启。

### 5.2 增强保活模式

作为可选项，给有强在线需求的用户。

特点：

- 后台心跳更积极。
- WebSocket 尝试维持更久。
- 重连策略更激进。
- 需要用户开启自启动、电池无限制、通知权限。
- 会增加耗电和发热。

适合：

- 客服账号。
- 运营账号。
- 高频消息用户。
- 需要尽量实时接来电的用户。

必须提示：

> 增强保活会增加电量消耗和后台运行时间，仍受 Android 系统和厂商省电策略限制，不能保证永久在线。

建议参数：

| 项目 | 默认省电模式 | 增强保活模式 |
| --- | --- | --- |
| 短后台心跳 | 30-60 秒 | 20-30 秒 |
| 长后台守护 | 2-5 分钟 | 60-120 秒 |
| 快速重连次数 | 3 次 | 5 次 |
| 长后台是否强求 WS | 否 | 尽量维持 |
| 主要兜底 | 厂商推送 | 厂商推送 + 更积极保活 |
| 耗电 | 低 | 中高 |

## 6. 具体实施项

### 6.1 客户端保活策略调整

需要调整 `BackgroundService` 和 `WebSocketService` 的协作方式：

- 记录 App 进入后台的时间。
- 根据后台时长切换策略：
  - 0-5 分钟：短后台模式。
  - 5-15 分钟后：长后台省电模式。
  - 用户开启增强保活：延长短后台策略时间。
- 后台 keepAlive 不直接无脑重连，先判断：
  - 当前是否有 token。
  - 网络是否可用。
  - 最近是否刚重连失败。
  - 最近是否刚收到 pong。
  - 是否处于长后台省电模式。
- 弱网或服务端不可达时进入退避。
- WebSocket 重连成功后触发离线同步。

### 6.2 前台服务通知修复

当前前台服务通知文案存在中文编码异常，需要修复。

建议文案：

- 无未读：
  - 标题：通用IM
  - 内容：后台消息服务运行中
- 有未读：
  - 标题：通用IM
  - 内容：你有 N 条未读消息
- 增强保活开启：
  - 内容：增强保活运行中，可能增加耗电

要求：

- 通知必须稳定显示。
- Android 8+ 使用固定通知渠道。
- Android 13+ 未授权通知时，引导用户授权。

### 6.3 推送兜底生产化

长时间锁屏收消息的核心是推送，不是保活。

需要完成：

- FCM 生产配置。
- HMS 生产配置。
- 小米推送生产配置。
- OPPO 推送生产配置。
- APNs 生产配置。
- 真机验证 token 获取、上报、推送送达。
- 管理后台展示设备推送状态。

要求：

- 厂商 SDK 可用且配置完整时，使用厂商 token。
- 厂商 token 获取失败时，回退 FCM。
- token 变化后立即上报。
- 后端按 `push_channel` 精准发送。
- 来电推送使用高优先级消息。

### 6.4 离线消息补偿同步

不漏消息要靠补偿同步兜底。

触发时机：

- App resumed。
- WebSocket reconnected。
- 用户点击通知。
- 网络恢复。
- 登录成功。

同步要求：

- 按会话增量拉取。
- 按 messageId 去重。
- 未读数最终一致。
- 通知点击进入会话前，确保目标会话消息已同步。

### 6.5 权限引导页

新增“消息通知保障”页面。

必须包含：

- 通知权限检测。
- 打开通知设置。
- 打开应用详情页。
- 自启动引导。
- 电池无限制引导。
- 锁屏通知引导。
- 后台弹出界面/全屏来电权限引导。

按品牌给不同说明：

- 华为/荣耀：应用启动管理、电池优化、通知管理。
- 小米/Redmi：自启动、省电策略、锁屏通知、通知管理。
- OPPO/realme/一加：自启动、耗电保护、通知权限。
- vivo/iQOO：后台高耗电、自启动、通知管理。
- 三星/Pixel/其他：电池优化、通知权限。

### 6.6 后台诊断能力

管理后台需要能定位“锁屏收不到消息”的原因。

建议展示：

- 设备 ID。
- 设备品牌和型号。
- Android 版本。
- App 版本。
- push channel。
- token 是否存在。
- token 最后上报时间。
- 设备最后活跃时间。
- 最近一次推送时间。
- 最近一次推送结果。
- 最近一次失败原因。
- 用户是否关闭推送设置。

建议功能：

- 测试推送。
- 推送配置自检。
- 厂商错误码展示。
- token 脱敏日志。

## 7. 推荐分阶段实施

### 第一阶段：省电保活策略

目标：

- 把当前保活从“尽量一直跑”调整为“分层策略”。

任务：

- 增加后台时长记录。
- 增加短后台和长后台模式。
- 后台心跳改为可配置。
- WebSocket 重连增加退避和节流。
- 修复前台服务通知中文文案。
- WebSocket 重连成功后触发离线同步。

验收：

- 前台收消息秒级。
- 锁屏 5-10 分钟尽量保持 WebSocket 可用。
- 弱网下不会持续高频重连。
- 长后台时耗电明显低于 15 秒固定心跳方案。

### 第二阶段：推送兜底

目标：

- 长时间锁屏后仍能收到系统通知。

任务：

- 补齐 FCM/HMS/小米/OPPO/APNs 生产参数。
- 执行厂商推送预检。
- 真机验证 token 上报。
- 后端测试推送。
- 来电推送高优先级验证。

验收：

- 华为、小米、OPPO、Google 服务可用 Android 至少各一台真机验证。
- 锁屏 30 分钟和 2 小时后，服务端推送能展示通知。
- App 被系统回收后，推送仍能到达，具体以 ROM 表现记录为准。

### 第三阶段：权限引导和增强保活

目标：

- 提升国产 ROM 到达率。
- 给重度用户可选增强保活。

任务：

- 增加“消息通知保障”页面。
- 增加默认省电模式和增强保活模式。
- 增强保活模式增加耗电提示。
- 按品牌展示设置引导。

验收：

- Android 13+ 能引导通知授权。
- 用户能打开系统设置。
- 增强保活开启后，后台策略按增强参数运行。

### 第四阶段：后台诊断

目标：

- 客户反馈收不到消息时能定位原因。

任务：

- 用户设备列表展示推送状态。
- 增加测试推送按钮。
- 记录最近推送结果。
- 展示失败原因。

验收：

- 能判断 token 未绑定、通道错误、配置缺失、厂商返回失败等问题。

## 8. 测试方案

### 8.1 性能和耗电测试

测试对比：

- 无保活。
- 固定 15 秒心跳。
- 默认省电模式。
- 增强保活模式。

记录指标：

- 1 小时锁屏耗电。
- 2 小时锁屏耗电。
- 设备温度变化。
- 后台网络请求次数。
- WebSocket 重连次数。
- 推送到达时间。
- 打开 App 后离线消息是否补齐。

目标：

- 默认省电模式耗电明显低于固定 15 秒心跳。
- 弱网场景下不会持续发热。
- 消息最终不漏。

### 8.2 锁屏收消息测试

每个品牌至少测：

- 锁屏 5 分钟。
- 锁屏 10 分钟。
- 锁屏 30 分钟。
- 锁屏 2 小时。
- 开启电池无限制。
- 未开启电池无限制。
- 默认省电模式。
- 增强保活模式。

记录：

- 手机品牌和型号。
- Android 版本。
- App 版本。
- 是否允许通知。
- 是否允许自启动。
- 是否电池无限制。
- push channel。
- token 是否上报。
- 消息发送时间。
- 通知到达时间。
- 点通知后是否进入正确会话。
- 离线消息是否补齐。

### 8.3 极端场景测试

- 从最近任务划掉 App。
- 系统设置强行停止 App。
- 低电量模式。
- 极限省电模式。
- 弱网。
- 网络断开后恢复。

说明：

- 强行停止 App 后，很多系统会阻止后台行为，不能承诺 100% 可达。
- 极限省电模式下，不承诺实时收消息。
- 用户关闭通知权限后，不能展示系统通知。

## 9. 对外承诺口径

建议对客户说明：

> 系统采用“WebSocket 实时消息 + Android 轻量保活 + 厂商推送兜底 + 离线消息补偿同步”的组合方案。App 前台和短时间后台尽量实时收消息；长时间锁屏或系统回收进程后，主要通过华为、小米、OPPO、FCM、APNs 等系统推送保障通知到达；用户打开 App 或点击通知后会自动补齐离线消息。该方案兼顾实时性、续航、发热和 Android 系统限制。

可以承诺：

- 前台消息实时。
- 短后台尽量实时。
- 长后台走系统推送兜底。
- 唤醒后补齐离线消息。
- 提供通知权限和电池设置引导。
- 提供后台诊断定位问题。

不建议承诺：

- WebSocket 锁屏永久在线。
- 所有国产机都秒到。
- 不开通知权限也能收到通知。
- 不配厂商推送也能长锁屏稳定收消息。
- 用户强行停止 App 后仍 100% 收消息。
- 极限省电模式下仍实时收消息。

## 10. 不建议做的方案

以下做法短期看似“保活强”，长期不稳：

- 15 秒以内固定后台心跳长期运行。
- 弱网下无限快速重连。
- 长锁屏仍强行维持 WebSocket。
- 不接厂商推送，只靠前台服务。
- 不做离线消息补偿。
- 不提示用户开启通知权限和电池设置。
- 对客户承诺“永久在线”。

## 11. 推荐优先级

| 优先级 | 工作项 | 原因 |
| --- | --- | --- |
| P0 | 修复前台服务通知文案 | 当前通知中文异常，影响用户感知 |
| P0 | 增加默认省电模式策略 | 平衡实时性、耗电和发热 |
| P0 | WebSocket 重连退避和节流 | 避免弱网耗电和发热 |
| P0 | 重连/唤醒后离线同步 | 防止漏消息 |
| P1 | 厂商推送生产化 | 长锁屏收消息核心 |
| P1 | 通知权限和电池设置引导 | 国产 ROM 必需 |
| P1 | 管理后台推送诊断 | 客户问题可定位 |
| P2 | 增强保活模式 | 给客服和重度用户使用 |
| P2 | 耗电和长锁屏测试记录 | 形成交付验收证据 |

## 12. 最终推荐

最终推荐默认使用：

```text
默认省电模式：
前台 WebSocket 实时
后台 0-5 分钟轻量保活
后台 5-15 分钟后降低心跳和重连
长锁屏主要靠厂商推送
唤醒后立即补拉离线消息
```

对重度用户提供：

```text
增强保活模式：
更积极的后台心跳和重连
要求开启自启动、电池无限制、通知权限
明确提示会增加耗电和发热
仍然使用厂商推送兜底
```

这是当前 Android 生态下更实际、可交付、可解释的保活方案。
