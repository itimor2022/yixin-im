# 线上稳定性与核心体验优化开发方案

日期：2026-06-27

范围：OSS 配置优先级、上传链路检测、消息可靠性、后台监控、安全、推送离线、数据库性能、宝塔部署规范、安卓真机回归。

不包含：一键回滚能力。本轮按用户确认的 1、2、4、5、6、7、8、9、10 项推进。

## 1. 总目标

把当前系统从“功能可用”提升到“线上可诊断、消息可信、部署不易误伤、客户端核心体验稳定”的状态。

核心交付结果：

- 后台数据库配置成为 OSS/存储配置的唯一业务入口，部署环境变量只做初始化和兜底。
- 上传链路可自检，能明确当前走 local 还是 OSS，并能验证 URL 可访问。
- 消息发送、重连、补拉、离线推送形成闭环，降低漏消息和重复消息风险。
- 后台健康监控能看到 MySQL、MongoDB、Redis、OSS、WebSocket、上传、推送的状态。
- 安全基线覆盖后台登录、上传、CORS、敏感配置、限流。
- 数据库索引和分页策略覆盖高频查询。
- 宝塔 SSL 永远由宝塔管理，部署脚本不写证书和 HTTPS vhost。
- 每次发包前有安卓真机回归流程。

## 2. 开发原则

- 先做可观测和可验证，再做深层重构。
- 保持前端上传接口不变，App 不直连 OSS，不暴露 OSS 密钥。
- 服务端配置以数据库系统设置为准，脚本只负责初始化和兜底。
- 所有改动分阶段上线，每阶段有明确验收命令和回归清单。
- 线上脚本不得写 `ssl_certificate`、`listen 443`、`http2`、HTTPS 跳转。
- 修改 IM 消息链路时，优先保证兼容现有消息数据和旧客户端。

## 3. 阶段总览

| 阶段 | 优化项 | 优先级 | 建议周期 |
| --- | --- | --- | --- |
| Phase 1 | OSS 配置优先级、上传链路检测、宝塔部署规范 | P0 | 2-4 天 |
| Phase 2 | 消息可靠性、离线补拉、发送失败重试 | P0 | 1-2 周 |
| Phase 3 | 后台健康监控、安全基线、推送诊断 | P0/P1 | 1-2 周 |
| Phase 4 | 数据库性能和分页优化 | P1 | 1 周 |
| Phase 5 | 安卓真机回归自动化和发包门禁 | P1 | 3-5 天 |

### 3.1 P0 开发进度记录

日期：2026-06-27

已落地：

- 存储配置运行时优先级改为：数据库 `system_settings.cloud_storage` 优先，环境变量只作为无数据库配置时的兜底。
- 后台新增存储诊断接口：
  - `GET /api/v1/admin/storage/status`
  - `POST /api/v1/admin/storage/test-upload`
  - 兼容入口：`/api/v1/admin/settings/storage/status`、`/api/v1/admin/settings/storage/test-upload`
- 存储状态接口只返回密钥是否已配置，不返回 AccessKey Secret 等明文。
- 测试上传会写入 `uploads/health/YYYY/MM/DD/storage_health_*.txt`，并用 HTTP HEAD/GET 验证公开 URL。
- 线上预构建包和更新包脚本增加 SSL 指令扫描门禁，包内出现 `ssl_certificate`、`listen 443`、`http2`、`return 301 https` 会直接失败。
- 消息幂等和补拉已核对当前实现：
  - 后端 `SendMessageWithResult` 已按 `client_msg_id/msg_id` 查重，重复提交直接返回已存在消息。
  - Mongo 消息集合已有 `chat_id + msg_id`、`chat_id + seq` 唯一索引。
  - App 已在登录/启动/恢复/WS 重连后走 `syncMissedMessages`，当前聊天收到 seq 跳号会触发增量同步。
  - 本地消息窗口按 `msg_id` 和 `chat_id + seq` 去重合并。

已验证：

- `go test ./internal/config ./internal/services ./internal/handlers`
- `go test ./cmd/server`
- PowerShell 打包脚本语法解析
- 实际部署脚本和 Nginx 配置扫描无 SSL 托管指令命中

待真机验收：

- 后台配置 OSS 后，重启容器仍走数据库 OSS。
- 后台点击测试上传，OSS URL 返回 200。
- 安卓真机语音发送、外放播放、弱网重试。
- 双账号弱网/杀后台/重连补拉消息不丢、不重复。

- 系统健康详情接口读取时会补充即时快照，但 2 分钟内不会重复插入，避免频繁刷新后台造成快照暴涨。
- 新增后台健康趋势接口：`GET /api/v1/admin/system/health-trend?hours=24`，支持 1-168 小时范围查询，默认 24 小时。

- Android 推送 token 改为按厂商通道独立保存：同一设备的 `jpush/fcm/hms/xiaomi/oppo` token 不再互相覆盖。
- 用户级推送分发新增主/备通道候选排序：同一 Android 逻辑设备有多个真实厂商 token 时，优先尝试后台配置的主通道，失败后再尝试备用通道，避免跨厂商混用 token。
- 推送发送拆出同步投递 helper，失败会逐通道写入 `PushDeliveryLog`；通道配置不完整不再被记录为成功。
- 设备列表、登出清理和终止设备按逻辑设备 ID 合并厂商 token 记录，避免后台看到重复设备或残留 token。
- 私聊消息拉取/断线同步后会自动把对方消息持久化为 `delivered`，并向发送方广播送达回执；`read` 持久化后会同步失效消息窗口缓存，避免短时间读到旧状态。
- Flutter 客户端新增 `delivered/message_delivered` 回执处理，发送方本地消息可从已发送升级为已送达，已读状态不会被送达回执降级，旧客户端仍可按数值状态兼容展示。
- 新增 P3 安卓核心冒烟脚本：`scripts/p3_android_core_smoke.ps1`，覆盖后端健康、登录/注册、私聊文本、delivered/read 状态、语音上传下载、语音消息发送；接真机时可补启动截图和弱网恢复检查。
- 消息统计接口 `/api/v1/admin/stats/messages` 从最近 12 个月 `messages_YYYYMM` 分表和旧 `messages` 集合汇总，不再只读旧集合；`messages_today` 按本地日期 00:00 起算，避免中国时区被 `Truncate(24h)` 偏移。
- 消息类型统计兼容 Mongo 中的数值类型和字符串类型，文本、图片、视频、语音、文件之外的旧数据归入 `other`，避免后台统计空白或分类错乱。
- 消息集合运行时索引扩展到 `chat_id + created_at`、`chat_id + sender_id + seq + status`、`created_at + type`、文件名检索索引，支撑消息窗口、送达状态更新、统计和文件搜索。
- 新增 P3 索引脚本：`backend/scripts/p3_search_stats_indexes.sql`、`backend/scripts/p3_search_stats_mongo_indexes.js`，用于线上低峰期补齐 MySQL 和 MongoDB 搜索/统计索引。

## 5. Phase 1：OSS 配置优先级

### 5.1 当前问题

后端已经支持 `system_settings.cloud_storage` 和 yaml 存储配置，但部署脚本也可能传入存储环境变量。需要明确优先级，否则后台配置和服务器环境变量可能互相覆盖。

### 5.2 目标规则

最终优先级：

1. 数据库 `system_settings.cloud_storage`
2. 环境变量 `GENERIC_IM_STORAGE_*`
3. yaml `storage`
4. 默认 local

说明：

- 数据库是线上真实配置来源。
- 环境变量用于首次部署初始化、容器兜底、无数据库时启动。
- 后台保存 OSS 后，后续部署不应覆盖后台选择。

### 5.3 后端改动

文件：

- `backend/internal/services/object_storage.go`
- `backend/internal/config/config.go`
- `backend/internal/handlers/setting_handler.go`
- `backend/internal/services/object_storage_test.go`

任务：

- 调整 `LoadStorageForRuntime`，确保数据库配置优先。
- 保留 `GENERIC_IM_STORAGE_*` 对 yaml 的覆盖能力，但不能覆盖数据库非空配置。
- 后台系统设置展示当前运行配置时，明确标识来源：`database`、`env`、`yaml`。
- 后台保存 `cloud_storage` 时，校验 OSS 必填项。
- 对 demo/admin 权限保持密钥脱敏。

### 5.4 管理后台改动

目标：让管理员能直接在后台配置 OSS。

字段：

- 存储类型：local / aliyun / qiniu
- 本地访问域名
- 阿里云 Endpoint
- 阿里云 Bucket
- 阿里云 AccessKey ID
- 阿里云 AccessKey Secret
- 阿里云公开访问域名/CDN 域名
- 是否 HTTPS

交互要求：

- 切换 provider 时只展示对应字段。
- 密钥字段默认脱敏，保存时允许不改密钥。
- 增加“测试连接/测试上传”按钮，调用后端检测接口。

### 5.5 验收标准

- 后台保存 OSS 后，发语音返回 OSS URL。
- 重启 Docker 后仍然使用数据库 OSS 配置。
- `.env.bt` 写 local 时，不覆盖数据库 OSS。
- 删除数据库 `cloud_storage` 后，才回退到环境变量/yaml。

## 6. Phase 1：上传链路检测

### 6.1 目标

上线一个可诊断接口和脚本，明确当前上传链路状态。

### 6.2 后端接口

新增后台接口：

```http
GET /api/v1/admin/storage/status
POST /api/v1/admin/storage/test-upload
```

`GET /storage/status` 返回：

```json
{
  "provider": "aliyun",
  "source": "database",
  "public_base_url": "https://media.example.com",
  "bucket": "bucket-name",
  "endpoint": "oss-cn-hangzhou.aliyuncs.com",
  "local_base_url": "",
  "masked": true
}
```

`POST /storage/test-upload` 行为：

- 生成一个小文本文件或小音频测试对象。
- 走当前运行时存储配置上传。
- 返回 URL。
- 服务端用 HTTP HEAD/GET 验证 URL 可访问。
- 测试对象写入 `uploads/health/YYYY/MM/DD/`。

返回：

```json
{
  "ok": true,
  "provider": "aliyun",
  "url": "https://media.example.com/uploads/health/...",
  "http_status": 200,
  "duration_ms": 342
}
```

### 6.3 脚本

新增脚本：

```text
scripts/check-online-storage.sh
```

输入：

- `API_BASE=https://api.example.com`
- `ADMIN_TOKEN=...`

检查项：

- `/health`
- `/admin/storage/status`
- `/admin/storage/test-upload`
- 返回 URL HEAD 访问

### 6.4 验收标准

- local 模式能检测本地上传 URL。
- OSS 模式能检测 OSS URL。
- OSS 密钥错误时返回明确失败原因。
- Bucket 非公开读或 CDN 未配置时能提示 URL 不可访问。

## 7. Phase 2：消息可靠性

### 7.1 目标

解决弱网、重连、App 杀后台、重复点击、离线恢复导致的漏消息、重复消息、状态不一致。

### 7.2 服务端契约

确认或补齐字段：

- `client_msg_id`
- `msg_id`
- `chat_id`
- `seq`
- `sender_id`
- `server_created_at`
- `message_type`
- `content`

发送接口要求：

- `client_msg_id` 必填。
- 同一用户同一 `client_msg_id` 重复提交必须幂等。
- 服务端返回最终 `msg_id` 和 `seq`。

同步接口：

```http
GET /api/v1/messages/sync?chat_id={chat_id}&after_seq={seq}&limit=100
```

返回：

- `messages`
- `from_seq`
- `to_seq`
- `has_more`
- `server_time`

### 7.3 客户端改动

消息状态：

- `local_pending`
- `queued`
- `sending`
- `sent`
- `failed_retryable`
- `failed_final`
- `read`

客户端策略：

- HTTP 发送响应、WebSocket 推送、补拉结果按 `msg_id`、`client_msg_id`、`chat_id + seq` 去重。
- App 启动、登录成功、WebSocket 重连、前后台切换、点击推送进入聊天时触发补拉。
- 发送失败消息支持手动重试。
- 媒体消息重试时优先复用已上传 URL，避免重复上传大文件。

### 7.4 后端测试

新增测试：

- 重复 `client_msg_id` 只入库一次。
- 乱序 seq 补拉正确。
- 权限失败不进入自动重试。
- 媒体消息只保存一次内容。

### 7.5 客户端测试

真机/模拟器场景：

- 断网发送文字，恢复网络后重试。
- 断网发送语音，恢复网络后重试。
- App 杀后台后，另一个账号发送消息，重启后补拉。
- WebSocket 断开再连，消息不重复。

## 11. Phase 4：数据库性能

### 11.1 目标

高频列表和权限查询不依赖全表扫描，消息量增长后仍能稳定。

### 11.2 优先索引

重点表：

- `messages`
- `user_chats`
- `chat_members`
- `contacts`
- `moments`
- `transactions`
- `push_logs`
- `upload_logs`

建议索引：

```sql
CREATE INDEX idx_messages_chat_seq ON messages (chat_id, seq);
CREATE INDEX idx_messages_chat_created ON messages (chat_id, created_at, id);
CREATE INDEX idx_user_chats_user_pin_sort ON user_chats (user_id, is_pinned, sort_time, id);
CREATE INDEX idx_chat_members_user_chat ON chat_members (user_id, chat_id);
CREATE INDEX idx_chat_members_chat_role_joined ON chat_members (chat_id, role, joined_at, user_id);
CREATE INDEX idx_contacts_user_status ON contacts (user_id, status, contact_user_id);
CREATE INDEX idx_push_logs_user_created ON push_logs (user_id, created_at, id);
CREATE INDEX idx_upload_logs_user_created ON upload_logs (user_id, created_at, id);
```

实际 SQL 以当前模型字段为准，开发前必须先核对表结构和已有索引，避免重复索引。

### 11.3 分页策略

任务：

- 消息列表使用 `seq` 或 `created_at + id` 游标分页。
- 后台大列表避免深分页 `OFFSET`。
- 统计查询避免 `DATE(created_at)` 直接作用于索引列。

验收：

- 聊天列表、消息列表、成员列表、后台日志列表在 10 万级数据下响应稳定。
- 慢 SQL 日志中不再出现核心接口全表扫描。

## 12. Phase 5：宝塔部署规范

### 12.1 固定规则

扫描范围：

- `scripts/*.sh`

- 打包产物 `update.sh`
- 打包产物 README

- B 用户
