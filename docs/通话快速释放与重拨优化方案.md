# 通话快速释放与重拨优化方案

## 目标

解决用户在一对一语音/视频通话中“刚挂断又立刻重拨”时，客户端提示“通话未就绪”或被旧通话状态阻塞的问题。

核心原则：

- 后端成为通话状态的权威方。
- 挂断、取消、拒接、异常残留都必须快速进入终态。
- 用户主动挂断后应立即允许再次呼出。
- 已接通通话不能因为 2 秒网络抖动被误杀。
- 多后端实例部署时不能因为并发处理产生重复通话或状态乱序。

## 当前问题判断

现有链路里，客户端挂断后会依赖本地 RTC、WebSocket、CallKit/系统通话 UI、后端通话记录一起释放。任何一层释放慢或请求丢失，都可能导致后端仍看到 `calling` / `connected` 状态，下一次 `/call/create` 被拦截。

用户感知上表现为：

- 刚挂断后马上再打，提示通话未就绪。
- 实际已经没有通话 UI，但后端仍认为账号在通话中。
- 弱网、杀进程、快速点击挂断/重拨时更容易复现。

## 总体方案

不要只把清理定时器改短，而是增加“主动释放 + 快速兜底 + 并发锁 + 事件补偿”四层机制。

1. 主动释放：`/call/end`、`/call/cancel`、`/call/reject` 只要收到请求，就立刻把通话改为终态。
2. 快速兜底：后端定时清理服务用 500ms 到 1s 周期扫描短残留，2 秒内释放未接通残留。
3. 并发锁：创建、挂断、清理同一通话时使用 DB row lock 和可选 Redis lock，避免重复处理。
4. 事件补偿：后端终止旧通话后主动推送 `call_ended` / `call_cancelled` / `call_released`，客户端按 `call_id` 精准释放。

## P0：快速止血，保证挂断后可立即重拨

### 范围

P0 只解决最影响客户体验的问题：用户点挂断后，后端必须立即释放通话占用，并允许发起人继续呼出。

### 后端改造

1. 统一终态判断

新增或规范以下终态：

| 状态 | 含义 |
| --- | --- |
| `ended` | 已接通后正常结束 |
| `cancelled` | 主叫在未接通前取消 |
| `rejected` | 被叫拒接 |
| `missed` | 呼叫超时未接 |
| `failed` | RTC/后端异常导致失败 |

后端所有活跃判断只认：

- `calling`
- `connected`

其余状态一律不得阻塞新通话。

2. `/call/end` 幂等化

接口行为：

- 如果通话是 `calling`，调用 `/call/end` 也允许结束，按 `cancelled` 或 `ended` 规则收口。
- 如果通话是 `connected`，设置为 `ended`。
- 如果已经是终态，直接返回成功，不返回错误。
- 每次返回都带 `call_id`、`status`、`duration`、`released=true`。

3. `/call/cancel` 幂等化

接口行为：

- 只要主叫取消未接通通话，立即设置 `status=cancelled`。
- 如果已经终态，返回成功。
- 取消成功后主动通知被叫 `call_cancelled`。

4. `/call/create` 前置释放发起人的旧通话

创建新通话前：

- 锁住发起人相关的 `calling/connected` 通话。
- 对发起人自己的旧 `calling` 记录，直接置为 `cancelled`。
- 对发起人自己的旧 `connected` 记录，直接置为 `ended`，原因 `client_replaced`。
- 然后继续创建新通话。

注意：

- P0 只自动替换“发起人自己的旧通话”。
- 被叫方如果确实有新鲜 `calling/connected`，仍然返回“对方正在通话中”。
- 避免一个用户快速拨号时被自己的残留状态卡住。

5. 短残留清理

清理服务增加短残留规则：

- `calling` 超过 2 秒且没有任何近期更新，可释放为 `missed` 或 `cancelled_timeout`。
- `connected` 不按 2 秒释放，仍走心跳超时，避免误杀真实通话。

建议配置：

```env
CALL_RINGING_RELEASE_GRACE=2s
CALL_CLEANUP_INTERVAL=1s
CALL_CONNECTED_HEARTBEAT_TIMEOUT=8s
CALL_CREATE_REPLACE_CALLER_ACTIVE=true
```

### 客户端配合

P0 不强依赖客户端大改，但建议客户端做到：

- 挂断按钮立即调用 `/call/end`。
- 本地 UI 先退出通话页。
- 收到 `call_ended`、`call_cancelled`、`call_released` 时按 `call_id` 释放当前通话。
- 如果事件 `call_id` 不是当前通话，忽略，防止旧事件冲掉新通话。

### 验收标准

必须通过：

- A 呼 B，A 立刻挂断，1 秒内 A 再呼 B，创建成功。
- A 呼 B，B 未接，A 取消后立即再呼，创建成功。
- A 重复点击挂断两次，接口均成功，不报错。
- `/call/active` 在挂断后返回 `active=false`。
- 后端数据库不遗留发起人的旧 `calling/connected`。

### 建议测试

后端单元测试：

- `calling` 调 `/call/end` 后变终态。
- 终态重复 `/call/end` 返回成功。
- `/call/create` 自动替换发起人旧 `calling`。
- `/call/create` 自动结束发起人旧 `connected`。

本地模拟器测试：

- 两个账号登录。
- A 呼 B，A 挂断后立刻再呼。
- 截图、后端日志、数据库状态都要留证据。

## P1：后端权威状态机，覆盖异常和多实例

### 范围

P1 把 P0 的快速释放机制做成稳定通话状态机，覆盖弱网、杀进程、WebSocket 断开、多后端实例、重复事件等场景。

### 后端改造

1. 引入通话状态流转函数

所有接口不得散落更新状态，统一走函数：

```text
transitionCall(callID, action, actorID, reason)
```

动作包括：

- `create`
- `accept`
- `reject`
- `cancel`
- `end`
- `heartbeat_timeout`
- `ringing_timeout`
- `client_replaced`
- `admin_force_end`

函数负责：

- 校验状态是否允许流转。
- 终态幂等。
- 设置 `end_time`、`duration`、`end_reason`。
- 生成通知事件。
- 写入审计日志。

2. Redis active key

增加快速活跃索引：

```text
call:user:{user_id}:active = call_id
call:{call_id}:lock = locked
```

用途：

- `/call/create` 快速判断双方是否活跃。
- `/call/end` 成功后立即删除双方 active key。
- 清理服务可优先扫描 Redis active key，再回查 DB。

TTL 建议：

- `calling`：30 秒。
- `connected`：心跳续期，默认 15 秒。
- lock：5 到 10 秒。

3. 多实例并发锁

如果部署多个后端实例：

- 状态更新用 DB row lock 作为最终保护。
- Redis lock 作为快速互斥，减少并发冲突。
- Redis 不可用时降级 DB lock，不影响基本可用性。

4. 事件补偿机制

所有终态都发标准事件：

```json
{
  "type": "call_released",
  "data": {
    "call_id": 123,
    "status": "ended",
    "reason": "hangup",
    "duration": 12,
    "released_at": "2026-06-26T12:00:00Z"
  }
}
```

同时保留兼容事件：

- `call_ended`
- `call_cancelled`
- `call_rejected`

客户端新版本优先处理 `call_released`，旧版本仍可处理原事件。

5. 后端心跳策略

建议：

- `connected` 心跳每 3 秒一次。
- 超过 8 秒无心跳，后端标记 `ended`，原因 `heartbeat_timeout`。
- `calling` 阶段不要求 RTC 心跳，但要看 `start_time` 和取消/拒接事件。

### 客户端配合

- 通话页进入后开始心跳。
- App 退后台、断网、销毁通话页时尽量补发 `/call/end`。
- 收到 `call_released` 后，无论本地 RTC 状态如何，都先释放业务通话状态。
- 本地可保留 1 到 2 秒按钮防抖，但不能依赖防抖解决后端残留。

### 管理后台

通话记录列表增加：

- 当前状态。
- 结束原因。
- 最后心跳时间。
- 是否由清理服务释放。
- 是否由新通话替换释放。

管理员强制结束时复用同一状态机。

### 验收标准

必须通过：

- 客户端杀进程不发 `/call/end`，后端能在配置时间内释放残留。
- WebSocket 断开后，通话状态不会永久卡在 `connected`。
- 双后端实例并发调用 `/call/end`，只有一次有效状态更新，其余幂等成功。
- 旧通话释放事件不会影响新通话。
- 后台通话记录能看出结束原因。

## P2：可观测、压测和体验优化

### 范围

P2 做生产级可观测性、压测、防误杀、体验细节和运维工具，让问题可定位、可回放、可解释。

### 后端可观测

1. 指标

增加指标：

- `call_create_total`
- `call_end_total`
- `call_release_latency_ms`
- `call_stale_cleanup_total`
- `call_replaced_total`
- `call_heartbeat_timeout_total`
- `call_create_blocked_active_total`

关键看板：

- 平均挂断释放耗时。
- P95/P99 挂断释放耗时。
- 残留通话清理数量。
- 新通话被 active 状态阻塞次数。
- 被 `client_replaced` 自动释放次数。

2. 结构化日志

每次状态流转打印统一日志：

```text
call_id=123 action=end from=connected to=ended actor=1001 reason=hangup duration=12 latency_ms=35
```

必须包含：

- call_id
- caller_id
- callee_id
- old_status
- new_status
- action
- reason
- actor_id
- duration
- request_id

3. 审计表

可选新增：

```text
call_events
```

字段：

- call_id
- event_type
- actor_id
- old_status
- new_status
- reason
- payload
- created_at

用于复盘客户投诉。

### 压测

压测场景：

- 单用户连续呼叫、挂断、重拨 100 次。
- 双用户互相呼叫、拒接、取消、重拨。
- 1000 个并发用户随机创建/挂断。
- Redis 临时不可用，DB lock 兜底。
- 后端实例重启，残留通话自动释放。

验收指标：

- 挂断后释放 P95 小于 500ms。
- 挂断后 2 秒内重拨成功率 99.9%。
- 不出现永久 `calling/connected` 残留。
- 不出现同一用户多条活跃通话。

### 客户端体验优化

- 挂断后按钮文案不显示“通话未就绪”，改为“正在结束通话，请稍后重试”，并尽量不超过 1 秒。
- 如果后端返回 `released=true`，客户端立即允许再次呼出。
- 快速重拨时显示正常呼叫中，不暴露底层 RTC 初始化细节。
- 通话失败时提示明确区分：
  - 对方正在通话中。
  - 音视频服务未配置。
  - 网络连接不可用。
  - 上次通话正在释放。

### 运维工具

增加管理接口：

- 查询用户当前 active call。
- 强制释放指定用户 active call。
- 批量释放超过阈值的残留通话。
- 查看最近状态流转事件。

这些接口只允许管理员或内部运维调用。

### 验收标准

必须通过：

- 压测后无脏 active 状态。
- 管理后台能定位任意一次通话为何结束。
- 用户快速重拨体验稳定。
- 生产日志能回答“为什么客户挂断后不能立刻再打”。

## 风险和边界

- 2 秒快速释放只适合未接通或明确挂断的通话，不能直接套到已接通通话。
- 已接通通话必须依赖心跳超时，否则弱网下会误杀。
- 多端同时登录时，需要确认同账号是否允许多设备同时通话；如果不允许，active key 应按用户维度唯一。
- 老客户端不认识 `call_released` 时，后端仍要保留 `call_ended` / `call_cancelled` 兼容事件。
- 如果 RTC 服务本身 Token 创建慢，不能用“通话未就绪”掩盖，应拆分为 RTC 配置/Token/业务 active 三类错误。
