# 真机测试全部功能

目标：用电脑控制两台 Android 真机，模拟真实用户完成 App 核心功能检测，并产出可复现的日志、截图、录屏和结论。

本文面向本地真机测试环境。真机不能访问电脑的 `127.0.0.1`，必须访问电脑局域网 IP。

- 当前电脑局域网 IP：`192.168.1.100`
- 本地 API：`http://192.168.1.100:8080/api/v1`
- 本地后台：`http://192.168.1.100:8082`
- 本地健康检查：`http://192.168.1.100:8080/health`
- Android 包名：`com.genericim.app`
- 两台设备：设备 A、设备 B
- 推荐账号：A 登录 `test_a`，B 登录 `test_b`
- 默认不重新安装 App，不清理 App 数据，避免触发手机侧安装验证、权限重授和登录态丢失。

如果电脑 IP 或端口变化，以实际为准：

```powershell
Get-NetIPAddress -AddressFamily IPv4
```

当前 `compose.yaml` 默认端口：

```text
api   -> 8080
admin -> 8082
```

## 1. 测试原则

优先用自动化控制，坐标点击只作为兜底。

推荐控制顺序：

1. `adb shell am` 启动页面、清理进程、控制系统状态。
2. `uiautomator dump` 获取页面控件树。
3. 按控件文本、content-desc、resource-id 定位点击。
4. 最后才使用 `adb shell input tap x y` 坐标点击。

每个失败必须保留：

- 当前截图
- 当前控件树 XML
- 设备日志
- 后端接口日志或失败接口响应
- 复现步骤

本测试不是只测主链路。必须做到：

- 每个页面都要扫描控件树。
- 每个可点击控件都要进入测试清单。
- 每个按钮、Tab、菜单、开关、输入框、弹窗按钮都要执行一次正向测试。
- 每个危险按钮至少验证弹窗和取消路径，例如删除、退出、清空、注销、拉黑。
- 每个入口都要验证返回路径。
- 每个失败都要实时写入日志并截图。
- 测试结束时未覆盖按钮数量必须为 `0`，否则不能标记全量通过。

## 2. 设备准备

连接两台真机后执行：

```powershell
adb devices
```

必须看到两个 `device` 状态的设备。

记录设备序列号：

```powershell
$env:DEV_A="设备A序列号"
$env:DEV_B="设备B序列号"
```

查看设备品牌、型号、系统版本：

```powershell
adb -s $env:DEV_A shell getprop ro.product.manufacturer
adb -s $env:DEV_A shell getprop ro.product.model
adb -s $env:DEV_A shell getprop ro.build.version.release

adb -s $env:DEV_B shell getprop ro.product.manufacturer
adb -s $env:DEV_B shell getprop ro.product.model
adb -s $env:DEV_B shell getprop ro.build.version.release
```

建议设备角色：

| 设备 | 用途 |
| --- | --- |
| A | 主测设备，覆盖登录、发送、发起通话、发红包、后台切换、推送接收 |
| B | 对端设备，覆盖接收、回复、离线、锁屏、接听、推送唤醒 |

## 3. 已安装 App 检查与启动

默认真机上已经装好 App。测试脚本不要自动执行 `adb install`，也不要自动执行 `pm clear`。

检查 App 是否已安装：

```powershell
adb -s $env:DEV_A shell pm list packages com.genericim.app
adb -s $env:DEV_B shell pm list packages com.genericim.app
```

预期输出包含：

```text
package:com.genericim.app
```

查看当前安装版本：

```powershell
adb -s $env:DEV_A shell dumpsys package com.genericim.app | findstr /i "versionName versionCode"
adb -s $env:DEV_B shell dumpsys package com.genericim.app | findstr /i "versionName versionCode"
```

启动 App：

```powershell
adb -s $env:DEV_A shell monkey -p com.genericim.app -c android.intent.category.LAUNCHER 1
adb -s $env:DEV_B shell monkey -p com.genericim.app -c android.intent.category.LAUNCHER 1
```

强杀 App：

```powershell
adb -s $env:DEV_A shell am force-stop com.genericim.app
adb -s $env:DEV_B shell am force-stop com.genericim.app
```

如需测试冷启动，可强杀后重新启动，但不要清数据：

```powershell
adb -s $env:DEV_A shell am force-stop com.genericim.app
adb -s $env:DEV_A shell monkey -p com.genericim.app -c android.intent.category.LAUNCHER 1
```

## 3.1 可选维护步骤：仅人工确认后执行

以下命令会触发手机安装验证、权限重授或登录态丢失。自动化脚本默认禁止执行。

重新安装 APK：

```powershell
adb -s $env:DEV_A install -r build\app\outputs\flutter-apk\app-release.apk
adb -s $env:DEV_B install -r build\app\outputs\flutter-apk\app-release.apk
```

清理 App 数据：

```powershell
adb -s $env:DEV_A shell pm clear com.genericim.app
adb -s $env:DEV_B shell pm clear com.genericim.app
```

只有在以下情况才允许执行：

- 当前安装版本错误。
- App 数据污染导致无法复现。
- 明确需要测试首次安装、首次授权、首次登录流程。
- 用户明确要求重新安装或清数据。

## 5. 权限准备

通知权限：

```powershell
adb -s $env:DEV_A shell appops set com.genericim.app POST_NOTIFICATION allow
adb -s $env:DEV_B shell appops set com.genericim.app POST_NOTIFICATION allow
```

相机、麦克风、定位权限按系统弹窗确认。自动化脚本必须检测权限弹窗，并点击“允许”。

常见权限弹窗文本：

```text
允许
仅使用期间允许
使用 App 时允许
始终允许
不允许
```

拒绝权限也必须单独测一次，验证 App 不白屏、不闪退，并给出明确提示。

## 7. 全量按钮遍历规则

每进入一个页面，必须先生成页面快照：

```powershell
adb -s $env:DEV_A exec-out screencap -p > "$env:RUN_DIR\A-$caseId-screen-before.png"
adb -s $env:DEV_A shell uiautomator dump /sdcard/window.xml
adb -s $env:DEV_A pull /sdcard/window.xml "$env:RUN_DIR\A-$caseId-window-before.xml"
```

从 `window.xml` 中提取所有控件。以下控件必须进入测试清单：

- `clickable="true"`
- `long-clickable="true"`
- `checkable="true"`
- `class` 包含 `EditText`
- `class` 包含 `Button`
- `class` 包含 `Switch`
- `class` 包含 `CheckBox`
- `class` 包含 `RadioButton`
- `class` 包含 `SeekBar`
- `content-desc` 非空的图标按钮
- `text` 非空的菜单项、Tab、列表操作项

每个控件生成唯一 ID：

```text
页面名 + 控件类型 + text/content-desc/resource-id + bounds
```

示例：

```text
CHAT_DETAIL.BUTTON.发送.[920,2130][1070,2210]
HOME.TAB.消息.[0,2200][215,2280]
SETTINGS.SWITCH.新消息通知.[850,520][1020,620]
```

遍历要求：

| 控件类型 | 必测动作 | 通过标准 |
| --- | --- | --- |
| 普通按钮 | 点击 | 页面变化、弹窗、接口请求或状态变化符合预期 |
| Tab | 点击并返回 | Tab 内容加载，不白屏 |
| 图标按钮 | 点击 | 弹层或页面正确打开 |
| 输入框 | 聚焦、输入、清空 | 键盘正常，文字不遮挡，校验正确 |
| 开关 | 开、关各一次 | 状态保存，刷新后不丢 |
| 复选框/单选框 | 选中、取消 | 状态正确 |
| 滑块 | 左/中/右三档 | 值变化正确，UI 不错位 |
| 列表项 | 点击首条、中间、末条 | 详情打开正确 |
| 长按项 | 长按 | 菜单出现，取消路径可用 |
| 危险操作 | 点击、取消、再确认测试环境允许的项 | 有二次确认，不误执行 |

严禁只测“看起来常用”的按钮。只要控件树中出现可操作控件，就必须记录测试结果。

## 8. 实时日志反馈协议

自动化执行时必须实时写三类日志。

### 8.1 JSONL 事件日志

文件：

```text
artifacts/real-device-test-YYYYMMDD-HHMMSS/events.jsonl
```

每一步追加一行 JSON：

```json
{"time":"2026-06-23T21:40:00+08:00","case_id":"CHAT-006","device":"A","page":"聊天详情","action":"tap","target":"发送","status":"running"}
{"time":"2026-06-23T21:40:02+08:00","case_id":"CHAT-006","device":"A","page":"聊天详情","action":"tap","target":"发送","status":"pass","evidence":["A-CHAT-006-screen-after.png","A-CHAT-006-window-after.xml"]}
```

失败格式：

```json
{"time":"2026-06-23T21:40:05+08:00","case_id":"PUSH-HMS-004","device":"A","page":"锁屏","action":"wait_notification","target":"HMS消息通知","status":"fail","reason":"60秒未收到通知","evidence":["A-PUSH-HMS-004-logcat.txt","A-PUSH-HMS-004-screen.png"]}
```

### 8.2 实时 Markdown 报告

文件：

```text
artifacts/real-device-test-YYYYMMDD-HHMMSS/report.md
```

每完成一个用例立即追加：

```markdown
| 时间 | 用例 | 设备 | 页面 | 控件/功能 | 结果 | 证据 |
| --- | --- | --- | --- | --- | --- | --- |
| 21:40:02 | CHAT-006 | A/B | 聊天详情 | 发送文本 | 通过 | A-screen, B-screen |
```

### 8.3 实时控制台反馈

执行器必须在控制台实时打印：

```text
[RUN] CHAT-006 A 点击发送按钮
[PASS] CHAT-006 B 收到文本消息，用时 1.2s
[FAIL] PUSH-HMS-004 A 锁屏 60s 未收到 HMS 通知，已保存截图和 logcat
[BLOCKED] CALL-007 RTC 未配置，前端提示正常，按预期跳过真实通话
```

状态只能使用：

```text
RUN / PASS / FAIL / BLOCKED / SKIP
```

`SKIP` 必须写原因，例如“当前账号无余额”“当前设备无 NFC”“用户未授权重装 App”。

## 10. 全量按钮覆盖率统计

每轮测试必须生成：

```text
artifacts/real-device-test-YYYYMMDD-HHMMSS/coverage.csv
```

字段：

```csv
page,control_id,type,text,content_desc,bounds,action,status,case_id,evidence,reason
```

示例：

```csv
聊天详情,CHAT_DETAIL.BUTTON.发送.[920,2130][1070,2210],button,发送,,[920,2130][1070,2210],tap,PASS,CHAT-006,A-screen.png,
设置,SETTINGS.BUTTON.退出登录.[40,1900][1040,1990],button,退出登录,,[40,1900][1040,1990],tap,PASS,SET-040,A-exit-cancel.png,
```

统计要求：

| 指标 | 要求 |
| --- | --- |
| discovered_controls | 扫描到的可操作控件总数 |
| tested_controls | 已执行控件数 |
| passed_controls | 通过控件数 |
| failed_controls | 失败控件数 |
| blocked_controls | 阻塞控件数 |
| untested_controls | 未测试控件数，必须为 0 |

如果有未测试控件，报告结论必须是“不通过”。

## 11. P0 核心链路

| ID | 模块 | 操作 | 预期 | 证据 |
| --- | --- | --- | --- | --- |
| P0-001 | 启动 | A/B 冷启动 App | 不白屏、不闪退，进入登录或首页 | 截图、logcat |
| P0-002 | 登录 | A/B 分别登录测试账号 | 登录成功，进入首页 | 截图、接口日志 |

## 14. 华为推送专项

适用于华为或荣耀真机。

### 10.1 设备信息

```powershell
adb -s $env:DEV_A shell getprop ro.product.manufacturer
adb -s $env:DEV_A shell getprop ro.build.version.emui
adb -s $env:DEV_A shell getprop ro.build.version.magic
```

### 10.2 Token 检查

登录后抓日志：

```powershell
adb -s $env:DEV_A logcat -v time | findstr /i "hms push token vendor huawei"
```

预期：

- 设备识别为 Huawei/Honor。
- `push_channel` 为 `hms`。
- 能拿到非空 HMS token。
- 后端保存 token 成功。

### 10.3 前台推送

步骤：

1. A 停留 App 前台。
2. B 给 A 发消息。
3. 观察 A 的 App 内消息和通知策略。

预期：

- App 内消息实时出现。
- 如果前台策略不弹系统通知，必须符合产品设计。

### 10.4 后台推送

步骤：

```powershell
adb -s $env:DEV_A shell input keyevent KEYCODE_HOME
```

B 给 A 发消息。

预期：

- A 收到系统通知。
- 点击通知可进入 App。
- 消息不丢失，未读数正确。

### 10.5 锁屏推送

步骤：

```powershell
adb -s $env:DEV_A shell input keyevent KEYCODE_POWER
```

B 给 A 发消息。

预期：

- A 锁屏通知可见。
- 亮屏后通知仍存在。
- 点击通知进入正确页面或首页。

### 10.6 杀进程推送

步骤：

```powershell
adb -s $env:DEV_A shell am force-stop com.genericim.app
```

B 给 A 发消息。

预期：

- 如果厂商通道支持 force-stop 后唤醒，应收到通知。
- 如果系统限制 force-stop 后推送，报告中必须明确标记为系统限制，不判定为 App 内实时链路失败。

### 10.7 Token 失效

步骤：

1. 后台清理 A 的旧 token 或模拟 token 失效。
2. A 重新登录。
3. B 再次发消息。

预期：

- A 重新上报 token。
- 后端使用最新 token。
- 无效 token 不应导致后台误判发送成功。

## 19. 放行标准

必须满足：

- P0 全部通过。
- 无 App 闪退、白屏、死循环。
- A/B 单聊消息无丢失、无重复、无乱序。
- 后台/锁屏推送至少在目标厂商设备上通过。
- 华为设备 HMS token 能上报并用于发送。
- 后台管理可登录，配置可读取。
- 所有失败项都有截图、日志、复现步骤。
- `coverage.csv` 中 `untested_controls = 0`。
- 每一个扫描到的按钮、Tab、开关、输入框、弹窗按钮都有 PASS/FAIL/BLOCKED/SKIP 结论。

允许带问题放行的范围：

- P2 体验问题。
- 明确受系统限制的推送场景，例如手动 force-stop 后系统禁止唤醒。
- 非生产配置未开启导致的功能不可用，但前端必须有明确提示。

不允许放行：

- 登录失败。
- 消息收发失败。
- 离线补偿失败。
- 推送 token 不上报。
- 后台管理无法进入。
- 支付/钱包出现错误扣款或余额错误。
- 通话入口空白或无提示失败。
