# 两步验证真实登录拦截修复计划

> 适用项目：`genericim-tongba`  
> 影响端：Go 后端、Flutter Android/iOS/Windows/Web、H5  
> 缺陷级别：P0 账号安全  
> 方案状态：待实施  
> 目标：修复“两步验证已开启但重新登录仍直接进入”的假保护问题，确保所有需要两步验证的登录路径在第二步验证成功前绝不签发正式 Token。

## 1. 问题结论

当前“两步验证”只完成了设置界面和服务端字段保存，没有接入登录认证链路，因此不能提供真实保护。

已确认的缺陷包括：

1. Flutter 开启两步验证时，把用户输入的二次密码直接做 SHA-256；
2. 同一 SHA-256 结果同时保存到手机本地和服务端；
3. 后端 `/user/two-step` 只保存 `two_step_enabled`、密码哈希和提示语；
4. `/auth/login` 验证完主密码后不读取 `TwoStepEnabled`，直接生成正式 Token；
5. Flutter 登录逻辑只处理设备锁挑战 `code=1001`，没有两步验证挑战；
6. 关闭开关只改变本地状态，没有可靠关闭服务端设置；
7. 开启接口失败时客户端没有检查最终响应，界面仍可能显示“已开启”；
8. 通过 `/user/privacy` 可以修改 `two_step_enabled`，但不强制同时配置有效二次密码；
9. 没有错误次数限制、挑战票据、单次消费、恢复流程和安全审计；
10. 普通登录、设备锁验证、二维码登录等 Token 签发入口没有统一的安全门。

所以这不是单个页面 Bug，而是认证状态机缺失。

## 2. 修复原则

### 2.1 服务端是唯一可信边界

客户端开关、SharedPreferences 和页面状态都不能决定是否需要两步验证。服务端必须在签发 Token 前读取账号的真实两步验证状态，并完成校验。

### 2.2 第二步未通过，不得签发 Token

包括但不限于以下入口：

- 账号密码登录；
- 新设备登录；
- 设备锁短信验证完成；
- Windows 登录；
- H5/Web 登录；
- 二维码登录确认；
- 管理员代操作以外的所有用户认证入口。

任何入口只要尚有必需验证步骤未完成，只能签发短时、单用途的挑战票据，不能返回正式 JWT。

### 2.3 不再由客户端生成或保存密码哈希

客户端通过 TLS 把二次密码提交给专用接口，服务端使用带独立盐的自适应密码哈希保存。快速 SHA-256 不适合密码存储；OWASP 推荐 Argon2id，兼容场景可使用 bcrypt 或 PBKDF2。

### 2.4 “两步”与“两因素”保持诚实

当前产品形态是“主密码 + 二次登录密码”，两个凭据都属于知识因素，因此可以称为“两步验证”或“二次登录密码”，不能宣传成真正的双因素认证。

本计划先修复现有二次密码的真实拦截能力；后续如接入 TOTP、可信设备批准或安全密钥，再升级为真正的 2FA/MFA。

## 3. 目标登录流程

### 3.1 普通登录

```text
客户端提交账号、主密码、设备信息
                |
                v
服务端验证账号状态、限流、主密码
                |
                v
是否需要设备锁验证？ ---- 是 ----> 返回 code=1001 + challenge_ticket
                |                            |
                否                           v
                |                    完成设备锁验证
                |                            |
                +----------------------------+
                |
                v
是否开启两步验证？ ------ 是 ----> 返回 code=1002 + challenge_ticket
                |                            |
                否                           v
                |                    提交二次验证密码
                |                            |
                +----------------------------+
                |
                v
所有必需步骤均通过
                |
                v
生成 JWT、写入 user_sessions/user_devices、返回登录成功
```

### 3.2 关键规则

- 主密码验证成功不等于登录成功；
- 设备锁验证成功后，如果两步验证开启，仍不能直接发 Token；
- 两步验证票据只能用于当前账号、当前设备和当前登录请求；
- 挑战票据成功使用一次后立即作废；
- 票据超时、设备不一致或步骤乱序时必须重新登录；
- 刷新已有有效 Token 不重复要求二次密码；
- 两步验证开启、重置或恢复后，应按产品策略撤销其他设备会话。

## 4. 产品交互设计

### 4.1 开启两步验证

开启流程不再只是输入一个新密码：

1. 用户点击“两步验证”开关；
2. 先验证当前账号主密码，防止已解锁手机被他人直接开启或替换二次密码；
3. 输入新的二次登录密码；
4. 再次确认二次登录密码；
5. 可选填写安全提示，但提示不得包含或复述密码；
6. 服务端保存成功后，客户端才把开关显示为开启；
7. 服务端保存失败时保持关闭并展示错误；
8. 开启成功后提示其作用范围和找回方式。

建议文案：

```text
两步验证
登录时除账号密码外，还需要输入二次登录密码。
请勿将二次登录密码设置为与账号密码相同。
```

### 4.2 重新登录

主密码正确且两步验证开启时，客户端进入不可跳过的第二步页面：

```text
验证二次登录密码
为保护账号安全，请输入你设置的二次登录密码。

[ 二次登录密码                  ]
密码提示：我的第一个工作地点（可选显示）

[ 验证并登录 ]
[ 忘记二次登录密码 ]
```

不允许通过返回键、关闭弹窗、切换页面或重启应用绕过验证进入主界面。

### 4.3 关闭两步验证

关闭流程：

1. 输入当前二次登录密码；
2. 服务端验证成功后关闭；
3. 删除服务端二次密码哈希和提示；
4. 客户端收到成功响应后关闭开关；
5. 清理旧版本遗留的本地 SHA-256 和提示数据；
6. 失败时保持开启。

仅点击确认对话框不能关闭服务端保护。

### 4.4 忘记二次登录密码

恢复流程不能弱于正常登录流程。建议第一期使用项目已有绑定手机能力：

1. 输入账号主密码；
2. 向已绑定手机号发送一次性验证码；
3. 验证短信验证码；
4. 设置新的二次登录密码；
5. 撤销全部其他设备会话；
6. 当前设备重新完成登录；
7. 记录安全审计事件。

账号没有绑定手机号时，不允许用密码提示直接重置。应提示通过人工申诉或已登录可信设备确认，不能提供弱安全问题绕过。

## 5. 后端认证状态机

### 5.1 统一挑战对象

新增统一登录挑战结构，优先存储在 Redis：

```go
type LoginChallenge struct {
    ID                   string    `json:"id"`
    UserUUID             string    `json:"user_uuid"`
    DeviceID             string    `json:"device_id"`
    DeviceType           string    `json:"device_type"`
    DeviceName           string    `json:"device_name"`
    ClientIP             string    `json:"client_ip"`
    PrimaryVerified      bool      `json:"primary_verified"`
    DeviceLockRequired   bool      `json:"device_lock_required"`
    DeviceLockVerified   bool      `json:"device_lock_verified"`
    TwoStepRequired      bool      `json:"two_step_required"`
    TwoStepVerified      bool      `json:"two_step_verified"`
    Attempts             int       `json:"attempts"`
    CreatedAt            time.Time `json:"created_at"`
    ExpiresAt            time.Time `json:"expires_at"`
}
```

要求：

- ID 使用密码学安全随机数，至少 256 bit；
- Redis 中只保存票据摘要或不可预测票据；
- TTL 建议 5 分钟；
- 绑定账号、设备 ID、客户端 IP 和登录步骤；
- 成功后原子消费；
- 超过最大尝试次数立即作废；
- Redis 不可用时，对已开启两步验证的账号必须失败关闭，不能绕过直接登录。

### 5.2 响应码

保留当前设备锁：

```text
1001 = device_lock_required
```

新增：

```text
1002 = two_step_required
1003 = login_challenge_expired
1004 = login_challenge_invalid
1005 = two_step_locked
1006 = client_upgrade_required
```

如果现有项目已有相同数字，应以全局错误码表重新分配，禁止冲突。服务端同时返回稳定的字符串 `reason`，客户端优先按 `reason` 处理，数字码用于兼容。

### 5.3 API 设计

#### 开启

```http
POST /api/v1/user/two-step/enable
Authorization: Bearer <token>

{
  "current_password": "主密码",
  "two_step_password": "二次登录密码",
  "hint": "可选提示"
}
```

#### 关闭

```http
POST /api/v1/user/two-step/disable
Authorization: Bearer <token>

{
  "two_step_password": "二次登录密码"
}
```

#### 登录第二步验证

```http
POST /api/v1/auth/two-step/verify

{
  "challenge_ticket": "一次性票据",
  "two_step_password": "二次登录密码"
}
```

成功后才返回：

```json
{
  "token": "正式 JWT",
  "user": {}
}
```

#### 恢复

```http
POST /api/v1/auth/two-step/recovery/send-code
POST /api/v1/auth/two-step/recovery/reset
```

旧的 `/user/two-step` 接口进入兼容期后废弃，不再接受客户端提交的 `password_hash`。

### 5.4 Token 签发集中化

新增唯一的最终签发方法，例如：

```go
func (h *AuthHandler) completeLoginAfterAllChallenges(...)
```

它必须检查：

- 主密码或等价主认证步骤已通过；
- 必需的设备锁已通过；
- 必需的两步验证已通过；
- 用户状态允许登录；
- 挑战票据未过期且未消费；
- 设备信息与挑战一致。

只有该方法可以执行：

- `jwt.GenerateToken`；
- `recordUserLogin`；
- 更新最后登录时间；
- 返回 `AuthStatus.authenticated` 所需数据。

普通登录、设备锁验证和二维码登录不能各自复制 Token 签发逻辑。

## 6. 密码存储与遗留数据迁移

### 6.1 新密码存储

推荐使用 Argon2id 编码字符串写入现有或新字段：

```text
$argon2id$v=19$m=19456,t=2,p=1$<salt>$<hash>
```

参数上线前需在服务器真实配置上压测，目标是单次验证可接受，同时显著提高离线破解成本。若当前 Go 依赖和部署资源暂时不适合 Argon2id，可先用 bcrypt，cost 不低于 10，再安排升级。

禁止：

- 客户端 SHA-256；
- 无盐 SHA-256；
- 明文存储；
- 可逆加密后直接比对；
- 把哈希写回客户端 SharedPreferences；
- 在日志、埋点或错误报告中输出密码、哈希或挑战票据。

### 6.2 数据字段

建议迁移 `user_privacy_settings`：

```text
two_step_enabled           TINYINT(1) NOT NULL DEFAULT 0
two_step_password_hash     VARCHAR(255) NOT NULL DEFAULT ''
two_step_hash_version      VARCHAR(20) NOT NULL DEFAULT ''
two_step_password_hint     VARCHAR(100) NOT NULL DEFAULT ''
two_step_updated_at        DATETIME NULL
two_step_recovery_phone_at DATETIME NULL
```

不把错误次数永久写进用户表，登录失败计数优先放 Redis，并按账号、设备和 IP 多维限流。

### 6.3 现有 SHA-256 用户迁移

现有 64 位十六进制哈希无法在不知道明文的情况下直接升级为 Argon2id，采用渐进迁移：

1. 识别 `two_step_enabled=true` 且哈希为 64 位十六进制的数据为 `legacy_sha256`；
2. 新客户端登录时仍要求用户输入原二次密码；
3. 服务端临时用 SHA-256 对输入做常量时间比对；
4. 验证成功后立即用 Argon2id 重新哈希并覆盖旧值；
5. 更新 `two_step_hash_version=argon2id`；
6. 删除客户端遗留哈希；
7. 忘记旧二次密码的用户走恢复流程；
8. 兼容迁移窗口结束后删除 legacy 校验代码。

禁止因为旧哈希较弱而直接把所有已开启账号视为未开启，这会继续形成静默绕过。

## 7. Flutter 客户端改造

### 7.1 设置页

修改 `privacy_settings_page.dart`：

- 删除客户端 SHA-256 生成；
- 删除本地 `two_step_password_hash` 保存；
- 开启前验证当前主密码；
- 调用 `/user/two-step/enable`；
- 只在 `response.isSuccess` 后更新开关；
- 关闭时要求二次密码并调用 `/user/two-step/disable`；
- 失败时保持服务端返回的真实状态；
- 从 `/user/privacy` 或专用状态接口重新校准开关；
- 清理账号级 SharedPreferences 中遗留的哈希和提示；
- 防止快速重复点击并发提交。

### 7.2 登录服务

修改 `auth_service.dart`：

- 增加 `1002/two_step_required` 分支；
- 收到挑战时保持 `AuthStatus.unauthenticated`；
- 不保存 Token，不初始化 WebSocket，不加载聊天缓存；
- 增加 `verifyTwoStep(challengeTicket, password)`；
- 只有验证成功并获得正式 Token 后才执行现有登录成功流程；
- 401、票据过期、锁定等状态使用明确但不泄露账号信息的错误文案；
- 账号切换或退出时清空内存中的挑战票据。

### 7.3 登录页面

修改 `login_page.dart`：

- 主登录返回 `two_step_required` 后进入专用页面或不可跳过的全屏步骤；
- 显示服务端允许返回的密码提示；
- 支持显示剩余锁定时间；
- 支持“忘记二次登录密码”；
- 防止返回主页面；
- 应用后台恢复后检查票据是否仍有效；
- 验证成功后统一执行 `_goAfterLogin()`。

建议新建：

```text
lib/features/auth/pages/two_step_verify_page.dart
lib/features/auth/pages/two_step_recovery_page.dart
lib/features/auth/models/login_challenge.dart
```

### 7.4 Windows、Web 和 H5

所有能使用账号密码登录的客户端都必须处理 `two_step_required`。旧客户端不认识新挑战时，服务端不得降级签发 Token，只能返回“客户端版本过低，请升级后登录”。

二维码登录需要明确规则：

- 若产品把“已登录手机确认”认定为独立持有因素，可将手机批准作为第二步，但必须在服务端挑战状态中记录；
- 若当前功能定义仍是“二次登录密码”，二维码确认后 Windows 仍需输入二次密码；
- 无论采用哪种规则，二维码确认本身不能绕过账号配置的安全策略。

本修复第一版建议保持一致：二维码确认后，Windows 继续输入二次登录密码。

## 8. 设备锁与两步验证组合

当前设备锁已有 `code=1001` 短信挑战。两项同时开启时必须按统一状态机执行：

```text
主密码 -> 新设备锁短信 -> 二次登录密码 -> 正式 Token
```

需要重点修复：现有设备锁验证接口如果验证成功后直接发 Token，必须改成先检查 `TwoStepEnabled`。当仍需二次验证时返回同一个挑战的下一步骤，不能签发 Token。

登录错误次数分别统计：

- 主密码失败次数；
- 设备锁验证码失败次数；
- 二次登录密码失败次数。

三类限流不能互相覆盖，也不能通过反复申请新票据清零。

## 9. 风控和安全要求

### 9.1 限流

建议初始策略：

- 单挑战最多 5 次二次密码尝试；
- 单账号 15 分钟最多 10 次；
- 单 IP 15 分钟最多 30 次；
- 连续失败采用指数退避；
- 达到阈值后旧票据失效；
- 成功验证后只清理合理范围的失败计数，不清除全局风控记录。

具体阈值需结合真实用户量和客服能力调整。

### 9.2 错误信息

登录前响应保持通用：

- 不泄露账号是否存在；
- 不泄露账号是否开启两步验证，直到主密码验证成功；
- 不返回完整手机号；
- 密码提示仅在主密码验证成功、挑战票据有效后返回；
- 服务端日志不得写入密码和票据。

### 9.3 会话处理

- 开启两步验证：保留当前设备，默认撤销其他设备会话；
- 修改二次密码：撤销其他设备会话；
- 恢复二次密码：撤销全部会话，包括当前会话，要求重新登录；
- 关闭两步验证：记录高风险安全事件，可选择撤销其他设备；
- 管理员重置：必须留下操作人、原因、时间和目标用户审计记录。

### 9.4 安全审计事件

至少记录：

```text
two_step.enabled
two_step.disabled
two_step.challenge.created
two_step.challenge.succeeded
two_step.challenge.failed
two_step.challenge.locked
two_step.recovery.started
two_step.recovery.completed
two_step.legacy_hash.upgraded
```

日志只记录用户 ID、设备 ID、IP、结果、时间和失败原因分类，不记录秘密。

## 12. 分阶段实施计划

### 阶段 0：风险止血

目标：新版本上线前不再给用户虚假的安全承诺。

- 在未完成真实拦截的版本中隐藏或禁用“两步验证”开关；
- 已开启用户显示“需要升级后重新确认”，不能继续显示“已受保护”；
- 禁止新增 legacy SHA-256 数据；
- 统计已开启用户数量和哈希类型；
- 保留数据，不直接清空用户设置；
- 输出迁移和客服说明。

完成标准：没有新用户继续开启无效保护。

### 阶段 1：后端安全闭环

- 新增挑战服务；
- 新增密码安全哈希服务；
- 新增 enable/disable/verify/recovery 接口；
- 登录和设备锁验证接入统一状态机；
- Token 签发集中化；
- 加入限流、审计和 legacy 校验升级；
- 完成 Go 单元与集成测试；
- 默认通过功能开关关闭强制拦截，仅供测试环境验证。

完成标准：后端测试证明第二步未通过时无法得到 Token。

### 阶段 2：Flutter 与 H5 客户端

- 设置页改成服务端确认后更新；
- 删除本地哈希；
- 增加第二步验证页；
- 增加恢复页；
- 普通登录、设备锁、二维码登录全覆盖；
- Android/iOS/Windows/Web/H5 处理挑战和升级提示；
- 完成 Flutter/H5 自动化测试。

完成标准：所有受支持客户端可以完成开启、登录挑战、关闭和恢复。

### 阶段 3：兼容迁移与灰度

## 13. 后端测试计划

### 13.1 登录主路径

- 未开启两步验证：主密码正确后正常签发 Token；
- 已开启：主密码正确只返回挑战，不返回 Token；
- 二次密码正确：消费票据并签发 Token；
- 二次密码错误：不签发 Token；
- 票据过期：不签发 Token；
- 票据重复使用：第二次失败；
- 票据设备 ID 不一致：失败；
- 票据账号不一致：失败；
- Redis 不可用且账号开启两步验证：失败关闭；
- 用户被禁用：任何步骤都不能继续。

### 13.2 组合路径

- 设备锁关闭 + 两步开启；
- 设备锁开启 + 两步关闭；
- 设备锁开启 + 两步开启；
- 设备锁通过后仍返回两步挑战；
- 二维码登录不能绕过；
- Windows、Android、iOS、Web 设备类型均正确绑定；
- Token 刷新只允许已有有效会话；
- 开启或恢复后旧会话按策略失效。

### 13.3 设置与恢复

- 主密码错误不能开启；
- 二次密码与主密码相同按产品策略拒绝或强提醒；
- enable 保存 Argon2id/bcrypt，不保存 SHA-256；
- disable 必须验证二次密码；
- 普通隐私接口不能直接开启两步验证；
- 恢复验证码错误、过期、重复使用均失败；
- 恢复成功后全部会话失效；
- legacy SHA-256 验证成功后升级为强哈希。

### 13.4 安全测试

- 登录枚举信息检查；
- 账号、IP、设备三维限流；
- 并发消费同一票据只有一个成功；
- 日志敏感信息扫描；
- SQL 注入和参数边界；
- 超长 Unicode 密码与提示；
- 重放攻击；
- 客户端篡改 `two_step_enabled=false` 无效；
- 直接调用 Token 签发方法必须被状态机阻止。

## 16. 发布与回滚策略

### 16.1 发布顺序

1. 数据库兼容迁移；
2. 后端新接口和挑战服务，强制开关保持关闭；
3. Flutter/H5 新客户端；
4. 测试账号开启；
5. legacy 用户小比例灰度；
6. 全量开启强制登录拦截；
7. 移除旧接口和客户端 SHA-256 兼容写入；
8. 迁移窗口结束后删除 legacy 校验。

### 16.2 回滚原则

若新挑战链路出现故障：

- 可以停止新增用户开启两步验证；
- 可以暂停灰度扩量；
- 可以回滚客户端展示；
- 不允许通过关闭服务端校验让已开启用户静默绕过；
- 应提供安全的恢复入口或临时人工恢复流程；
- 回滚不得清除用户哈希、恢复记录和审计日志。

## 17. 完成定义

只有同时满足以下条件才能把“两步验证”标记为已完成：

- [ ] 服务端真实保存开启状态和强密码哈希；
- [ ] 客户端不保存二次密码或哈希；
- [ ] 主密码通过后、第二步未通过前没有正式 Token；
- [ ] 设备锁和两步验证组合不会提前签发 Token；
- [ ] Windows、Android、iOS、Web/H5 登录均不能绕过；
- [ ] 开启、关闭、修改、恢复全部由服务端确认；
- [ ] legacy SHA-256 用户具有可执行的迁移路径；
- [ ] 旧客户端不能降级绕过；
- [ ] 限流、票据过期、单次消费和安全日志生效；
- [ ] Go、Flutter、H5 自动化测试通过；
- [ ] Android + Windows 跨端真实登录验收通过；
- [ ] iOS 侧完成构建与登录验收；
- [ ] 发布监控能够观察失败率、锁定率和恢复率；
- [ ] 产品文案不再声称尚未实现的安全能力。

## 18. 权威安全依据

- OWASP Password Storage Cheat Sheet：密码应使用 Argon2id、bcrypt、PBKDF2 等自适应哈希，快速 SHA-256 不适合作为密码存储方案。  
  https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html
- OWASP Multifactor Authentication Cheat Sheet：MFA 需要不同类型的认证证据，并应设计可靠的恢复和重认证流程。  
  https://cheatsheetseries.owasp.org/cheatsheets/Multifactor_Authentication_Cheat_Sheet.html
- NIST SP 800-63B：密码本身不具备重放抗性；更高保障场景应优先使用抗钓鱼的密码学认证器。  
  https://pages.nist.gov/800-63-4/sp800-63b.html
- RFC 6238：后续接入基于时间的一次性密码时遵循 TOTP 标准。  
  https://www.rfc-editor.org/info/rfc6238/
